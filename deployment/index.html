Deployment ​

The workflow: agents live in their own GitHub repository, CI builds a Docker image, and Flux deploys it to your Kubernetes cluster. Every agent repository is an app with one or more agents, its own store connection, its own GitHub App and its own channels.

agent repo --push--> CI --image--> registry --Flux image automation--> HelmRelease --> cluster
                                                                            |
                                         OpenClaw --MCP--> app (/mcp) --hooks--> OpenClaw
                                         GitHub ---webhooks---> app (/channels/github) --comments--> GitHub

Pieces ​

PieceBuilt as
@chamvi/app + @chamvi/clicreateApp({ agents, modules }) boots config, store, engine (with its channels) and HTTP in order and tears them down in reverse, draining on SIGTERM. The chamvi bin with dev, build, start, run-job and migrate. See Apps & Modules
Base imageghcr.io/chamvi/node: Node 26 on Debian trixie slim, tini, uid 1000, linux/amd64 and linux/arm64; agent repositories use a two-stage Dockerfile
Helm chartchamvi/helm: one shared OCI chart, oci://ghcr.io/chamvi/helm/agent-app, for every agent app; each repository gets a small HelmRelease
Template repositorychamvi/agent-template: a GitHub template with an example agent, Dockerfile, CI that builds and tags images for Flux, and example Flux manifests

Configuration ​

Configuration comes from environment variables, typically from Kubernetes Secrets: the database URL, the HTTP port, the default model and provider API keys (CHAMVI_MODEL, CHAMVI_PROVIDER_<NAME>_* or the bare ANTHROPIC_API_KEY, ...; only providers you declare, no gateway by default, see Pick a Model; chamvi start --check checks them, the store and the agent folders in CI with the production or staging env), static API tokens for machine clients, and OpenClaw and GitHub settings. How the Secrets get into the cluster (plain Secrets, SOPS, External Secrets) is the cluster's choice.

Observability ​

The app writes structured JSON log lines to stderr, and the HTTP app serves Prometheus metrics on /metrics (the chart's optional ServiceMonitor scrapes them). OpenTelemetry spans for runs and steps are planned.
