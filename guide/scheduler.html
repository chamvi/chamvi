Cron Scheduling ​

The cron channel, @chamvi/channel-cron, fires the cron.on() subscriptions of your agents. Every replica registers the same channel; a lock in the shared store elects one replica per tick, and engine.dispatch() deduplicates a second firing of the same tick.

bash
npm install @chamvi/channel-cron @chamvi/core --save
ts
const engine = new Engine({
    store,
    agents,
    // every replica registers the same channel; a store lock fires each tick once
    channels: [cronChannel({ onError: (error, { agent, subscription }) => console.error('[cron]', agent, subscription, error) })],
});

// recovers runs, then starts the channel
await engine.start();

process.once('SIGTERM', async () => {
    // stops the channel first (no new ticks), then lets the runs in flight finish
    await engine.drain({ timeoutMs: 25_000 });
    process.exit(0);
});

cron.on(expression, options?) validates the expression (cron-parser) and the timezone and throws InvalidAgentDefinitionError for one it refuses. engine.start() starts the channel after recovering runs: it creates one hubwire scheduled component per cron subscription of the engine's agents, and the subscription of an agent without a revision (one passed in code) it cannot use (an expression croner refuses) fails engine.start() with InvalidAgentDefinitionError, naming the agent and subscription; an agent folder's goes to onError and leaves that agent unscheduled. The channel follows agents registered, replaced and removed at runtime. With @chamvi/app, schedulerModule() contributes the channel.

A second cron channel (cronChannel({ name: 'cron-eu' })) has its own on(): its subscriptions fire only there, and cron.on() ones only on the channel named cron.

One dispatch per tick ​

For a tick planned at scheduledAt, a replica:

  1. acquires the store lock cron:<agent>:<subscriptionId>:<scheduledAt ISO> for lockTtlMs (default 10 minutes). The key is never released, so a replica that fires the same tick late cannot win it again. The other replicas skip the tick.
  2. applies the subscription's overlap policy.
  3. dispatches through the channel (envelope channel the channel's name, trigger the subscription id) with payload options.payload ?? { scheduledAt } (an ISO string) and the idempotency key <subscriptionId>@<scheduledAt ISO>. A subscription's own idempotencyKey() is ignored for cron.

Starting or restarting a replica fires nothing: the first dispatch is at the next scheduled tick. Missed ticks are not caught up, neither a tick that falls into a restart nor one whose timer fires lockTtlMs or more late. A failing lock store, overlap check or dispatch reaches onError(error, { agent, subscription }), and the next tick runs normally.

Overlap policies ​

"Active" means a run of the same subscription in queued, running, waiting or interrupted.

PolicyThe tick is skipped whenDefault concurrencyKey
skip (default)any run of the subscription is activethe subscription id
queue-onea run of the subscription is still queuedthe subscription id
allownevernone

The default concurrency key makes queue-one wait: the engine starts one run per agent and key at a time (see Concurrency), so the queued run starts when the active one settles. It also makes a race harmless: when a tick checks while the previous tick's dispatch is still in flight, the second run waits instead of running alongside. A concurrencyKey(payload) on the subscription wins over the default.

Inside a conversation ​

cron.on(expression, { conversation, text }) starts each run inside an existing conversation of another channel, for example a briefing in a user's Discord DM. conversation is a ConversationRef (from @chamvi/core: { channel, account, chat, audience, address? }) naming the registered channel and the conversation identity its intake computes for a message in that chat; text is the user turn of each run. Build the reference with the platform setup's conversation() helper (Discord, WhatsApp), so it names the same conversation a message from that chat does:

ts
export const briefer = defineModelAgent({
    name: 'briefer',
    model,
    instructions: 'Write a short morning briefing and send it with the reply tool.',
    // the cron run joins the conversation, so it needs memory like the chat
    conversation: true,
    channels: [
        // later DMs from the user land in the same conversation and recall the briefing
        discord.channel.on(),
        cron.on('0 7 * * *', {
            timezone: 'Europe/Berlin',
            // the DM with user 500000000000000001: its thread id is discord:@me:<DM channel id>
            conversation: discord.conversation({ threadId: 'discord:@me:600000000000000001', user: '500000000000000001' }),
            // the user turn of each run
            text: 'Send me my morning briefing.',
        }),
    ],
    // the reply goes to the source DM: no outbound approval even in a tainted run
    tools: { reply },
});

export const brieferApp = createApp({
    agents: [briefer],
    modules: [chatModule({ channel: discord.channel })],
    // a cron dispatch has no invoker: allow it by agent (or by access.identity)
    conversations: { authorize: ({ agent }) => agent === 'briefer' },
});

The run is dispatched through that channel's trusted conversation intake (dispatchConversation) instead of a plain dispatch:

  • Its source is the conversation's channel and address: a reply emitted there needs no outbound approval, even after the run read untrusted content, while an emit to another address still waits for one.
  • text becomes the user turn and the sent reply the assistant turn of the conversation, so a later chat message there recalls both. The first firing creates the conversation when no message did.
  • The idempotency key and the overlap policy work as above, but the run carries the conversation's concurrency key (one run per conversation at a time), never the subscription id; a concurrencyKey() on the subscription is not used.
  • conversations.authorize decides as for a message, with no invoker (the access names the agent and the identity). A refusal creates no run and reaches onError. The platform's message policy (allowMessage, resolveInvoker) is not consulted: the reference is app code, never input.

conversation and text go together (InvalidAgentDefinitionError at cron.on() otherwise, also for a blank field). The agent must enable conversation, and the engine must hold the named channel: both are checked when the channel schedules the subscription. Such a subscription runs only in the app's scheduler: runJob() (and chamvi run-job) refuses it, since a job starts no channel to deliver the replies.

Timezones ​

cron.on(expression, { timezone }) takes an IANA zone; without one, the process's local zone applies. A local time that occurs twice at the fall-back change fires once, at its first occurrence. A local time the spring-forward change skips fires once, an hour later in local time.

Shutdown ​

engine.drain() (and engine.stop()) stop every channel first: the cron channel unschedules its subscriptions and waits for ticks in flight, then the drain waits for the runs. See Cancel, Drain & Recovery.

One-shot jobs ​

runJob() fires one cron subscription once and waits for its run, for a Kubernetes CronJob instead of a long-lived replica:

ts
// a Kubernetes CronJob: fire the agent's cron subscription once and exit with its outcome
const engine = new Engine({
    store,
    agents: [agent],
    // the engine must hold the channel; runJob starts it with start({ channels: false })
    channels: [cronChannel()],
});
const { status, exitCode } = await runJob({
    engine,
    agent,
    drainTimeoutMs: 120_000,
});

console.log('cron run', status);
process.exitCode = exitCode;

The tick is dispatched at the current time (the overlap policy applies). The engine is then started with start({ channels: false }), so a job never starts cron schedules or any other channel, and runs one approval tick even when the tick is skipped, so leftovers of earlier jobs make progress: a run whose pod was killed is recovered, an interrupted or answered run is executed, and an approval past its timeout is denied. The job returns when the run is completed (exit code 0), waiting for an approval, its own or a descendant's (0, the pod is not held; waitingRunId names a waiting descendant), queued behind a run of the same subscription that waits for an approval (0, under queue-one), failed or cancelled (1), or skipped by the overlap policy (0). A run that waits on the runs it dispatched keeps the job going until they settle. It polls engine.getRun every pollMs, so a run finished by another replica also ends the job. It never calls process.exit. The engine must hold the subscription's cron channel.

A job runs a full engine

engine.start() recovers and executes every queued run of every agent in the shared store, not only the cron run, and the final drain() interrupts whatever still runs after drainTimeoutMs. runJob waits only for its own run, so a leftover run is finished by a long-lived replica or by a later job pod, within that pod's drainTimeoutMs. Size drainTimeoutMs to the job's runs, and prefer a long-lived deployment with cronChannel() when runs are long.
