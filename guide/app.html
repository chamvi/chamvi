Apps & Modules ​

An agent repository is one entry file: export default createApp({ agents, modules }). @chamvi/app boots config, store, engine, channels and HTTP from environment variables and shuts them down in order; @chamvi/cli turns that into a process with chamvi dev | build | start | run-job | migrate, signals and exit codes.

bash
npm install @chamvi/app @chamvi/cli ai @ai-sdk/anthropic typeorm pg
npm install --save-dev tsdown   # for chamvi build and a TypeScript entry

@chamvi/app is a library without process concerns: it registers no signal handlers, never calls process.exit and reads no argv. Everything about the process lives in the CLI.

The entry ​

ts
// src/index.ts
import {
    consoleChannelModule,
    createApp,
    cron,
    defineModelAgent,
    http,
} from '@chamvi/app';

const digest = defineModelAgent({
    name: 'digest',
    // no model: the app's default below
    instructions: 'Summarize what happened since the last digest.',
    channels: [
        // POST /agents/digest/runs, the dashboard and MCP
        http.on(),
        // weekdays at 08:00, Berlin time
        cron.on('0 8 * * 1-5', { timezone: 'Europe/Berlin' }),
    ],
});

// synchronous and side-effect free: chamvi start | run-job | migrate load this default export
export default createApp({
    // the default model; MODEL overrides it, ANTHROPIC_API_KEY configures the provider
    model: 'anthropic/claude-sonnet-5-5',
    agents: [digest],
    // tools write to it with ctx.channels.findOneOrFail('console').emit(...)
    modules: [consoleChannelModule()],
});
  • The entry is src/index.ts. dev, build and start --dev take --entry, else the package.json field "chamvi": { "entry": "<path>" }, else src/index.ts. The built commands (start, run-job, migrate) default to dist/index.mjs and never read that field. Without any entry file the commands run the default app, createApp({}), whose agents come from ./agents: a folder of agent folders is a complete app.
  • createApp() is synchronous and side-effect free: no env read, no I/O, no provider import. Everything happens in start(), runJob() and migrate(), which the CLI calls.
  • An entry whose default export is not an app (checked with isApp(), which also recognizes an app of another installed copy) makes the CLI exit 2.
  • @chamvi/app re-exports @chamvi/core, @chamvi/access (Permission, can, canSome and the binding types, see Permissions and authup) and the common part of @chamvi/http (the Authenticator, Principal, HttpRoute* and StaticToken types, the controller helpers), so an agent repository imports one package.

dev transforms the source with the engine and the tsconfig.json that build bundles with (tsdown), so both compile the same syntax; Node resolves the imports, so relative imports carry .ts and tsconfig paths are not applied. Decorators need experimentalDecorators in that tsconfig.json, see TypeScript entries. The template tsconfig.json:

json
{
    "compilerOptions": {
        "target": "ES2023",
        "module": "NodeNext",
        "moduleResolution": "NodeNext",
        "strict": true,
        "skipLibCheck": true,
        "verbatimModuleSyntax": true,
        "allowImportingTsExtensions": true,
        "erasableSyntaxOnly": true,
        "noEmit": true
    },
    "include": ["src", "test"]
}

Env variables ​

An env variable is named after what it configures. chamvi's own settings have no prefix (MODEL, TOKENS, PUBLIC_URL, MAIL_ACCOUNTS, SANDBOX_PROVIDER), a setting for an external system carries that system's name (AUTHUP_URL, GITHUB_APP_ID, DISCORD_TOKEN, OPENCLAW_BASE_URL, ANTHROPIC_API_KEY), and conventional names keep their meaning (PORT, HOST, DATABASE_URL, NODE_ENV).

Models ​

An agent's model is optional: without one it uses the app's default (MODEL, chamvi.json or createApp({ model })). Model strings '<provider>/<model id>' resolve through the providers the app declares (env, chamvi.json, createApp({ providers })), never through the Vercel Gateway or the AI SDK's global provider; chamvi start --check checks them before a deploy. See Pick a Model.

Modules ​

Modules are orkos IModules on an eldin container, unwrapped. Eight built-in modules are always there; listing a module with a built-in's name (ModuleName) replaces it, which is also how you configure one (storeModule({ dataSource }), httpModule({ cors })). Two modules of one name, a built-in's included, throw InvalidAgentDefinitionError from createApp.

ModuleDoes
configModule()Reads every variable once (environment) and registers the config, the clock and the JSON line logger
storeModule()The database repositories over DATABASE_URL, migrated unless MIGRATE=false; without DATABASE_URL memory repositories (warned outside dev). The app builds every service from the registered repositories, plus the store-purge component: hourly purgeExpired() of the lock, idempotency and limit services (also on memory). A module of the same name that registers the repository tokens replaces it
staticTokensModule()The staticTokens() authenticator from TOKENS
engineModule()Reads the model settings (env, chamvi.json, code) into the default model and the provider resolver, builds the Engine (which checks every agent's model) with every contributed channel (AppToken.CHANNELS) and starts it, which starts the channels
agentsModule()Loads the agent packages (createApp's specifiers, chamvi.json, AGENTS) and the agent folders of AGENTS_DIR (else ./agents when it exists) before the engine starts and watches the folders (the agents-watcher component; a package whose skill preparation failed retries in agents-packages); an app with no agent at all starts with a warning
componentsModule()Runs every component (AppToken.COMPONENTS) in start mode, after the engine and before the server listens, and stops them in the stopping phase, before the drain
schedulerModule()The cron channel (cronChannel() from @chamvi/channel-cron); SCHEDULER=false leaves firing to Kubernetes CronJobs and chamvi run-job (cron.on() subscriptions still validate)
httpModule()The http, mcp and webhook channels, createHttpApp() with every contributed route and authenticator, mounting every contributed channel with an in at /channels/<name>, the graceful shutdown, serve() on HOST:PORT

An app's own tables live in a database module (databaseModule() of @chamvi/app): its own data source on the same DATABASE_URL, its own migrations, never chamvi's store.

The optional modules ship with the package they configure, on its /module subpath (@chamvi/app is an optional peer there, and the package's main entry never imports it), so install the feature package of each one you use. Each factory reads and checks its variables when it is called, that is when the entry is imported, so a malformed one fails before the app starts. The modules of a connection page (githubModule(), toolMailModule(), toolCalendarModule()) resolve their connection in setup, from the env and the connection store; one not configured starts idle and its tools report it. sandboxModule().manager exists at once; githubModule().app is a facade at once, bound when the factory finds a complete env, else in setup (until then each use throws ConnectionNotConfiguredError); knowledgeModule().knowledge exists once setup built it. Each module also provides its instance on the engine before it starts, so a tools factory injects it per execution with the package's inject*Context(ctx) (see Context); a channel a module contributes is reached with ctx.channels.findOne(name):

ts
// src/index.ts
import {
    ToolDeniedError,
    createApp,
    defineModelAgent,
} from '@chamvi/app';
import { githubModule } from '@chamvi/github/module';
import { openclawModule } from '@chamvi/channel-openclaw/module';
import { sandboxModule } from '@chamvi/sandbox/module';
import { uiModule } from '@chamvi/ui/module';
import { codingTools } from '@chamvi/coding';
import { github, injectGithubContext } from '@chamvi/github';
import { injectSandboxContext } from '@chamvi/sandbox';

// every factory reads its env when it is called (GITHUB_APP_ID, GITHUB_APP_PRIVATE_KEY, ...)
const githubApp = githubModule();
// SANDBOX_PROVIDER, when set, wins over the option
const sandbox = sandboxModule({
    provider: 'docker',
    allowRepo: (url) => url.startsWith('https://github.com/acme/'),
});

const repro = defineModelAgent({
    name: 'repro',
    instructions: 'Reproduce the reported bug with a failing test and comment the result.',
    channels: [github.on('issues.labeled')],
    // each module provides its instance on the engine; a factory injects it per execution
    // (github.app and sandbox.manager still exist at import time, for definition-time use)
    tools: (ctx) => {
        const manager = injectSandboxContext(ctx);

        return {
            ...injectGithubContext(ctx).readTools(),
            ...manager.tools(),
            ...codingTools(manager),
        };
    },
    hooks: {
        // every shell command waits for the owner, asked in their OpenClaw chat
        async beforeToolExecution({ toolName, input }, ctx) {
            if (toolName !== 'bash') {
                return input;
            }

            const { approved } = await ctx.channels.findOneOrFail('openclaw').approve({
                title: 'Run a shell command?',
                body: (input as { command: string }).command,
            });

            if (!approved) {
                throw new ToolDeniedError('The owner refused the command.');
            }

            return input;
        },
    },
});

export default createApp({
    // repro has no model of its own: it takes this default
    model: 'anthropic/claude-sonnet-5-5',
    agents: [repro],
    modules: [
        // the github channel: deliveries at POST /channels/github, comments out
        githubApp,
        // attached to the engine on start, closed after the engine drained
        sandbox,
        // the channel named 'openclaw', approval links from PUBLIC_URL
        openclawModule(),
        // the dashboard at /ui
        uiModule(),
    ],
});

Channel names are unique per app, so openclawModule() beside openclawModule({ name: 'ops' }) contributes two channels (ctx.channels.findOne('ops')); two channels of one name fail the setup with InvalidAgentDefinitionError. @chamvi/app/authup stays in the app package, since @chamvi/http cannot depend on @chamvi/app.

With PUBLIC_URL set, the GitHub and OpenClaw modules link approvals to the dashboard: <PUBLIC_URL><basePath>/ui/approvals?run=<runId>&approval=<approvalId>, without a token. A missing required variable throws InvalidAgentDefinitionError naming it, from the factory or, for a module that also reads the connection store, from setup (a GitHub module with nothing set starts idle instead); no message ever echoes a value.

TIMEZONE (an IANA zone such as Europe/Berlin, default UTC) sets the zone utilityTools() from @chamvi/tool-utils reads dates in; it is read when the factory is called, and an invalid zone throws InvalidAgentDefinitionError. It is optional and needs no module.

Setup contributes, onReady consumes ​

orkos sets every module up in dependency order, then calls every onReady. chamvi splits the work along that line:

  • In setup, a module registers what it contributes on the container's collection tokens: AppToken.HTTP_ROUTES, HTTP_CONTROLLERS and OPENAPI_DOCUMENTS (Controllers), CHANNELS, COMPONENTS (background components), AUTHENTICATORS (with an order, lowest first), LIFECYCLE_HOOKS and AGENT_CHECKS (an (agent) => void that throws InvalidAgentDefinitionError for a folder agent the module could not serve, run before the agent is registered).
  • In onReady, the consumers build: the engine module collects the channels, the http module the routes, the controllers (their factories run here), the authenticators and the channels it mounts.

So a contribution never depends on module order. A module that resolves ENGINE or SERVER in its own onReady lists that module in dependencies. Nothing starts in onReady: the engine and the http module register start steps, which the app runs (the engine with its channels, then the components, then the started hooks and listening) only once every module's onReady ran, user modules included. So a configuration error any of them finds starts nothing: no queued run of the shared store executes on a replica that then exits 2.

Start and stop ​

app.start() resolves once the server listens, so /readyz turns green only after everything runs:

  1. config
  2. store (and the migrations, advisory-locked, so every replica may run them)
  3. every onReady: the engine is built with every contributed channel, the agent folders are loaded into it, the HTTP app is built, nothing runs yet
  4. engine.start(): recovery, then every channel's start() (the cron schedule among them)
  5. the components (the store purge, the agents dir watcher, the knowledge poll, your own), then the started hooks
  6. serve() on HOST:PORT, listening last

app.stop() is memoized and also stops a start still setting up (which then never listens):

  1. /readyz answers 503, then READINESS_DELAY_MS (0)
  2. the stopping hooks, in setup order: the components stop among them, up to DRAIN_TIMEOUT_MS (a component that does not stop in time is logged and stop() rejects)
  3. the app's closers (SSE streams, MCP waits)
  4. server.close()
  5. engine.drain(): every channel's stop() first, then the runs get what remains of the same DRAIN_TIMEOUT_MS (30 s) budget, which began with the components' stop: the two together never take longer than one timeout
  6. up to CLOSE_TIMEOUT_MS (5 s) for the close, then server.close(true)
  7. the workspace manager closes (with sandboxModule, up to 30 s)
  8. the database modules' data sources (after the drained hooks) and the store's data source are closed

orkos swallows teardown errors; chamvi does not: every teardown error is logged, and stop() then rejects with app_stop_failed (the CLI exits 1). An app runs one lifecycle: a second start(), runJob() or migrate() rejects with app_in_use.

runJob({ agent, subscription? }) builds config, store and engine (with the folder agents, loaded once), starts no channel and no HTTP, fires the cron subscription once through runJob() and tears down. migrate() only migrates the store and every database module; it fails without DATABASE_URL.

Background components ​

A job that runs beside the engine, such as a poll or a periodic cleanup, is a hubwire component contributed to AppToken.COMPONENTS as { name, component }. The components module runs them as one group, in start mode outside a check only: they start in contribution order (the order the modules set up, which follows their dependencies, not the order of the module list) after engine.start() and before the server listens (a failing start() fails the app start and stops the ones already started), and stop in the stopping phase, before the drain (a module set up before the components module runs its stopping hook first). Names follow the agent-name rule and are unique; a bad or duplicate name throws InvalidAgentDefinitionError. A useFactory contribution is built in the components module's onReady, so before the onReady of any module set up after it: resolve only what setup registered. Add hubwire to your app's dependencies:

ts
export function reportModule(): IModule {
    return {
        name: 'report',

        async setup(container: IContainer) {
            const context = container.resolve(AppToken.CONTEXT);

            // components run in start mode only: a check, a job or a migrate contributes none
            if (context.mode !== 'start' || context.check) {
                return;
            }

            const logger = container.resolve(AppToken.LOGGER);

            container.registerMany(AppToken.COMPONENTS, {
                useValue: {
                    // agent-name rule, unique per app; listed by GET /components
                    name: 'nightly-report',
                    component: defineIntervalComponent({
                        name: 'nightly-report',
                        intervalMs: 60 * 60 * 1000,
                        // the app clock, so tests step it with a ControllableClock
                        clock: container.resolve(AppToken.CLOCK),
                        // never hold the process open for a background job
                        unref: true,
                        handler: async ({ signal }) => {
                            signal.throwIfAborted();
                            // a throw after logging marks the pass failed in the status
                            logger.info('report written');
                        },
                    }),
                },
            });
        },
    };
}

Each component's last success, last error, last pass and a pass in flight are listed by GET /components and on the dashboard's Components page, together with the channels that report a status (the cron channel).

Writing a module ​

The module contract comes from the main entry of @chamvi/app: AppToken, ModuleName, AppContext, ILifecycleHook, the env readers and the orkos IModule and eldin IContainer types, so a module needs no direct orkos or eldin import. A module that shares an instance with tools provides it in the engineCreated hook and exports an inject* function next to it, keeping its key internal:

ts
export interface IAuditLog {
    write(line: string): void;
}

// the key stays inside the package; the pair below is its public face
const AUDIT_CONTEXT = defineContextKey<IAuditLog>('audit');

export function injectAuditContext<S extends StateSchema = StateSchema>(ctx: ToolContext<S>): IAuditLog {
    return inject(ctx, AUDIT_CONTEXT);
}

export function auditModule(): IModule {
    let unsubscribe: (() => void) | undefined;

    return {
        name: 'audit',
        // onReady resolves ENGINE, so the engine module sets up first
        dependencies: [ModuleName.ENGINE],

        // setup contributes: every consumer (engine, http) builds in onReady
        async setup(container: IContainer) {
            container.registerMany(AppToken.HTTP_ROUTES, {
                useValue: {
                    method: 'GET',
                    path: '/audit',
                    // extra routes check their own credentials
                    handler: async () => ({ status: 200, body: { ok: true } }),
                },
            });

            const logger = container.resolve(AppToken.LOGGER);
            const log: IAuditLog = { write: (line) => logger.info(line) };

            container.registerMany(AppToken.LIFECYCLE_HOOKS, {
                useValue: {
                    name: 'audit',
                    // before engine.start(): tools reach the log through injectAuditContext(ctx)
                    engineCreated: (engine) => engine.provide(AUDIT_CONTEXT, log),
                    started: () => logger.info('audit ready'),
                    drained: () => logger.info('audit: every run drained'),
                },
            });
        },

        // onReady consumes: the engine exists but has not started, the server is not listening yet
        async onReady(container: IContainer) {
            // migrate builds config and store only: no ENGINE to resolve
            if (container.resolve(AppToken.CONTEXT).mode === 'migrate') {
                return;
            }

            const logger = container.resolve(AppToken.LOGGER);

            unsubscribe = container.resolve(AppToken.ENGINE).on('run.updated', ({ run }) => {
                logger.info('run updated', { run: run.id, status: run.status });
            });
        },

        // also called after an onReady that threw half-way
        async teardown() {
            unsubscribe?.();
        },
    };
}
  • Hooks (LIFECYCLE_HOOKS): engineCreated(engine) before engine.start() (the place for engine.provide(); a throwing hook, such as a second value for one key, is logged through context.report() and the app still starts), started() after engine.start() (channels started), before the server listens, stopping() first in the shutdown, before the drain stops the channels, drained() after the engine drained and before the store closes.
  • Failures: orkos never tears down a module whose setup threw, so such a setup closes what it opened before rethrowing. A module whose onReady threw is torn down, so teardown tolerates state that onReady never built.
  • Stopping: AppToken.CONTEXT holds the lifecycle's signal, aborted once stop() is called; throwIfStopped(context) before a long step keeps a stopped start from going on. context.report(error) logs an error and, during stop(), makes it reject.
  • Modes: AppToken.CONTEXT holds the mode: start builds everything, job (runJob) config, store and engine, migrate only config, store and the database modules. A module that resolves ENGINE in onReady returns early in migrate mode, as the sample does, or chamvi migrate fails.
  • Testing: createModuleHarness({ modules, env?, agents?, clock? }) from @chamvi/app/testing runs the real module lifecycle (setup, onReady, the start steps) of the modules you list, built-ins included, without start() and a port: harness.container resolves what a module contributed, harness.reported holds every context.report() call, harness.stop() tears down. Components run only when the harness lists componentsModule() (a module whose work is a component, such as knowledge indexing, does nothing without it). The feature packages test their own modules with it.
  • Dependencies: dependencies name modules the app registers ({ name, optional: true } for one it may lack). A missing one, a cycle or a version mismatch throws InvalidAgentDefinitionError from start, runJob and migrate before any module set up (the CLI exits 2).

Testing an app ​

start({ env }) takes the environment instead of process.env for the built-in modules, and models replaces a provider, so an app runs in a test without keys or network:

ts
const app = createApp({
    agents,
    // 'anthropic/claude-sonnet-5-5' resolves to the mock: no package, no key, no request
    models: { anthropic: customProvider({ languageModels: { 'claude-sonnet-5-5': model } }) },
});

// the env replaces process.env for the built-in modules
await app.start({
    env: {
        PORT: '3101',
        HOST: '127.0.0.1',
        TOKENS: JSON.stringify([{
            value: 'test-token-0123456789',
            id: 'test',
            permissions: '*',
        }]),
        LOG_LEVEL: 'error',
    },
});

try {
    const response = await fetch('http://127.0.0.1:3101/agents', { headers: { authorization: 'Bearer test-token-0123456789' } });

    return await response.json();
} finally {
    // drains the engine, closes the server and the store
    await app.stop();
}

The optional module factories read options.env ?? process.env when they are called, never start({ env }): configure them in a test through their own env option, for example githubModule({ env: { GITHUB_APP_ID: '1', ... } }).
