# Vercel Skills SDK reference

Source baseline: the npm package [`skills`](https://github.com/vercel-labs/skills) 1.8.1 (`vercel-labs/skills`, API reference `docs/api.md`, public types `dist/index.d.mts`). `@chamvi/skills` depends on `skills@^1.8.1`; nothing else in chamvi does. Import from `skills` only (its single entry point), never the CLI.

| Upstream function | Chamvi owner and use |
|---|---|
| `resolveSource(source, { ref, includeInternal, signal })` | `packages/skills/src/prepare/module.ts`: clone the pinned commit once and list its skills (`handle.skills`, each with `name`, `path`, optional `duplicates`); `handle.dispose()` removes the temporary clone in `finally`. |
| `installSkills(handle, { cwd, skills: [name], ... })` | `prepare/module.ts`: copy one selected skill into sibling staging, then inspect `installed`, `failed` and `skipped`. |
| (plain git, no SDK) | `prepare/tree.ts` `verifyPinnedTree()`: fetch the pinned commit without blobs into `<stage>/tree` and inspect its tree before any install (see Symlinks and gitlinks). |
| `isDiagnostic(error, ...codes)` | `prepare/helpers.ts` `toPreparationError()`: classify a thrown SDK diagnostic by its permanent `code`. |

## Options chamvi passes

- `ref: revision` and the check `handle.source.commit === revision`: a git source is cloned at the pin and the checked-out commit is verified without running git. A different `commit` is refused; an absent one (the SDK's own git call failed or timed out) is retryable. A HEAD that moved past the pin does not matter.
- No `fullDepth`: discovery reads upstream's standard locations (the repository root, `skills/` with `.curated`, `.experimental`, `.system`, the agent project skill folders and plugin paths) and the whole tree only when those hold nothing. A vendored copy declaring a selected name in a deep folder is then no duplicate; a skill that exists only deep in a source with standard-location skills is not found. `installSkills` given a handle reuses the handle's discovery, so it takes no discovery option. `includeInternal: true`: the operator selects names explicitly, so `metadata.internal` skills are selectable.
- Submodules: upstream runs `git submodule update --init --recursive --depth 1` after every clone, at the commits the superproject's gitlinks record; a failure prints one `console.warn` and the clone continues. Discovery treats their checkouts as ordinary folders, so chamvi refuses a gitlink at, inside or around a selected skill (see Symlinks and gitlinks).
- Subpaths: `owner/repo/sub/dir` narrows discovery to that folder (upstream's subpath); a `..` segment is refused by upstream (`SKILLS_UNSAFE_SUBPATH`, `SKILLS_SUBPATH_OUTSIDE_REPO`).
- GitHub lookup: for a `github` source, `resolveSource` makes an unauthenticated `GET https://api.github.com/repos/<owner>/<repo>` (privacy and the canonical repository name, which then becomes `handle.source.url`); its failure is ignored.
- Selection: each requested name must match exactly one `handle.skills` entry with no `duplicates` and a `path`; otherwise `invalid()`.
- Install: `agents: ['universal']` and `mode: 'copy'` (a plain `<stage>/.agents/skills/<name>` copy, no agent links), `lockfile: false`, `telemetry: false`, `duplicates: 'error'`, `symlinks: 'reject'`, one name per call. A `failed` entry is upstream's wrapper for a filesystem error while copying (ENOSPC, EIO, EACCES) and is retryable; otherwise the result is accepted only with `skipped` empty and exactly one `installed` entry whose path is `join(stage, '.agents', 'skills', name)` and a real directory.
- No `onWarning`: upstream then drops its warning diagnostics, whose `data.path` can hold temp paths.
- YAML warnings: upstream parses frontmatter with `yaml`'s default log level, so the parser's warnings reach `process.emitWarning` quoting the source text, as a `YAMLWarning` (an unresolved tag) or as an untyped string with one of yaml's own texts (yaml 2.9.1 has one: `Keys with collection values will be stringified due to JS Object restrictions: `); `onWarning` covers neither. `withoutYamlWarnings()` (`prepare/helpers.ts`) drops those two kinds while an SDK call runs, matching the strings by prefix; every other warning passes, untyped strings included; overlapping preparations share the filter and the last one restores `process.emitWarning`.
- `signal` goes to both calls.

## What chamvi adds

- **Local paths**: upstream refuses `ref` for a local path, so the adapter recognises a local path itself and passes `pathToFileURL(resolve(path)).href`, which upstream clones and pins like any git URL (working-tree edits excluded).
- **Pre-checks before any fetch**: a source starting with `-` is refused. For non-local sources also a `#` fragment, a `?` query (Azure `?version=`/`?path=`), `github.com/<owner>/<repo>/tree/<ref>` and GitLab `/-/tree/<ref>` paths (a GitHub Enterprise `/tree/` URL is not recognised, which is harmless since the `ref` option overrides an inline ref; the shorthand `owner/repo/tree/main` is read as the subpath `tree/main`; `https://gitlab.com/group/tree/repo.git` stays valid), an `@` in a source without `://` that is not scp-style `user@host:path` (`owner/repo@skill`, `owner/repo@v1`, `github:github:o/r@x`), and every `<transport>::` remote helper (`ext::`, `fd::`). After resolve, `handle.source.type` must be `git`, `github` or `gitlab`.
- **Cancellation**: upstream checks `signal` between steps but does not interrupt a running clone. The adapter awaits the SDK call to settlement and disposes the handle before rejecting with `signal.reason`; stop can therefore wait for a clone. A failure of an SDK or git call after the abort rejects with `signal.reason` too (`orAbortReason()`), never with a mapped error.
- **Pinned tree check** (`prepare/tree.ts`): after the pin matched and before any install, `git init --bare` plus `git fetch --depth 1 --filter=blob:none --no-tags --no-recurse-submodules` of `handle.source.url` at the pin (`-c protocol.ext.allow=never`, `GIT_TERMINAL_PROMPT=0`, 5 minute timeout), then `rev-parse --verify FETCH_HEAD^{commit}` (must equal the pin) and `ls-tree -r -z FETCH_HEAD` (30 s each; `ls-tree` output up to 64 MiB, a larger listing is configuration), all through bounded `execFile` joined on `close` with the caller's signal. The repository lives in the stage and goes with it. This fetch uses the host's plain git credentials only, none of the SDK's `gh`/SSH fallbacks, so a private source the SDK reaches only through `gh` fails here (retryable).

## Symlinks and gitlinks

Upstream's `symlinks: 'reject'` lstats only the selected skill's own files, while its discovery walks through committed directory links (`skills -> /host/dir`, `.claude -> ...`, relative `../..` links) and copies host files reached that way. Chamvi therefore refuses any tracked `120000` entry anywhere in the pinned tree. Submodule content is kept out of the corpus in two layers: a `160000` gitlink whose path equals, lies inside or contains a selected skill's `path` refuses the source, compared NFC-normalised and lower-cased (the SDK reports containers lexically as `skills`, `.claude/skills`, while a case-insensitive filesystem lets `Skills/` or `.Claude/` hold them; a case-sensitive host may over-refuse); and a staged skill folder holding an entry named `.git` at any depth is refused after its install and before `verify`. Submodules elsewhere are allowed.

## Error mapping

`toPreparationError()` never forwards an SDK or git message (they can hold credentials or private content):

- `InvalidAgentDefinitionError`: `SKILLS_GIT_AUTH_FAILED` (upstream also reports a missing repository this way), `SKILLS_GIT_SAML_SSO_BLOCKED`, `SKILLS_UNSUPPORTED_GIT_TRANSPORT`, `SKILLS_INVALID_OPTION_VALUE`, `SKILLS_LOCAL_PATH_NOT_FOUND`, `SKILLS_NO_VALID_SKILLS`, `SKILLS_NO_MATCHING_SKILLS`, `SKILLS_AMBIGUOUS_SKILL_SELECTOR`, `SKILLS_DUPLICATE_SKILL_NAME`, `SKILLS_SKILL_CONTAINS_SYMLINKS`, `SKILLS_UNSAFE_SUBPATH`, `SKILLS_SUBPATH_OUTSIDE_REPO`; a failing or flooding `rev-parse`/`ls-tree` on the fetched commit, a fetched commit other than the pin, a refused tree entry.
- `InvalidAgentDefinitionError` too: `SKILLS_GIT_CLONE_FAILED` whose raw git answer (`error.cause.message`, never the message, which embeds the URL) says the repository is missing (`does not appear to be a git repository`, `fatal: repository '...' not found`, `returned error: 404`): a missing `file://` or ssh path and a plain https 404 arrive this way, GitHub's "Repository not found" arrives as `SKILLS_GIT_AUTH_FAILED`.
- Retryable `skill_preparation_failed`: `SKILLS_GIT_CLONE_TIMEOUT`, any other `SKILLS_GIT_CLONE_FAILED` (also a missing ref, whose cause stays ambiguous), `SKILLS_SOURCE_FETCH_FAILED`, every unknown code (upstream adds codes in minor releases), every non-diagnostic, an absent `handle.source.commit`, a `failed` install entry, the tree fetch failing or timing out and a metadata command killed by a signal or its timeout.

Upstream's clone falls back to the host's `gh` login and SSH agent/keys after an HTTPS GitHub authentication failure, and honours `SKILLS_CLONE_TIMEOUT_MS`; the public skills reference documents both for operators.

## Ownership

The optional package owns the dependency and the adapter. Its public options/results are chamvi-owned shapes, with no upstream SDK type aliases or re-exports. Application consumers configure sources, independent reviewed pins and role selection through chamvi; they do not import the SDK. No SDK dependency belongs in `@chamvi/app` or core. Preparation preserves the reviewed selected bytes, verifies independent bundle pins before replacing assets and cleans staging on failure. Never approve a newly computed digest during application startup. Importing or loading skills must not invoke the CLI, change process cwd, prompt or execute skill scripts.

Filesystem ownership is `packages/skills/src/bundle/`: `bundle.ts` (`hashSkillBundle`, `readSkillBundle`) verifies complete local inventories and exact framed byte hashes; `helpers.ts` validates strict root metadata; `module.ts` (`loadSkillBundles`) creates immutable catalogs; `packages/skills/src/catalog/` owns domain types, catalog rendering and the ordinary load tool; `runtime/` owns validation, custom adapters and per-engine caches/fingerprints. Core owns only the generic preparation/contribution protocol and lifecycle coordination. Supporting `.yaml`/`.yml` files are opaque UTF-8 references, including `agents/openai.yaml`. Only surrounding description whitespace is trimmed before nonblank/length/control checks. Body/reference bytes and hash framing are unchanged.

The selected `tada5hi/skills` profile at `233532ce04af00916c026f97a3f6097ee7f189df` is the compatibility profile: common `ponytail`, `codebase-design`; maintainer `generate-commit-message`, `investigate-pr-comments`, `create-pull-request`, `release-please-version-bump`. It does not establish compatibility for unselected scripts, SVG/CSS, hidden templates or binary assets.
