# Store and Database

Read before changing a repository contract, the memory store or `@chamvi/store-db` (entities, migrations, conversations on Postgres).

The contract itself (the `IStore` capabilities, the rules every implementation keeps, `findOne`/`find`/`OrFail`) is in architecture.md → *Repository Contract*.

`createDatabaseStore()` (`@chamvi/store-db`) assembles separate `Database*Repository` classes on one PostgreSQL DataSource, including conversations. Every method goes through the entities' repositories and query builders; the only hand-written SQL fragments are the `jsonb_exists` key check in `findDocuments` (TypeORM has no key-existence operator) and conversation recall's `octet_length` byte bound, containment uses `JsonContains`; `repository/helpers.ts` maps entities to `Run`, `Step` and `Checkpoint` (a `RETURNING` row is hydrated through the entity metadata). The listed run, artifact, idempotency, lock and checkpoint atomic operations each use one statement: `insert().orIgnore()` returning `id` (`runs.insert`, `artifacts.insert`), `insert().orUpdate()` with the overwrite condition `run_id =` returning the metadata (`artifacts.save`, no row means another run's id), `insert().orUpdate()` with the overwrite condition `expires_at <= now` returning a row (`idempotency.claim`, `locks.acquire`), a conditional `update()` (`claim`, `renewClaim`, the `update` guards, the latter returning `*`) and `insert().orUpdate()` with the overwrite condition `step_index <=` (`save`). Conversation operations instead use transactions and a `FOR NO KEY UPDATE` lock on the conversation row (never deleted, key never changed, so child-row foreign key `KEY SHARE` locks do not conflict) to serialize ownership and journal changes; a reset with `keepNotes` drops expired notes in both stores. Time comes from the `IClock` as a parameter, never the database's `now()`. Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt`, `waiting.notifiedAt` and `taint.at` are revived as `Date`. Only the latest checkpoint is kept. Artifacts live in `chamvi_artifacts` (`ArtifactEntity`: `id` varchar(128) PK, `run_id` indexed, `agent`, `media_type`, `filename` nullable, `size` int, `data` `bytea` with `select: false`, `created_at` timestamptz; migration `1792368000000-artifacts.ts`); `chamvi_idempotency_keys.scope` is varchar(1024) (migration `1792454400000-idempotency-scope.ts`, a hand-written `ALTER COLUMN ... TYPE`, since TypeORM's generated length change drops and re-adds the column); `chamvi_kv.key` is `COLLATE "C"` (migration `1792540800000-kv-key-collation.ts`, `KvKeyCollation1792540800000`, hand-written the same way), so `find` orders by code point; markers live in `chamvi_agent_revisions` (`AgentRevisionEntity`: `agent` varchar(64) `COLLATE "C"` PK, `hash` varchar(128), `changed_at` timestamptz; migration `1792627200000-agent-revisions.ts`, `AgentRevisions1792627200000`), `save` a repository `upsert` on `agent` (no compare needed: the engine holds `agents:<name>`), `find` ordered by `agent`; `findOne`/`find` never load `data`, `read` returns a plain `Uint8Array`. `migrateStore(dataSource)` runs the migrations under the advisory lock `chamvi:migrations`; `pendingMigrations(dataSource)` names the migrations not run yet through `MigrationExecutor.getPendingMigrations()` (read-only: it never creates the migrations table); `store.idempotency.purgeExpired(now?)` and `store.locks.purgeExpired(now?)` each delete expired rows and return a count; the app schedules both. Documented divergences from `createMemoryStore()`: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, `save(key, undefined)` reads `{ result: null }`, `upsertDocument(..., undefined)` reads `doc: null`, `findDocuments` `where` is `jsonb` containment and orders by `id`, `find` ties use `COLLATE "C"`.

Migration `1792713600000-conversations-run-taint.ts` (`ConversationsRunTaint1792713600000`, a new class name so a development database that recorded the pre-bundle `Conversations1792713600000` fails loudly instead of skipping the taint column) adds the checkpoint/step run foreign keys as PostgreSQL `NOT VALID`: older store methods allowed missing-run IDs, so existing orphan rows are preserved without fabricated runs while new inserts and changes to run references are checked. Other new foreign keys are validated normally. TypeORM does not model the validation flag; both fresh and legacy-upgraded schemas must still pass `assertSchemaMatchesMetadata` with the ordinary relation metadata. Do not automatically validate those two constraints while legacy orphans may remain; docs `repositories/database.md` gives the operator's orphan query and `VALIDATE CONSTRAINT` statements.


## Module map (`packages/store-db/src`)

| Path | Purpose |
|------|---------|
| `entities/` | One TypeORM entity per table, the repositories the store queries through; `TableName` and the jsonb transformers (`JSON_VALUE_TRANSFORMER`, `OPTIONAL_JSON_TRANSFORMER`) in `constants.ts`, `toJsonParameter()` (jsonb sanitizing) in `asserts.ts` |
| `migrations/` | `1792195200000-init.ts` (`Init1792195200000`), `1792368000000-artifacts.ts` (table `chamvi_artifacts`), generated from the entities; `1792454400000-idempotency-scope.ts` (`scope` varchar(1024), hand-written), `1792540800000-kv-key-collation.ts` (`chamvi_kv.key` `COLLATE "C"`, hand-written), `1792627200000-agent-revisions.ts` (`AgentRevisions1792627200000`, table `chamvi_agent_revisions`); `1792713600000-conversations-run-taint.ts` (`ConversationsRunTaint1792713600000`, the 0.4 bundle: four conversation-owned tables, scalar run/checkpoint bindings, eleven constraints generated from standard TypeORM relationships, including checkpoint/step run ownership, indexes on the five new foreign key columns (`chamvi_runs`/`chamvi_checkpoints.conversation_scope_id`, `chamvi_conversation_items`/`notes`/`operations.run_id`), then nullable `chamvi_runs.taint` JSONB and the unfinished-run backfill) |
| `conversation/` | `DatabaseConversationRepository` on the run DataSource, transaction-bound repository getters, shared core persistence policy and local options; identity-row locking, generation fences, journal and note-operation transactions, bounded operation-prune pages |
| `schema/` | `migrateStore()`, `pendingMigrations()` (`module.ts`), `STORE_ENTITIES`, `STORE_MIGRATIONS`, `MIGRATION_LOCK_NAME` |
| `repository/` | `createDatabaseStore()` (`module.ts`), entity to domain mapping, value builders and `RETURNING` row hydration (`helpers.ts`), `DatabaseStoreOptions`, `DatabaseStore` |
| `run/`, `step/`, `checkpoint/`, `idempotency/`, `lock/`, `effect/`, `state/`, `artifact/`, `agent-revision/` | Separate `Database*Repository` capability classes; idempotency and lock repositories each own numeric `purgeExpired()` |
