# Store and Database

Read before changing a repository contract, the memory store or `@chamvi/store-db` (entities, migrations, conversations on Postgres).

The contract itself (the `IStore` capabilities, the rules every implementation keeps, `findOne`/`find`/`OrFail`) is in architecture.md → *Repository Contract*.

`createDatabaseStore()` (`@chamvi/store-db`) assembles separate `Database*Repository` classes on one PostgreSQL DataSource, including conversations. Every method goes through the entities' repositories and query builders; the only hand-written SQL fragments are the `jsonb_exists` key check in `findDocuments` (TypeORM has no key-existence operator) conversation recall's `octet_length` byte bound and `update`'s `expectWaitId` condition `COALESCE(waiting->>'id', waiting->>'approvalId') = :waitId` (no `->>` in the ORM), containment uses `JsonContains`; `repository/helpers.ts` maps entities to `Run`, `Step` and `Checkpoint` (a `RETURNING` row is hydrated through the entity metadata). The listed run, artifact, idempotency, lock and checkpoint atomic operations each use one statement: `insert().orIgnore()` returning `id` (`runs.insert`, `artifacts.insert`), `insert().orUpdate()` with the overwrite condition `run_id =` returning the metadata (`artifacts.save`, no row means another run's id), `insert().orUpdate()` with the overwrite condition `expires_at <= now` returning a row (`idempotency.claim`, `locks.acquire`), a conditional `update()` (`claim`, `renewClaim`, the `update` guards, the latter returning `*`) and `insert().orUpdate()` with the overwrite condition `step_index <=` (`save`). Conversation operations instead use transactions and a `FOR NO KEY UPDATE` lock on the conversation row (never deleted, key never changed, so child-row foreign key `KEY SHARE` locks do not conflict) to serialize ownership and journal changes; a reset with `keepNotes` drops expired notes in both stores. Time comes from the `IClock` as a parameter, never the database's `now()`. Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt`, `waiting.notifiedAt` and `taint.at` are revived as `Date`. Only the latest checkpoint is kept. Artifacts live in `chamvi_artifacts` (`ArtifactEntity`: `id` UUID primary key, `run_id` indexed, `agent`, `media_type`, `filename` nullable, `size` int, `data` `bytea` with `select: false`, `created_at` timestamptz); `chamvi_idempotency_keys.scope` is varchar(1024); `chamvi_kv.key` is `COLLATE "C"`, so `find` orders by code point; markers live in `chamvi_agent_revisions` (`AgentRevisionEntity`: `id` UUID v7 PK, `agent` varchar(64) `COLLATE "C"` unique, `hash` varchar(128), `changed_at` timestamptz), `save` a repository `upsert` on `agent` (no compare needed: the engine holds `agents:<name>`), `find` ordered by `agent`; `findOne`/`find` never load `data`, `read` returns a plain `Uint8Array`. `migrateStore(dataSource)` runs the migrations under the advisory lock `chamvi:migrations`; `pendingMigrations(dataSource)` names the migrations not run yet through `MigrationExecutor.getPendingMigrations()` (read-only: it never creates the migrations table); `store.idempotency.purgeExpired(now?)` and `store.locks.purgeExpired(now?)` each delete expired rows and return a count; the app schedules both. Documented divergences from `createMemoryStore()`: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, `save(key, undefined)` reads `{ result: null }`, `upsertDocument(..., undefined)` reads `doc: null`, `findDocuments` `where` is `jsonb` containment and orders by `document_id`, `find` ties use `COLLATE "C"`.

Migration `1792713600000-conversations-run-taint.ts` (`ConversationsRunTaint1792713600000`, a new class name so a development database that recorded the pre-bundle `Conversations1792713600000` fails loudly instead of skipping the taint column) adds the checkpoint/step run foreign keys as PostgreSQL `NOT VALID`: older store methods allowed missing-run IDs, so existing orphan rows are preserved without fabricated runs while new inserts and changes to run references are checked. Other new foreign keys are validated normally. TypeORM does not model the validation flag; both fresh and legacy-upgraded schemas must still pass `assertSchemaMatchesMetadata` with the ordinary relation metadata. Do not automatically validate those two constraints while legacy orphans may remain; docs `repositories/database.md` gives the operator's orphan query and `VALIDATE CONSTRAINT` statements.

Run references (`steps.insert`, `checkpoints.save`, `conversations.beginTurn`, and `runs.insert` of a child) map a foreign key violation (code `23503`) whose constraint is one of the runs table's foreign keys from the entity metadata (`runForeignKeyNames()`, the self foreign key included) to `RunNotFoundError` through `withRunReference()` (`repository/helpers.ts`), never the translated detail text. `runs.insert` of a run with `trigger.parent` goes through it because `orIgnore()` does not suppress a foreign key violation.

Migration `1792800000000-run-lineage.ts` (`RunLineage1792800000000`, #129) adds `chamvi_runs.parent_run_id` (varchar(128) `COLLATE "C"`, indexed, a self `@ManyToOne` with the scalar `parentRunId`) and `subtree_usage` jsonb, backfills `parent_run_id` from `trigger->'parent'->>'runId'`, rewrites a stored `parent.kind` `handoff` to `dispatch` with `role: 'handoff'`, and backfills `waiting.id` from `waiting.approvalId` (the `expectWaitId` guard also falls back to `approvalId`). The self foreign key is `NOT VALID`, like the 0.4 bundle's, so legacy children whose parent row is gone survive; `down()` reverses each step. `find({ ids })` uses `In(...)`; `toRun` revives both wait point kinds and normalizes a missing approval `id`.

The generated baseline `1793923200000-init.ts` requires an empty database. Every table has one UUID `id` primary key, except existing bigint `seq` keys. Public run, artifact and scope IDs are the primary keys; documents and operation receipts have separate caller-defined `document_id` and `operation_id` business keys. Supply `uuidv7()` on inserts; UUID primary columns have no SQL default and use `update: false` so upserts retain their row identity. Identifier timestamps are independent of the repository clock. Conversations have a unique canonical `identity_key`. Malformed UUID lookups return absent results, matching memory, rather than database parsing errors (PR #170). All foreign keys are validated. `chamvi_connections.name` is unique, and entries have a unique `(connection_name, key)` index and a connection-name FK `ON DELETE CASCADE`. Entries are sealed bytes; the repository never sees plaintext or keys. `writeEntries` is one transaction: an `update()` of `updated_at` (existence plus a row lock serializing batches and `delete`), then the fence's lock row read `FOR SHARE` (`pessimistic_read`, owner), so an `acquire` taking the lease over, a `renew` or a `release` waits for the commit; then `expires_at > now` against a clock reading taken after both row locks are held (a reading before the waits would pass a lease that expired meanwhile, PR #165); no row or an expired one is `LeaseLostError` and a rollback. `replace` (the vault's recreate) is the same fenced transaction (connection row `FOR UPDATE`, then the fence, then delete and insert): an unfenced `delete` before the lease check would let an opener whose lease lapsed cascade away the next holder's entries (PR #165). A fence check outside the write's transaction (or a plain read without the row lock) would let a takeover slip between check and write. Memory checks the fence through the store's own `MemoryLockRepository.holds()` in the same tick, so a `MemoryConnectionRepository` needs the lock repository of its store. `locks.renew` is a transaction: the lease row `FOR UPDATE` (`pessimistic_write`, owner), then the clock, then `expires_at > now` and the update, for the same reason.

## Module map (`packages/store-db/src`)

| Path | Purpose |
|------|---------|
| `entities/` | One TypeORM entity per table, the repositories the store queries through; `TableName` and the jsonb transformers (`JSON_VALUE_TRANSFORMER`, `OPTIONAL_JSON_TRANSFORMER`) in `constants.ts`, `toJsonParameter()` (jsonb sanitizing) in `asserts.ts` |
| `migrations/` | `1793923200000-init.ts` (`Init1793923200000`), generated from entity metadata for an empty database |
| `conversation/` | `DatabaseConversationRepository` on the run DataSource, transaction-bound repository getters, shared core persistence policy and local options; identity-row locking, generation fences, journal and note-operation transactions, bounded operation-prune pages |
| `schema/` | `migrateStore()`, `pendingMigrations()` (`module.ts`), `STORE_ENTITIES`, `STORE_MIGRATIONS`, `MIGRATION_LOCK_NAME` |
| `repository/` | `createDatabaseStore()` (`module.ts`), entity to domain mapping, value builders and `RETURNING` row hydration (`helpers.ts`), `DatabaseStoreOptions`, `DatabaseStore` |
| `run/`, `step/`, `checkpoint/`, `idempotency/`, `lock/`, `effect/`, `state/`, `artifact/`, `agent-revision/`, `connection/` | Separate `Database*Repository` capability classes; idempotency and lock repositories each own numeric `purgeExpired()` |
