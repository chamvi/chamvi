# Store and Database

Read before changing a port of `@chamvi/store`, how a service of `@chamvi/core` uses its repository, the memory repositories (`@chamvi/store-memory`), `@chamvi/store-db` (entities, migrations, the adapter base) or an app's database module.

The layering rules (a repository decides nothing, the service transaction shape, no record of all repositories) are in architecture.md → *Repository Contract*; #231 holds the design.

## Ports (`@chamvi/store`)

- `IEntityRepository<T>`: `findMany(query)` (rapiq, `{ data, meta: { total, limit?, offset? } }`), `findOneById`, `findOneBy`, `findManyBy` (`EntityWhere<T>`: a value, `null` or an array of values per field; at most one unbounded array per where, the adapter splits it), `create`, `merge`, `save`, `upsert`, `upsertMany` (one transaction, chunked by the driver, a later entity of a key wins, results in input order equal to the next reads), `remove`, `removeMany`, `removeManyBy` (one statement, resolves the count, never an empty where), `validateRelations`, `checkUniqueness`, `transaction(fn)`. Write multi-row child changes with `upsertMany`/`removeManyBy` inside the root's transaction after the root's locked read; never loop single writes over unbounded children, never `removeMany(await findManyBy(...))`.
- `save` decides by object identity: an object from `create()` is inserted, one from a read is updated with the columns changed since the read (a snapshot per object); a spread copy of a created entity counts as an update. A row read with a field selection is refused by `upsert`/`upsertMany` (`EntityQueryError`), since it would clear the other columns.
- The finders that stay: `IRunRepository.findByWaitKind`, `IStateDocumentRepository.findContaining`, `IArtifactRepository.readData`, `ILockRepository`/`IIdempotencyRepository` `removeExpiredBy(time)`, `IConnectionRepository.findFence(lock)`. Children bound to the root's transaction: connection `entries`, `secrets`; conversation `items`, `notes`, `operations`. A new finder goes through the bases' `findManyWhere` hook, decides nothing and is asserted with paging and total on both drivers.
- An order the storage owns is a constant beside the port (`STEP_STORED_ORDER`, `CONVERSATION_ITEM_STORED_ORDER`), never a hidden key named in a service.
- Six storage errors (ebec `BaseError`, fixed message, entity label only): `EntityNotFoundError` (`entity_not_found`), `EntityConflictError` (`entity_conflict`), `EntityRelationError` (`entity_relation_invalid`, `relation` names the referenced label), `EntityDeadlockError` (`entity_deadlock`: PostgreSQL 40P01, a memory lock cycle), `EntityQueryError` (`entity_query_invalid`: a where with an `undefined` value, `findOneById(undefined)`, `removeManyBy({})`, an upsert of a field-selected row, an operation a port does not offer such as a step upsert), `EntityInvalidError` (`entity_invalid`, not retryable: a value the table refuses, PostgreSQL class 22, 23502, 23514, 23000, SQLite NOT NULL, CHECK, datatype, too big; `operation` and the driver's column or constraint name in `field`).
- rapiq on both bases: `caseSensitive: true`; strings sort by code point; the database base renames public field paths to entity properties (`fields`); a non-uuid filter value on a uuid column matches nothing; a filter value on a date field is compared as the instant it names (memory: the fields in `dates`), one naming no instant is `EntityQueryError` (an `ne` stand-in would match every row).
- `@chamvi/store` imports nothing from `typeorm` and takes no name from its API; `packages/store/test/unit/exports.spec.ts` greps its sources for `typeorm`, `JoinColumn`, `EntityManager`, `QueryBuilder`. Runtime dependencies: access, `@rapiq/core`; `ai` an optional type-only peer. `normalizeEnvelope`/`normalizeWaitPoint` read legacy stored shapes back.

## Services (`@chamvi/core`)

One folder per aggregate (`<aggregate>/service.ts`, its context type in `types.ts`), each taking its port (and its clock where it compares time). Consumers narrow with `Pick<XService, ...>`, so fakes stay possible. Reads drop properties set to `undefined`; a change returns what `save`/`upsert` returned, through the read mapping.

| Service | Rules |
|---------|-------|
| `RunService` | `create` insert-if-absent (`false` for a taken id), `parentRunId` from `trigger.parent`, a missing parent `RunNotFoundError`; `update` guards `expectStatus`/`expectOwner`/`expectWaitId` (`InvalidRunStateError`); `find` (`ids`, `parentRunId(s)`, `hasParent`, `waitKind`, createdAt then id, `order: 'desc'`); `list(query)` splits the wait kind off to `findByWaitKind` and ties sorts by `id`; `claim`/`renewClaim` leases. Run row lock `FOR NO KEY UPDATE` |
| `StepService`, `CheckpointService` | Append-only steps; the highest `stepIndex` wins, an equal one replaces (locked read, one retry on `EntityConflictError`). A missing run (`EntityRelationError` `run`) is `RunNotFoundError` |
| `EffectService`, `StateService`, `AgentRevisionService` | `upsert` by the natural key keeping the stored id (`upsertKey`); `save(key, undefined)` and `upsertDocument(..., undefined)` store `null`; `set(..., undefined)` removes a KV key; `findDocuments` top-level deep equality, document id in code-point order; `list`/`listDocuments` take a rapiq query. Markers: `delete` of a missing one is a no-op, `find` in agent code-point order |
| `ArtifactService` | `create` insert-if-absent by id and `(runId, key)`; keyed `save` keeps `id`, `agent`, `createdAt` (locked read of the key's row, one retry); `read` through `readData`, a plain `Uint8Array` |
| `LockService`, `IdempotencyService` | One plain read first: a held lease or an unexpired key is refused on it. A free key is inserted in a transaction of its own; a conflict, or an expired row, goes to a locked takeover in a new transaction (clock after the lock). `renew`/`release` lock the row. `purgeExpired(now?)` through `removeExpiredBy`, a count, on memory too; the app schedules both |
| `ConnectionService` | The fence and the config reads, see [connections.md](connections.md) |
| `ConversationService` | Every rule of conversations, see [conversations.md](conversations.md) |

Rule cases whose outcome depends on the driver (large batches, ordering, byte sizes, bind limits, concurrency) run on PostgreSQL too, in store-db's `test/unit/repositories/<aggregate>/service.spec.ts`.

## Memory repositories (`@chamvi/store-memory`)

`MemoryRegistry` holds the rows, the row locks and the declared references of every repository of a process; build all of them on one registry. `MemoryEntityRepository<T>({ entity, registry, key, unique?, references?, upsertKey?, dates? })` copies in and out (`structuredClone`); inside `transaction(fn)` every single-row read locks the row until the end (a cycle is `EntityDeadlockError`), so memory serializes like the database. References (also nested paths, `conversation.scope.id`) are enforced both ways, as foreign keys: a missing referenced row and removing a referenced row are `EntityRelationError`; remove children before their parent (the database cascades, memory refuses). Children are built in the root's constructor and rebound in `bind()` (`bindChild`); a child used after its transaction ended is refused. `dates` must be listed by hand to match a database date column. `runs.has(id)` is a synchronous presence check. The connection fence reads the `lock` rows of the same registry. The memory port suites run in `packages/test-kit/test/unit/`, never from store-memory.

## Database repositories (`@chamvi/store-db`)

`EntityRepositoryAdapter<T, E>(repository, { entity, alias, target, lock?, toEntity?, fromEntity?, fields?, related?, upsertKey? })` implements the port on TypeORM; a subclass adds `withManager(manager)` (a transaction binds it, `bindTo()`, children through `bindChild`). Lock modes: `no-key-update` for runs and conversations (it does not block the `KEY SHARE` locks of referencing inserts), `share` for the fence read, `update` otherwise; SQLite takes none. Every statement stays below the driver's bind limit (65 535 PostgreSQL, 32 766 better-sqlite3): `upsertMany` one `INSERT ... ON CONFLICT` per chunk, long arrays split, several statements of one call outside a transaction run in one of their own. `upsert` writes every non-key column and an explicit NULL for an omitted one: a repository whose entity has a database default, generated or identity column supplies it in `toEntity` (or drops it in `fromEntity`, as steps do), so the returned value equals the next read (asserted on both drivers). chamvi's migrations name their constraints; the base maps a violated constraint to an entity label through `related`, so every database repository maps each foreign key of its tables and its contract spec asserts the `relation` label. `applyQuery` is the only path from a rapiq query to TypeORM (`@rapiq/adapter-typeorm` through `import()`). Hand-written SQL fragments only where the ORM has no operator: `jsonb_exists` and `doc -> key = value` in `findContaining`, `waiting->>'kind'` in `findByWaitKind`.

Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt`, `waiting.notifiedAt` and `taint.at` are revived as `Date`. Every table has one `id` primary key: uuid v7 (`uuidv7`), bigint increment on `chamvi_steps` and `chamvi_conversation_items` (append-only; `id` stays a string at the boundaries). The natural identity of a row is a unique key: keyed artifacts `(run_id, key)`, checkpoints `run_id`, idempotency keys `(scope, key)`, locks and effects `key`, kv `(agent, key)`, docs `(agent, collection, document_id)`, agent revisions `agent`, connections `name`, connection entries and secrets `(connection_id, key|name)` (FK `ON DELETE CASCADE`), conversations `key` (the identity's sha256), items and notes `(scope_id, generation, key)`, operations `(scope_id, generation, operation_id)`; an upsert's conflict target is that key and `id` is never overwritten. Every text column of these unique keys and every sorted text column is `COLLATE "C"`, so byte order holds whatever the database locale; the alpine test image sorts bytewise anyway, so a missing one shows only in `migrate.spec.ts`. Artifacts (`chamvi_artifacts`): private nullable `key` (`select: false`), `run_id` indexed with no foreign key (attachments are stored before the run), `data` `bytea` with `select: false`, read only by `readData`. Conversation items carry `bytes` (the UTF-8 length the service stamps); the recall pages `id, bytes`. Divergences from memory: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, identifier length limits.

Errors: `LegacySchemaError` (`store_legacy_schema`, an ebec `BaseError`; store-db has no core peer), `DatabaseUnavailableError` (`database_unavailable`: the operation and the driver's code only, never the URL, parameters or rows; `maskDatabaseUrl` masks up to the URL's last `@`), `DatabaseOptionsError`, `DatabaseDriverMissingError`, `DatabaseBusyError` (`holder`: a transaction or an operation).

SQLite (an app's database only): every use of a better-sqlite3 data source (transactions, plain statements, `synchronize`, `close`) goes through one in-process queue (`queueDataSource`); work inside a transaction joins through its manager, never the queue (rejected: plain `dataSource.transaction` overlap, which better-sqlite3 breaks). Work waiting `waitTimeoutMs` (30 s) behind one holder is `DatabaseBusyError`; a close behind a never-ended transaction closes at that deadline.

## Migrations

`migrateStore(dataSource)` runs the store's migrations under the advisory lock `chamvi:migrations` into TypeORM's `migrations` table and resolves the names it ran; `pendingMigrations(dataSource)` is read-only (it never creates the table). The baseline `1794096000000-uuid-baseline.ts` (`UuidBaseline1794096000000`) creates the schema; later: `ConnectionsRevisionsItemBytes1794230765000` (the 0.9 bundle: connection settings and secrets, `chamvi_runs.agent_revision`, and `chamvi_conversation_items.bytes`, added nullable, filled with `octet_length(text)` (`convert_to` on a non-UTF8 server) and set `NOT NULL` in one transaction: the precedent for a data backfill). `assertStoreNotLegacy()` (`schema/legacy.ts`) refuses a database that records a migration before the baseline or holds a `chamvi_*` table without it: `migrateStore` calls it first, and `chamvi start --check` regardless of `CHAMVI_MIGRATE` (exit 1); temporary, removed in the version after the baseline.

**Generate every schema migration, never write its SQL by hand.** Run `CHAMVI_MIGRATION_DATABASE_URL=<throwaway database> npx chamvi migration generate --database store --name <Name>` in the repository: it writes `packages/store-db/src/migrations/<timestamp>-<kebab-name>.ts`; add the class to `migrations/index.ts` and `STORE_MIGRATIONS`. `chamvi migration drift --database store` on a migrated database must exit 0, and `a follow-up generated migration is empty` in `migrate.spec.ts` must stay green. Index, constraint and key names come from TypeORM's naming strategy: a guessed name or reordered statement makes the next generated migration drop and recreate it. Allowed edits: the copyright header, formatting, removing the `"public".` qualifier generated on `DROP INDEX` (it breaks `down()` in a custom schema), and data backfills.

## An app's database

- `databaseModule(options)` (`@chamvi/app`, `modules/database/`): name `chamvi:db:<name>` (default `default`; `store` is reserved for `chamvi migration --database store`; rejected: letting an app database shadow it), depends on config and store. It reaches store-db, TypeORM and the drivers only through `import()`, so an app without one loads none. PostgreSQL on `DATABASE_URL` (read as chamvi's config reads it, no second variable), its own migrations table (a plain lower-case identifier, never `migrations`, not `chamvi_*`/`typeorm_metadata*` except the names in `CHAMVI_OWNED_MIGRATIONS_TABLES`/`OWNED_MIGRATIONS_TABLES` (store-db, app; a spec pins both), which chamvi's own database modules take, unique per module) under the lock `chamvi:db:<name>`; else SQLite in memory, synchronized, refused with `NODE_ENV=production` and in migrate mode. `postgres: true` refuses the SQLite fallback (`InvalidAgentDefinitionError` without `DATABASE_URL`); `installExtensions` is TypeORM's (default on), `false` for a database whose migration or operator creates the extensions.
- Modes mirror the store module: start and job migrate with `CHAMVI_MIGRATE` (else pending is `store_not_migrated`); `migrate` after the store; a check writes nothing and fails on pending migrations only with migrate off. After connecting and before migrating or serving, the setup refuses a column whose type came out `Object` (`findUntypedColumns`) and checks `schemas` (`validateEntitySchemas`, also in a check).
- The data source closes in a `drained` hook registered in `onReady` (rejected: in `setup`, it would close before the drained hooks of the modules using it; a module that uses it in `drained` registers its hook in `setup`); `teardown` closes it when no engine drained. The descriptor sits under `Symbol.for('chamvi.database.descriptor')` on the module object, read by `readDatabaseDescriptors(app)` from `App[APP_MODULES]` without a lifecycle. The data source token hands out a raw TypeORM data source: on SQLite, direct use outside `EntityRepositoryAdapter` bypasses the queue.
- `chamvi migration <generate|run|revert|status|drift> [--database] [--name] [--entry]` (`commands/migration.ts`, store-db's `runMigrationOperation`): loads the entry (generate the source, the others the built one), reads the descriptors, never calls a lifecycle method; `--database store` loads no entry. `generate` works only on `CHAMVI_MIGRATION_DATABASE_URL` (development only, never a chart value: it creates and drops that database; `isSameDatabase` refuses the `DATABASE_URL` database in any spelling, the scratch database is marked by a comment and re-checked before every drop); `run` takes the same lock as a start's migrate; `status` waits under it. Refusals exit 2 through `cli_usage`, drift and pending exit 1.
- `@chamvi/store-db-vector` (the knowledge tables, see [knowledge.md](knowledge.md)) is a `DatabaseModule` subclass named `chamvi:knowledge-repository` on the database `vector`: its own chain in `chamvi_vector_migrations` under `chamvi:db:vector` (no common lock with `chamvi:migrations`: the chains share no table), `postgres: true`, `installExtensions: false`. Its generated first migration starts with the one allowed hand edit, `CREATE EXTENSION IF NOT EXISTS vector`, and `down()` never drops it; generate and drift with `--database vector`. store-db's chain never needs `vector` (CI runs `postgres:18-alpine`); the vector suites run on `pgvector/pgvector:pg18`.
- `createTestDataSource({ entities, url? })` (`@chamvi/test-kit`) loads store-db by a variable specifier resolved from the app (structural types, no dependency field); under pnpm's strict layout it cannot see the app's packages, as `@chamvi/sandbox/module` cannot.

## Testing

- Port suites (`describe<Port>RepositoryContract`, `@chamvi/test-kit`) take `{ name, create, untilBlocked? }`; `untilBlocked()` resolves once a statement waits for a row lock (memory: a few microtasks; PostgreSQL: `untilLockWait(dataSource, count)` in store-db's `test/utils/database.ts`, no timers). Race cases are deterministic: a spec-local repository subclass holds each transaction's read at a one-shot barrier (`test/utils/barrier.ts`).
- store-db creates a database per spec file (`createTestDataSource()` in `test/utils/database.ts`, `TimeZone=America/New_York` sessions, fsync off) and runs at most four spec files at once: more pile their `CREATE DATABASE` statements up. Load-sensitive under machine load: `prune-pool.spec`, the migration specs.
- `@chamvi/app` compiles `test/fixtures/database/**` with decorator metadata (a second swc plugin in `test/vitest.config.ts`); `test/unit/app/lazy.spec.ts` runs `test/fixtures/lazy/{memory,database}.mjs` with the packages in `LAZY_FORBID` throwing on load, proving an app without a database module loads no TypeORM, driver or typeorm-extension.
