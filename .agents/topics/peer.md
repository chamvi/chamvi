# Peer

Read before changing `@chamvi/peer` (resolver, transport, `peerModule()`) or the peer routes of `@chamvi/http`. The engine side (stand-ins, polling, wake, peer intake) is in [agents.md](agents.md) (Remote agents) and [channels.md](channels.md) (Peer intake).

`@chamvi/peer` builds core's `IPeerResolver` from options (`createPeerResolver({ peers, clock, fetch?, approvalUrl? })`); it depends on `@chamvi/http-kit` and `smob`, peers on core, and only `/module` imports the optional peer `@chamvi/app`.

- **Untrusted** (`peers.<name>.untrusted`): taints both ways, every result at the caller (`peer:<peer>/<remoteRunId>`) and every run the peer starts at the receiver (`peer:<peer>` at creation, also without the caller's `taint`).
- **Recognition** (`recognize(invoker)`): the peer name comes only from the credential, never from a request: a static token principal (`kind: 'token'`, its `id` = `incoming.token`) or an authup client (`kind: 'authup'` and `identity.type === 'client'`, `identity.id` = `incoming.authupClient`; another issuer's client never matches). Two peers with one incoming credential are `InvalidAgentDefinitionError`. Rejected: a principal kind `peer`; a peer token is an ordinary `CHAMVI_TOKENS` entry, so the existing grant check applies unchanged.
- **Transport** (`transport/module.ts`, an http-kit `Client` over its own `dispatch`): every request goes to the peer's origin only (another origin is refused) with `redirect: 'manual'` (a redirect is an error), so the bearer never reaches another host; every error message goes through `redact()` with the credential's secrets. It honours the caller's signal only: the engine owns the deadline (`PEER_REQUEST_TIMEOUT_MS`), the transport adds no timer.
- **Permanent or retryable**: 400, 401, 403, 404, 415, 413 without `Retry-After` (an oversized start never shrinks), 409 (except the codes `entity_conflict`, `entity_deadlock`, `agent_replaced`, `invalid_run_state`, which the receiver answers for passing races), any redirect, and an authup token endpoint 4xx (not 429), redirect or answer without `access_token` are a permanent `ValidationError`; 429, a 413 with `Retry-After`, 5xx and network failures (also while reading the token answer) a retryable `PeerRequestError` (`peer_request`, `retryAfterMs` from the `Retry-After` of a 429 or 503). Rejected: retrying 401, 403 or a redirect (a misconfiguration would resend starts until the stand-in's 24 h deadline). The transport's own errors (redirect, origin) are recognized by instance (`TRANSPORT_ERRORS`, a `WeakSet`), never by code: http-kit copies a peer's answer `code` into its `ApiError`, so a code match is forgeable by the peer.
- **authup outgoing**: the client-credentials token is cached on the `IClock` until `PEER_TOKEN_REFRESH_MARGIN_MS` before expiry; a 401 drops it and retries once inline, a second 401 is permanent.
- **Module**: `peerModule(options)` validates the options when called and in `setup` registers the resolver as `AppToken.PEERS` (`approvalUrl` defaults to `approvalUrlOf(config)`, the clock to `AppToken.CLOCK`); the engine module passes it to the engine, so `@chamvi/app` names no feature package. `PEERS` holds one value: the last registration wins.

## HTTP peer routes

`@chamvi/http` serves the receiving side with the existing routes; a principal is a peer when `engine.peers?.recognize(toInvoker(principal))` names one.

- **Start** (`POST /agents/:name/runs` with `role` or `peer`): from any other principal 400 before validation, any engine call or idempotency claim. For a peer the grant (`chamvi_agent_run` for `{ name, private }`) comes before body validation, and an unknown and an ungranted agent answer the same 404, so a peer cannot probe agents; no `http.on()` is needed (`engine.dispatchPeer()`).
- **503**: only `PeerStartBusyError` (`peer_start_busy`, the peer-count lock held) maps to 503 with `Retry-After: 1`, not reported to `onError`. Rejected: mapping `InvalidRunStateError`, which artifact storage throws too.
- **Peer view** (`GET /runs/:id`): a peer reads only runs it started (invoker `id` and `kind` equal and a `peer` parent of that peer), as `{ id, status, waiting?, approval?, output?, error?, tainted, usage }` (`usage` = the run's plus its `subtreeUsage`, so the caller's `maxSubtreeTokens` counts the remote tree); `approval` is the pending approval in the run or below it, with `url` from `peers.approvalUrl`. Any other run answers the unknown-run 404. Cancel follows the same rule and needs no `chamvi_run_cancel`.
- **Wake** (`POST /runs/:id/wake`, content free): a non-peer gets the unknown-run 404; every peer gets 202 whatever the run (a stand-in that settled or was cancelled meanwhile is routine; a 404 would reach the waking app's `onError`), and only a stand-in waiting on that peer is marked. A detached `engine.tick()` follows only when `engine.wake()` answers `marked` (a fresh mark), so repeated wakes add no ticks.
- **Starts**: a recognized peer credential starts runs only through the peer path (`dispatchPeer()`: its taint and `from` check); without the peer and role fields `POST /agents/:name/runs` answers 400, and the ordinary dispatch (MCP `run_<agent>`, `RunHttpService.dispatch()`) refuses it with 400. Rejected: an ordinary run for a peer token (untainted, past the role's `from`).
- **Approve** (`/runs/:id/approve`, MCP `approve_run`, both `answer()`): a peer principal gets the unknown-run 404 before any read, whatever its grants (answering stays with the owning app).
- On every other route a peer principal is an ordinary principal: `chamvi_agent_run` for an agent also reads its non-private runs, so a peer token gets narrow grants.

## Testing

`packages/peer/test/unit/` drives the transport with a fake `fetch` (`test/utils/fetch.ts`) and a `ControllableClock`; `e2e.spec.ts` runs two real `@chamvi/app` apps (`memoryStoreModule()`) against each other over HTTP on free ports. `packages/http/test/unit/runs/peer.spec.ts` covers the routes with a fake resolver.
