# App and CLI

Read before changing `@chamvi/app` (lifecycle, modules, config, models, agent folders, check) or `@chamvi/cli`.

`@chamvi/app` (library, no process concerns) turns `export default createApp({ agents, modules?, models? })` into a running app; `@chamvi/cli` (bin `chamvi`, citty only) adds argv, entry loading, signals and exit codes. The CLI, env, routes and image they expose are the downstream contract: check a change against [references/helm.md](../references/helm.md) and [references/agent-template.md](../references/agent-template.md) (AGENTS.md → *Downstream Repos*).

- **App**: `createApp()` is synchronous and side-effect free (refuses options that are no object or an `agents` that is no array (no agents at all is allowed: `chamvi:agents` logs `NO_AGENTS_MESSAGE` as a warning when there is no agents dir or package either), a string `agents` entry that is no bare package specifier (`splitAgentEntries()`, `package/helpers.ts`: relative/absolute paths, URLs, Node builtins, a specifier listed twice; strings go to `IApp.packages`/`AppContext.packages`, everything else to `IApp.agents`, never a file access), a `modules` entry that is no `IModule` object, since orkos would `import()` a string, and a name used twice, a built-in's included) and branded (`APP_BRAND`, `isApp()` matches another installed copy). Each lifecycle (`start({ env?, dev? })`, `check({ env?, dev? })`, `runJob({ agent, subscription?, env? })`, `migrate({ env? })`) builds one orkos `Application` over a fresh eldin `Container` with `AppToken.CONTEXT` (`mode` `start`/`job`/`migrate`, `dev`, `env`, the stop `signal`, `report`, `models`, `agents`, `packages`, `check: true` for `check()`, `job: { agent }` for `runJob()`) registered first; an app runs one lifecycle (`app_in_use` after it, also after `stop()`). orkos graph errors (a dependency the app does not register, a cycle, a version mismatch) become `InvalidAgentDefinitionError` (`toSetupError()`). `stop()` is memoized: it aborts the context signal (`app_stopped`), waits for the lifecycle in flight, tears down; a setup error answered by `app_stopped` is logged, never lost; every teardown error is reported (orkos swallows them, `reportingModule()`) and `stop()` (or a job's teardown) then rejects with `app_stop_failed`. A module whose `setup` throws is never torn down by orkos, so each destroys its own partial state first; one whose `onReady` threw is, so every `teardown` tolerates half-built state.
- **Modules**: built-ins in order `chamvi:config`, `chamvi:store`, `chamvi:static-tokens`, `chamvi:engine`, `chamvi:agents`, `chamvi:scheduler`, `chamvi:http` (`ModuleName`), each replaced in place by a user module of the same name, then the user modules. `setup` contributes to the collection tokens (`HTTP_ROUTES`, `CHANNELS` (every `IChannel` the engine registers: the engine module's `agent` channel (`agentChannel()`, start and job mode, so a user channel named `agent` clashes), the scheduler module's `cron` channel, the http module's `http`, `mcp` and `webhook`, `consoleChannelModule()`'s, the feature modules'; names unique, a clash fails the setup with `InvalidAgentDefinitionError`), `AUTHENTICATORS` with an `order`, `LIFECYCLE_HOOKS`, `CONNECTION_TYPES`, `UI_PAGES`, `GIT_CREDENTIALS` (git credential sources, structurally `GitCredentialSource`, for `sandboxModule()`; `githubModule()` contributes its App's)); `onReady` consumes (engine: channels; http: authenticators, routes, every contributed channel with an `in` for `createHttpApp({ channels })`), so contributions need no order; a module resolving `ENGINE` or `SERVER` in `onReady` lists it in `dependencies`. Start steps (`module/start.ts`, internal): the engine module registers `engine.start()` in `onReady` (job mode: `runJob` starts it with `channels: false`); the app runs the steps once every `onReady` ran (user modules included): `engine.start()` (recovery, then every channel's `start`), then the http module's serve step (the `started` hooks, i.e. the purge timer, then `serve()` and `ready()`); without the http module the app runs the `started` hooks itself and the `stopping` hooks before the teardown. So a configuration error found in any `onReady` starts nothing and executes no queued run of the shared store. Hooks: `engineCreated` (start, job and a check), `started`, `stopping` (first in the shutdown, before the drain stops the channels), `drained` (after the engine drained, before the store closes); a throwing hook is reported, the others run. The static-tokens module contributes `CHAMVI_TOKENS` in `setup` and, in dev without any other authenticator, a random `*` token (id `dev`, logged once) in `onReady`; http lists it as an optional dependency. Optional modules live in the feature packages on a `/module` subpath (`@chamvi/github/module` `githubModule`, `@chamvi/channel-openclaw/module` `openclawModule`, `@chamvi/sandbox/module` `sandboxModule`, `@chamvi/ui/module` `uiModule`; `@chamvi/app` an optional peer there, `src/module/` the only folder importing it, kept external in `dist/module.mjs` so one `AppToken` set exists per process) and contribute their channel to `CHANNELS` or provide their instance in the `engineCreated` hook through the package's context pair; a throwing `engineCreated` hook (e.g. a second provide of one key) is caught by `runHooks` and reported through `context.report()`, the app still starts. `@chamvi/app` keeps only `/authup` (`authupModule`, `oidcModule`: moving them to `@chamvi/http` would make http depend on app, a cycle) and `/testing` (`buildModuleHarness()`/`createModuleHarness()`: the real lifecycle over the given modules, `reportingModule` and `runStartSteps` included, `reported` collecting `context.report()`), and its main entry exports the module contract (`AppToken`, `ModuleName`, `AppContext`, `ILifecycleHook`, env readers, `approvalUrlOf`, the orkos `IModule` and eldin `IContainer` types). No `@chamvi/*` feature package is in any of its dependency fields. nx 23.3 and release-please's node-workspace plugin (17.x, `updatePeerDependencies: true`) both read the package.json graph: nx turns dev and peer dependencies into static edges, release-please takes dependencies, devDependencies, optionalDependencies and peerDependencies, and a cycle aborts the whole release run (`found cycle in dependency graph`, nx exclusions do not reach it). So the graph is acyclic in all four fields, without `nx.implicitDependencies` exclusions: `@chamvi/test-kit` does not depend on `@chamvi/sandbox` (its workspace contract types `IWorkspace` structurally), which would close `sandbox -> app -> ... -> test-kit -> sandbox`, and `@chamvi/sandbox` names no provider package. `packages/app/test/unit/graph.spec.ts` pins it from `release-please-config.json`. Optional modules read `options.env ?? process.env` and check their options when the factory is called (errors name the variable, never echo a value, also for the values `createGithubApp()` and `openclawChannel()` refuse) and expose their instance synchronously.
- **Config and env** (`readConfig(env, { mode, dev })`, `env/`): empty is unset, integers `/^\d+$/` and every `*_MS` at most `TIMER_MAX_MS` (2^31 - 1, a larger Node timer fires after 1 ms), booleans `true|false|1|0`; every error names the variable and never its value. `DATABASE_URL` builds a `DataSource` (`STORE_ENTITIES`, `STORE_MIGRATIONS`, `connectTimeoutMS` `STORE_CONNECT_TIMEOUT_MS` 10 s, password masked in place in every error), migrated in migrate mode or with `CHAMVI_MIGRATE`; without it in-memory repositories from `createMemoryStore()` (warned outside dev); `purgeExpired()` hourly in start mode. Models (`models/`; the user page is docs `guide/models.md`): `createApp({ model?, providers?, models? })`, `chamvi.json` (`CHAMVI_CONFIG_FILE`, else `./chamvi.json` when it exists; JSON `{ model?, providers?, agents?, remotes? }` (`agents`: package specifiers, validated only by `readConfigFileAgents()` in the agents module, located from `process.cwd()` like the model settings, never `AgentsModuleOptions.cwd`, so both read one file; a problem fails the agents setup, not as a model setting), `locateConfigFile()`/`readConfigFile()`/`readConfigFileAgents()` in `file.ts`, refusing a literal `apiKey` and literal credential headers `SECRET_HEADER_PATTERN`) and env (`CHAMVI_MODEL`, `CHAMVI_PROVIDER_<NAME>_TYPE|API_KEY|BASE_URL|HEADER_<HEADER>`, `TEAM_A` <-> `team-a`) are merged by `readModelSettings()` (`settings.ts`) into `ModelSettings { model?, providers, configFile? }` plus `ModelIssue`s: env over file over code, per provider name and field; a higher source with another `type` replaces the provider; a `CHAMVI_PROVIDER_<NAME>_*` variable without `_TYPE` needs another source to declare the name; a declared provider replaces the implicit one (bare `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`, `MISTRAL_API_KEY`, `XAI_API_KEY`, plus `ANTHROPIC_BASE_URL`/`OPENAI_BASE_URL`, `BUILTIN_PROVIDERS`; `gateway` never implicit). Every field and default model carries its `SettingSource` (`env | file | code | implicit`). `ProviderConfig { type, apiKey?, baseURL?, headers? }`, `ProviderType` `anthropic | openai | openai-compatible | google | mistral | xai | gateway` (`PROVIDER_TYPES`: package, factory, public default URL, `keyRequired`; only `openai-compatible` may be keyless and needs `baseURL`), `SecretValue = string | { env } | { file }` (`readSecret()`, `secret.ts`: `{ env }` from the app's env only, `{ file }` relative to the cwd, one trailing newline trimmed), base URLs absolute http(s) without userinfo, query or fragment (`assertBaseUrl()`, `helpers.ts`), header names lower-kebab. `createModelResolver(settings, { models?, importer? })` (`resolver.ts`, internal) imports each needed package up front, builds each provider once with an explicit `apiKey` and `baseURL` (never a factory's `process.env` fallback) and is the engine's `IModelResolver`; `models` (AI SDK providers by id) wins for its ids; a package that is not installed is recorded in `errors` and refused at `check` (`Provider type "<type>" needs package <pkg>.`); an unknown provider names the variables (`Agent "<a>" uses provider "<p>", which is not configured. Set CHAMVI_PROVIDER_<P>_TYPE and CHAMVI_PROVIDER_<P>_API_KEY, or declare it in chamvi.json.`). The engine module reads the settings in `setup` (start and job; any issue: one `InvalidAgentDefinitionError` `The model settings have <n> issue(s):` with a line each) and passes `model` and `models` to `new Engine`. No module reads or writes the AI SDK's global default provider, so two apps in one process keep their own providers. No key, credential header value or credential-bearing URL reaches a store row, log line, error or the `start --check` output.
- **Agent folders** (`loader/`, `modules/agents/`): `CHAMVI_AGENTS_DIR` (optional, relative to the cwd; unset, `AgentsModule.setup` takes `./agents` (`DEFAULT_AGENTS_DIR`) when it is a directory, and an explicitly named dir that is none fails `onReady`) and `CHAMVI_AGENTS_POLL_MS` (`DEFAULT_AGENTS_POLL_MS` 5000, 1 to `TIMER_MAX_MS`) and `CHAMVI_AGENTS` (`packages`, see Agent packages) in `AppConfig.agents`. Layout `<dir>/<name>/agent.ts` and nothing else enforced (owner decision 2026-10-22; folder name = agent name, `.`/`_`-prefixed folders skipped): `agent.ts` default-exports `defineModelAgent()`'s or `defineSimpleAgent()`'s result, checked structurally (`name` a string, `definition` an object) so another core copy's agent passes; its `name` must equal the folder name (a missing `agent.ts` is `<name>: has no agent.ts.`, no `.mts`/`.js`/`.mjs` variant), and its `definition` is re-run through this copy's factory of its `kind` (kind-less, from an older core: a model agent unless it has `run`). The rest of the folder is the user's: `agent.ts` loads its tools, instructions, subscriptions and helpers with plain imports or reads (`readFileSync(new URL('./prompt.md', import.meta.url))`). `agent.ts` loads through one `jiti` (`moduleCache: false`, `fsCache: false`, `createModuleJiti()`, `readFreshModule()`): `readModule()` evaluates it with `evalModule(source, { forceTranspile: true })`, and its relative `.ts`/`.mts` imports transpile fresh too; a JavaScript file anywhere in the folder (`.js`/`.mjs`/`.cjs`, `assertNoScripts`, checked before any load) is a load error, since Node's native import cache never forgets one; required JSON is dropped from the CommonJS cache after each read. `createPackageAliases()` pins `@chamvi/*`, `ai` and `@ai-sdk/*` (every non-wildcard exported subpath, ESM conditions, closest `node_modules` of `@chamvi/app` first) as jiti aliases, so an agents dir anywhere (a volume outside the app) gets the app's instances; packages load natively. A `node_modules` folder in an agent folder or the agents dir is a load error (a second copy). `test/unit/loader/identity.spec.ts` pins a module-provided context key injected by a tool `agent.ts` imports, on the built packages (so nx runs the app's tests after its build). `locter` (`locateMany`, folder discovery and hashing) and `jiti` are dependencies of `@chamvi/app` only. `hashAgentFolder` = sha256 hex over every file (dot-entries skipped, and `isHashIgnored()`: a basename matching `HASH_IGNORE_PATTERNS` (`README*`, `CHANGELOG*`, `NOTES*`, `LICENSE*`, `*~`, `*.swp`, `*.swo`, `*.bak`, `*.orig`, `.DS_Store`, case-insensitive, any depth) whose extension is not in `HASH_IMPORTABLE_EXTENSIONS` (`.ts`, `.mts`, `.cts`, `.json`), `loader/constants.ts`) by relative POSIX path, `path\0bytes\0`, taken before and after the read (a difference is `changed while loading`); `hashFolder()` (`loader/helpers.ts`) is the shared walk, and `formerAgentFolderHash()` the full-folder hash of before the ignore list, passed by the watcher as `putAgent`'s `formerRevision` when it differs, so the upgrade moves markers instead of cancelling runs. `loadAgent` throws `InvalidAgentDefinitionError` naming files relative to the agents dir; `loadAgents` returns `issues`. `AgentsModule` (depends on config and engine): `setup` resolves the dir (`this.root`) and, without one, only warns for an app without agents passed in code (`NO_AGENTS_MESSAGE`), else registers `AGENT_ISSUES` and, in start mode, the lifecycle hook `chamvi:agents-watcher` (`started` starts, `stopping` stops); `onReady` (start and job) checks the dir (`NO_DIRECTORY_MESSAGE`) and boots the watcher with a role (`AgentsWatcherOptions.role`: `check` for `context.check`, `job` in job mode, else `start`): every folder loaded and `putAgent(agent, { revision: hash })` (role `start`; the model checked by `putAgent` itself), `putAgent(agent, { revision: hash, reload: false })` (role `job`: a missing marker written, a different one moved only without unsettled runs; an `InvalidRunStateError` is an issue `<name>: <message> A job never reloads an agent: start the app to apply the change.` kept as `watcher.conflict(name)`, and when `context.job.agent` has one `onReady` throws `InvalidRunStateError`, so the job exits 1, while another agent's conflict lets the job run) or `engine.checkAgent(agent)` (role `check`, no store access), then (role `start` only, unless `removeOrphans` is false: a package failed before its agents were known, `ORPHANS_KEPT_MESSAGE`) every marker with neither a folder nor a `reserved` name removed (`removeOrphanAgents()`, `helpers.ts`; without an agents dir the module runs it over package markers only (`isPackageMarker()`), keeping code and claimed package names, so folder markers outlive a missing or unmounted dir); all before the start steps. Before the boot (not in a check) it subscribes to `agents.cancelled` and logs each sweep at `info`: `agent reloaded` (`AGENT_RELOADED_MESSAGE`) or `agent removed` (`AGENT_REMOVED_MESSAGE`) with `{ agent, revision?: formatRevision() (core, public), cancelled: <run ids> }`; `teardown` unsubscribes. Upgrading to the ignore list changed folder hashes: a marker at the former full-folder hash is moved to the new hash without a cancel (`formerRevision`); a folder that also changed while the app was down cancels once, as any change does. Before `putAgent` a folder agent passes the `check`: every `AGENT_CHECKS` contribution (scheduler: `assertSchedulable`; http: `assertMcpRunTool` unless `mcp: false`; both in start and job mode), and an `InvalidAgentDefinitionError` from `putAgent` itself (a subscription to an unknown channel, a model that does not resolve, thrown before any store write) is an issue too, so nothing a later consumer refuses crashes the boot or cancels runs; the cron channel and `createRunToolSource` report a folder agent's failure to `onError` instead of throwing. A load is registered only when it read exactly the poll's stable hash (else `unstable`: nothing recorded, the next stable poll decides; the boot retries `BOOT_LOAD_ATTEMPTS` 3 times). Every poll reads the markers once and records an applied agent whose marker another process moved or removed while its folder is unchanged as an issue (logged `agent revision moved`), without re-syncing. The watcher (`createAgentsWatcher`, internal) polls on the `IClock` (`keepAlive: false`): a folder whose hash differs from the last attempted one loads once two consecutive polls see the same hash, a folder with an invalid static definition is tried once per content; failed skill preparation instead retries with capped exponential backoff (an issue `{ agent, message, at }` logged `agent load failed`, the previous agent kept, no marker written), a folder missing on two polls is removed, a missing agents dir removes nothing, a store failure retries on a later poll; a folder with a `reserved` name (`AgentsWatcherOptions.reserved`: the agents passed in code, then package agents, each with its issue message) is an issue, never loaded or removed. The register tail (checks, `prepare`, `putAgent` and the outcome mapping) is `registerAgent()` (`register.ts`), shared with package agents. `AGENT_ISSUES` reaches `createHttpApp({ agentIssues })` and the UI's agents page notice.
- **Agent packages** (`package/`, `modules/agents/packages.ts`; #118): specifiers merged by `mergePackageSpecifiers()` in order createApp, `chamvi.json`, `CHAMVI_AGENTS` (that order is the duplicate-name order), loaded once in `onReady` before the folder watcher boots (no watcher: a package does not change within a process; `chamvi dev` restarts). `loadAgentPackage()` resolves with jiti's `esmResolve` from `AgentsModuleOptions.cwd` with the process's user conditions first (`userConditions()`: `--conditions`/`-C` in `execArgv` and `NODE_OPTIONS`; jiti alone uses only `node`, `import`, so a `development` export would load `dist` while the package's own imports take `src`) (real path, so a linked workspace package and its image copy are one root), walks up to the `package.json` naming the package, needs a string `version`, then `pinPackageImports(root)` (`hooks.ts`): one `module.registerHooks()` resolve hook per process that maps the `createPackageAliases()` specifiers to the app's copies for every parent URL below a package root (its nested `node_modules` included). Rejected: jiti aliases, which leave imports inside built `.js` in `node_modules` unpinned (a nested `@chamvi/core` loads). Then a native `import()` (linked `.ts` sources: Node's type stripping, so explicit `.ts` imports and erasable syntax only, documented; rejected: jiti for them, a second loader path beside the hook); the default export is an agent, a non-empty array, or a function (sync or async, called once without arguments; a throw is a load error) returning one of those, checked by `isDeclaredAgent()` and rebuilt by `rebuildAgent()` (`loader/helpers.ts`, shared with folders). Revision: `<name>@<version>` (prod), `<name>@<version>+<12 hex of hashAgentPackage(root, { entry })>` in dev (`context.dev`; the npm publish set: `files` with `!` excludes plus `package.json` and `main`, else all but top-level `test/`, plus the resolved entry's top-level folder, since a linked package may export `src/` outside `files`; code imported from outside both is not hashed, documented, owner decision over hashing the whole root; `node_modules`, dot-entries and `isHashIgnored(key, PACKAGE_HASH_IMPORTABLE_EXTENSIONS)` left out, so `.js`/`.mjs`/`.cjs` count whatever the name; `package.json` hashed as JSON without `version`); over 128 characters (the marker column) is an issue. Dev passes the prod marker as `formerRevision`, prod a stored `<name>@<version>+<12 hex>` (read after preparation, never in a check), so a dev/prod switch never cancels. Trade-off (owner decision): every version bump cancels (linked versions: every release cancels every package agent's runs), a production change without a bump keeps the marker. Order createApp > package > folder: a package agent named like an agent passed in code or an earlier package's is an issue keyed `<spec>\0<name>`; a claimed name stays reserved against folders also when its check or preparation fails, and while a package is `unresolved()` (start and job) every name whose stored marker is a package marker (`isPackageMarker()`: contains `@`) is reserved too, so a folder never takes over (and cancels) a package agent whose import broke. Resolve/import/shape failures are issues keyed `<spec>\0` (`unresolved()`), recorded once (Node caches a failed evaluation); only skill preparation retries (`nextRetryDelay()`). A job of a failed package agent, or of an unknown agent while a package is unresolved, throws `package_agent_failed` (exit 1); its revision conflict `InvalidRunStateError`. Messages and the `agents.cancelled` log name a non-hash revision in full (core's public `formatRevision()`). `test/unit/loader/package-identity.spec.ts` pins the hook on the built packages with throwing decoy copies nested in a built and a linked TypeScript package.
- **Keyring and connections** (`keyring/`): `AppToken.KEYRING` is a lazy `useFactory` of the config module (`readKeyring(env)`, `CHAMVI_ENCRYPTION_KEYS`, errors prefixed with the variable, never the value) unless a module registers one: read only when resolved, so an app without such a module needs no key, and a check fails through the resolving module's setup. `AppToken.CONNECTIONS` is a collection the http module resolves once in `onReady` (contributions happen in `setup`) as `createHttpApp({ connections })`. `AppToken.CONNECTION_CONFIGS` is a second lazy `useFactory` of the config module, over `STORE` with a keyring getter, so only creating a row (every row gets a wrapped data key) or touching a secret reads the variable; it throws on a store without `connections`, so the http module and every feature module check `store.connections` first and then stay env-only (no stored accounts, types listed read-only, no save answering 200). `AppToken.CONNECTION_TYPES` is the collection of `IConnectionTypeProvider`s.
- **Provider pages** (`modules/ui-page/`): `uiPageModule({ name, label, types, slug, root, uiBase? })` contributes the page's `staticRoutes()` at `<uiBase>/ext/<slug>` to `HTTP_ROUTES` and its entry to `AppToken.UI_PAGES` (`GET /ui-pages`), reading the dashboard's authup variables for the CSP. `uiBase` (default `/ui`) must equal `uiModule({ basePath })`; every `*-ui` factory takes and forwards it. A page needs no dependency on `@chamvi/ui`, and `uiModule()` plus any number of pages coexist in either registration order.
- **Stop order**: `createShutdown().shutdown()` (readiness 503, `CHAMVI_READINESS_DELAY_MS`, the `stopping` hooks, closers, `server.close()`, `engine.drain()` (every channel's `stop()` first, the cron schedule among them), the close timeout), then the engine module's `drained` hooks (sandbox: `detach()` and `manager.close()`, which keeps the workspaces of live runs unless the store is a `createMemoryStore()`), then the store's `dataSource.destroy()`.
- **Check** (`IApp.check()`, `chamvi start --check`; a connection listed `incomplete` is an issue, `connectionIssuesOf()`): the `start` lifecycle (mode `start`, `context.check: true`, `app_in_use` after it) that `setup()` ends before `runStartSteps` and the app-run `started` hooks, then tears down and resolves `AppCheckResult { issues }` (`AGENT_ISSUES`, else `[]`; `AppCheckOptions = AppStartOptions`). Every module sets up and checks as for a start (config, authenticators, the model settings, channels), and nothing writes the store: the store module never migrates and registers no purge hook, and with `CHAMVI_MIGRATE=false` (not the default) a TypeORM store with pending migrations (`pendingMigrations()`) fails with `APP_ERROR_CODE.STORE_NOT_MIGRATED` (`store_not_migrated`, exit 1), in-memory repositories or `options.store` is not checked; the agents module registers no watcher hook, does not subscribe to `agents.cancelled` and boots the package agents (resolve, import, checks) and the watcher with role `check` (`engine.checkAgent()` instead of `putAgent`, no store read) and runs every `AGENT_CHECKS` contribution over the agents passed in code (a start does the cron check in `engine.start()`, which a check never reaches); the http module passes `readinessDelayMs: 0` and registers no `stopping` callback, so of the hooks only the paired `engineCreated` and `drained` run. An agent passed in code on an unknown channel rejects (`invalid_agent_definition`), a folder agent on one is an issue (bug 15 by construction). The scheduler and http modules register their `AGENT_CHECKS` in `setup` (no `IAgentCheckSource` any more).
- **CLI**: commands `dev`, `build`, `start` (`--check`), `run-job`, `migrate`; exit codes `0` success, `1` runtime failure or forced exit, `2` usage or configuration (citty's `CLIError`, `cli_usage`, `invalid_agent_definition`; `exitCodeOf()` takes the codes from `@chamvi/app`). The entry is `--entry <path>` (a bare one is exit 2), else `chamvi.entry` (source commands only), else `src/index.ts` or `dist/index.mjs`; with none of them `resolveEntry()` is `undefined` and `loadEntryApp()` builds the default app `createApp({})` (agents from `./agents` or `CHAMVI_AGENTS_DIR`, packages from `chamvi.json` or `CHAMVI_AGENTS`, `DEFAULT_APP_NOTICE` on stderr), `dev` spawns `start --dev` without `--entry`, `build` exits 2 (nothing to build); a missing `dist/index.mjs` beside a `src/index.ts` keeps the build hint. Signals (`installSignalHandlers()`): the first SIGTERM/SIGINT stops (exit 0, or 1 when the stop failed); a repeat within `SIGNAL_REPEAT_MS` (1 s) is the same signal (npm forwards SIGINT while the terminal signals the group); a later one exits 1; `CHAMVI_FORCE_EXIT_MS` (90 s, dev 15 s) after the first exits 1, on a kept-alive timer cleared once the stop settled. `run-job` exits 1 for `package_agent_failed`; it keeps the job's code over the stop's (a failed run stays 1 after a signal) and prints `<agent>: <status> (run <id>)`. `dev` spawns `node --watch [--env-file-if-exists=.env] <cli> start --dev --entry <src>` detached (the env flag only when `.env` exists at start; Linux `node --watch` fails with ENOENT on a missing env file) (one forwarded signal per signal; SIGHUP and the CLI's exit send SIGTERM) with a stdin pipe only it writes and `CHAMVI_DEV_LINK=1`, so `start --dev` ends the whole group (`kill(-ppid)`) once the pipe closes (the CLI died by SIGKILL). `start --check` (`commands/start.ts`): the same entry resolution, `.env` (`--dev`) and signal handlers as `start`, then `app.check({ dev, env })` (an app of a copy without `check` is a usage error): no issue prints `CHECK_PASSED_MESSAGE` (`chamvi: start check passed`) on stdout, exit 0; else each issue's message on its own stderr line, exit 2; a rejection goes through `exitCodeOf` (2 configuration, 1 a store failure). `build` drives tsdown (optional peer) into `<out-dir>/index.mjs` with `clean: true`, refusing an out dir that is the project folder or above it, holds the entry, or holds anything but `.mjs`/`.mjs.map` files. `start --dev` (hidden from the usage) loads `.env` with `node:util` `parseEnv` before the entry import.

## Testing

- `@chamvi/app` tests run modules on `createHarness()`/`buildHarness()` (`test/utils/harness.ts`, an alias of the public `createModuleHarness()`/`buildModuleHarness()` from `@chamvi/app/testing`: an orkos `Application` over a fresh eldin container with `AppToken.CONTEXT` registered, the modules wrapped like the app does, `setup()` also running the start steps, `reported` collecting `context.report()`) or a whole `createApp()` with `start({ env })`; real loopback ports come from `freePort()` (`test/utils/port.ts`), log lines from `createRecordingLogger()` (`test/utils/logger.ts`). `test/unit/readme.spec.ts` starts the README example with `ANTHROPIC_API_KEY` in its `env` (it builds the implicit `anthropic` provider the example's default model names, through the `@ai-sdk/anthropic` devDependency; nothing calls the model); a spec that starts an app with a string model passes a key or `models`, since no global provider exists any more. The Postgres suites (`describePostgres`, a database per test from `createTestDatabaseUrl()` in `test/utils/database.ts`) need Docker like `@chamvi/store-db`: `test/global-setup.ts` starts `postgres:18-alpine` with testcontainers, skipping with a warning locally and failing when `CI` is set. `test/unit/app/check.spec.ts` drives `IApp.check()` over capabilities from `createMemoryStore()` with a recording `Proxy` per role (every call not named `find*`/`read*` is a write) to pin that a check writes nothing; the harness takes `check` and `job` (copied into the context), and `test/utils/agents-dir.ts` passes them on.
- The optional modules' specs live in their feature package (`test/unit/module/`) and run on `createModuleHarness()` from `@chamvi/app/testing` with the built-ins they need, asserting a contribution (a channel in `AppToken.CHANNELS`, a route) through `harness.container` and a refused provide through `harness.reported` (never a rejected `setup()`); `test/unit/context/` pins a context pair against a real `Engine` run. Their vitest config aliases `@chamvi/app`, `@chamvi/app/testing`, `@chamvi/http`, `@chamvi/channel-cron`, `@chamvi/store-db`, the package itself and its own `/module` to sources. `@chamvi/sandbox` still never imports `@chamvi/test-kit`.
- `test/unit/loader/identity.spec.ts` spawns `test/fixtures/identity/run.mjs` on the built `@chamvi/app` and `@chamvi/core` (a folder tool in a temp dir outside the tree injects a module's context key), so `nx` runs `@chamvi/app:test` after its build (`dependsOn: ["build"]`); running that spec by hand needs `npm run build` first. `test/utils/agents-dir.ts` builds the agents module harness for the newer agents specs.
- `@chamvi/cli` command tests call `runCli(argv, context)` with the fake process of `test/utils/process.ts` (signals, a `ControllableClock`, recorded exit codes, `linkToParent` calls) over the apps in `test/fixtures/` (`app`, `failing`, `hang`, `slow`, `keyless`, `broken`). The `test/unit/bin/` specs spawn the built `dist/cli.mjs` (`spawnCli()` in `test/utils/spawn.ts`), which imports the built `@chamvi/app`, so `nx` runs `@chamvi/cli:test` after its build (`dependsOn: ["build"]`); running vitest by hand needs `npm run build` (at least `@chamvi/app` and `@chamvi/cli`) first. `test/unit/commands/start-check.spec.ts` pins `start --check` (exit codes, one stderr line per folder issue, nothing listening).
