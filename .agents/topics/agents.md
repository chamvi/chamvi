# Agents, Registry and Models

Read before changing `defineModelAgent()`, `defineSimpleAgent()`, instructions, the tool context, the live agent registry or model resolution (`@chamvi/core`).

## Agents

`toolCallKey(ctx)` reads the active frame and returns opaque run/step/call identity, stable on replay (#171). Use it for call-scoped artifact keys: a provider can reuse SDK call IDs across model steps. It refuses missing, expired or foreign-run frames; do not expose the mutable internal frame.

`defineModelAgent({...})` and `defineSimpleAgent({...})` take a typed config object and return `{ kind, name, definition }` with the budget defaults applied (`maxSteps: 20`, `timeoutMs: 15 min`). `model?: ModelRef` is optional (the engine's default applies, see Models); tool code reaches a model through `resolveModel(ctx, ref?)`, never a bare string to the AI SDK. Agent names match `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 chars, unique per app; `channels: ChannelSubscription[]` (subscription ids unique per agent, `InvalidAgentDefinitionError` otherwise). `private?: boolean` (both factories, `assertPrivate`) marks an agent whose runs and state only `chamvi_agent_read` reads; core only carries it, `@chamvi/http` enforces it (see [http.md](http.md)). `tools` is a plain `ToolSet` or a factory `(ctx: ToolContext) => ToolSet`, called per execution. `assembleTools` builds one `ToolContext { run, state, artifacts, channels }` per execution (shared by the factory and every call) and passes it as the `ToolLoopAgent`'s `toolsContext` (`as never`: a `ToolSet` infers no context type) only to tools whose `contextSchema === toolContextSchema` (`tool/`: `defineTool()`, `defineEffectTool()` and the state tools set it; `validate` returns the value by identity and rejects a non-object, which fails the run, since the AI SDK validates the context outside its tool-error handling). The agent's `toolsContext?: Record<string, unknown>` entries go unchanged (by reference, never cloned or stored) to tools that are not chamvi's (also to one without a `contextSchema`); an entry naming a chamvi tool or no tool is an `InvalidAgentDefinitionError` (`assertToolsContext`, `agent/helpers.ts`: thrown by `defineModelAgent` for a plain set, a failed run before any model call for a factory), and a third-party tool with a required `contextSchema` and no entry (or a rejected one) fails the run. `toRunError` turns that AI SDK `TypeValidationError` (`context.field === 'tool context'`) into a `ValidationError` naming the tool and the issue paths only, since the SDK's message (and some validators' issue messages) hold the entry's value, which may be a secret; chamvi's own missing-context issue keeps its message. `StepResult.toolsContext` is never stored (steps are built field by field). `artifacts` (`IRunArtifacts`: `put`, `get`, `list`) is scoped to the run (`get` of another run's artifact is `undefined`) and is no effect by itself (wrap `put` in `defineEffectTool` for exactly once). `output` takes an AI SDK `Output` (`Output.object({ schema })`), passed to `ToolLoopAgent` as is. `hooks: { beforeToolExecution?, afterToolExecution? }` run inside `wrapToolsForRun` for every tool of the merged set (user, chamvi, state, third-party) that has a local `execute`; a tool without one (provider-executed tools) passes through unwrapped, so neither hook sees its calls (see [Approvals and hooks](approvals.md)). An AI SDK tool declaring its own `needsApproval` is refused (`assertNoNeedsApproval`, `agent/helpers.ts`: `defineModelAgent` for a plain set, a failed run before any model call for a factory), since nothing answers that request. `toolPolicy(toolName, { run, now })` (`ToolPolicyContext`, `now` = `clock.now()` at each check; may return a promise) is applied to the merged tool set (state tools included) in `assembleTools`, once per execution: the allowed names become the `ToolLoopAgent`'s `activeTools`, so a refused tool is never offered to the model, while every tool stays in `tools` so a pending call that runs after an approval (policy tightened before the resume) still reaches `wrapToolsForRun`, which re-checks every call and answers a refused one with a `ToolNotAllowedError` tool error (the run goes on). A model that calls a refused tool anyway gets the AI SDK's `NoSuchToolError` answer (the tool is not in `activeTools`); `refusedCallError()` (`execute/helpers.ts`) records that tool step as `ToolNotAllowedError` (`tool_not_allowed`), only for a tool of the full set whose invalid call carries a `NoSuchToolError`, so a genuinely unknown tool keeps the SDK's error. The policy should depend only on the run snapshot, so the tool set is stable across executions. `requireToolPermission({ withoutInvoker? })` (`permission/`) offers a tool when `can(invoker, chamvi_tool_use, { attributes: { agent, name }, now })` of `@chamvi/access` holds (a stored old-string invoker grants nothing, never throws); runs without an invoker follow `withoutInvoker` (default `'deny'`). With a `toolPolicy`, `effect/wrap.ts` awaits the policy again per call (a synchronous policy is answered synchronously, so the pass-through of a tool without hooks stays), so a `time` policy that closed during an approval refuses the resumed call; a policy that rejects there is a `FatalToolError` (`The tool policy failed for "<tool>": ...`). Under an asynchronous policy a plain-function `defineTool()` tool returning an `AsyncIterable` is reduced to its final value (it is only known to stream after the await); an `async function*` tool keeps streaming; a synchronous policy changes nothing.

`defineSimpleAgent()` preserves a concrete tool set as its second inferred generic (#171); the first remains state. Declared calls use SDK `InferToolOutput`; inputs remain raw `unknown` before schema validation/transforms; dynamic names and sets annotated only as `ToolSet` keep `unknown` results for runtime-added tools. Tool factories must retain their concrete return type for inference.

**Simple agents** (#131): `Agent` is the union `ModelAgent | SimpleAgent` on `kind` (`'model'`/`'simple'`, narrows the definition too; `?: never` members keep `definition.x` reads on the union compiling); each kind has its own factory with one plain input (`defineModelAgent`, `defineSimpleAgent`; rejected: one factory with a union input that inferred the kind from `run`). `defineModelAgent` refuses `run` (`assertModelAgent`), `defineSimpleAgent` refuses `model`, `instructions`, `skills`, `output`, `conversation`, `toolsContext` and a tools factory (`assertSimpleAgent`); `assertRegistrable` first refuses a `kind` that is unknown or disagrees with the definition (`assertAgentKind`: hand-built agents), then skips `checkAgentModel` for a simple agent; the app loaders rebuild a declared agent through the factory of its `kind`, a kind-less one (older core) as a model agent unless it has `run`; the skills runtime skips the agent (global contributions too). `Engine.execute` forks into `engine/execute/simple.ts` after the shared cancel, revision guard and requeue, skipping conversation admission: `bindTrust`, `bindRunSnapshot` and the same `ToolContext` (`createToolContext`) as a model run, then `run(payload, ctx)` inside one synthetic frame (`toolCallId` `run`, `toolName` the agent, `stepIndex` 0, fresh ordinals per execution, so ids are `0:run:<n>`/`0:run:w<n>`). After `run()` settles, `frame.suspended` wins over whatever it returned or threw (user code may catch the `SuspendSignal`); else one `tool` step named after the agent, then `completed` (JSON-serialisable `output`) or `failed` (a `dispatch()` `ValidationError` too); no `llm` step, no checkpoint, `maxSteps`/`maxTokens` ignored, `timeoutMs` per execution. **Replay rule**: every execution re-runs `run()` from the top; only effect-recorded calls return their records, and a wait's record is returned by its id whatever runs the replay passes, so the order of suspend points must not depend on unrecorded state. `ctx.tools` (`simple-tools.ts`) is the assembled set after `toolPolicy`, each call through `executePendingCall` with `toolCallId` `run:<n>` (ordinal taken synchronously), so effect keys, trust and gates match a model's call; a tool error rethrows (a `FatalToolError` also fails the run, caught or not, ahead of a pause), calls still in flight are awaited (bounded by the run signal) before the pause or settle so an effect never runs past the frame, a tool's suspension throws `SuspendSignal`, an unknown name refuses through a `Proxy` (`ValidationError`).

## Structured instructions

`AgentInstructions` is a string or readonly array of native `SystemModelMessage | UserModelMessage | AssistantModelMessage`; aliases and native content types are exported from core's `message/` and re-exported normally by app. `defineModelAgent` validates array shape/allowed roles synchronously, including sparse entries; SDK validation retains role-specific content/provider options. Strings normalize to one system block. Execution composes agent blocks before contribution blocks and splits only the longest leading system run into SDK `instructions`; the remainder is a transient ordered prompt prefix. `allowSystemInMessages` is enabled only for a configured later system block. The durable transcript is checked for system roles before pending replay/model work and on response append. Trigger payload role-like text remains user content.

Configured prefixes hydrate artifact markers before model/replay and on subsequent prepareStep calls, without mutating configuration or persisting prefixes/bytes. Recalled conversation messages follow the configured prefix; conversation persistence also excludes configured blocks and hydrated prefix bytes. Pending tool analysis and checkpoints use transcript messages only; normal and replay tools see the same conversational prefix. Current-definition prefixes are rebuilt on each execution, including fresh-Engine approval resume. `@chamvi/skills` contributes a frozen system array (or `[]`), with metadata only; manual `SkillCatalog.instructions` remains a string. MCP descriptions use the first nonblank configured system line or the named fallback, never conversational examples or binary data.

## Context

`context/` (core): `defineContextKey<T>(name)` returns a frozen `ContextKey<T>`, unique per call (registered in a module-private `WeakSet`; the name is for messages only, an empty or non-string one is `InvalidAgentDefinitionError`). `engine.provide(key, value)` stores the value by reference in the engine's `Map` and refuses a foreign key, also one of another `@chamvi/core` copy a package resolved (`Context "<name>" has no key from defineContextKey() of the engine's @chamvi/core: ...`), `undefined` (`Context "<name>" needs a value.`) and a second value for one key (`Context "<name>" is already provided.`), each `InvalidAgentDefinitionError`; a value provided after `start()` reaches the next execution, since the map is read at call time. There is no `EngineOptions.context`. The engine passes the map as `ExecuteContext.provided`; `assembleTools` binds it to the execution's `ToolContext` through a module-private `WeakMap` (`bindProvided`, `context/helpers.ts`) right after building the context and **before** the tools factory runs, so `inject(ctx, key)` / `tryInject(ctx, key)` return the same object in the factory, in `execute` and in the effect hooks (`alreadyApplied`, `effectKey`). `ToolContext` is exactly `{ run, state, artifacts, channels }` (no own key for a provided value, string or symbol), and nothing provided is stored, cloned or serialized into steps, checkpoints or runs. A spread copy (`{ ...ctx }`) or a hand-built context has no binding: `inject` takes the context the engine passed. `inject` without a value throws `ContextNotProvidedError` (`context_not_provided`, naming the key only, never a value): a tool error in `execute` and in the effect hooks (they run inside the wrapped `execute` of `wrapToolsForRun`), a run failure before any model call in the factory (`assembleTools` rethrows it, `guardedExecute` settles the run `failed` and reports it to `onError`). Feature packages export a core-only pair per shared instance (`provide*Context(engine, value)`, `inject*Context(ctx)`) and keep the key internal. Channels need no pair: `ToolContext.channels` holds run-bound handles (see [Channels](channels.md)); tools never get the engine itself.

## Live registry

**Live registry** (`engine/registry/`): the agent set changes at runtime. `putAgent(agent, { revision?, signal? })` registers an agent or replaces the one of the same name in place (a new one goes last), refusing a subscription to an unknown channel or a model that does not resolve like the constructor (`assertRegistrable`, `checkAgentModel`), before any store write, and resolves `added | replaced | unchanged` (`unchanged`, no event, for the same object at the same revision); `removeAgent(name)` resolves whether it was registered here; `agentRevision(name)` is the revision an agent was registered at (`undefined` for an agent without a revision). Both emit `agents.changed` (`AgentChange { name, kind: 'added' | 'replaced' | 'removed' }`, local; `EngineEvent = RunEvent | AgentChange`). Every marker operation runs under the store lock `agents:<name>` (`withAgentLock`, owner a fresh `randomUUID()` per attempt, TTL `AGENT_LOCK_TTL_MS` 300 s, retried every `claimTtlMs / 3` on the `IClock`, `InvalidRunStateError` after 300 s): with a `revision` (a folder's content hash), `syncRevision` reads the marker and, when it differs, cancels the agent's unsettled runs (`queued | running | waiting | interrupted`) created before `changedAt = now` (only when a marker existed: a first sight cancels nothing), then writes `{ agent, hash, changedAt }` (`changedAt` taken right before the write) and sweeps again for runs created before it (a replica at the old hash may create and start one until the write lands), so a change cancels once across replicas; while it syncs, this engine starts no run of the agent (`syncing`, checked by `prepareStart` and `isCurrent`); without one, replacing a registered agent cancels its unsettled runs created before now. `removeAgent` first unregisters the agent and emits `removed` (no further dispatch here), then `dropRevision` cancels all unsettled runs and deletes the marker when one exists (also for an agent this engine never loaded), unless this engine had the agent at another revision (a newer one registered elsewhere: marker and runs left alone); without a marker it cancels the runs of an agent registered here (with or without a revision: no replica runs it any more, so a lagging replica's runs never stay queued). Cancels run concurrently through the engine's `cancelRun(id, reason)` (a run settled or gone meanwhile is skipped, other failures go to `onError`) and store a reason as `Run.error` (`agentCancelReason()`, `registry/helpers.ts`; no error class): `agent_replaced` (`Agent "<a>" was reloaded at revision <12 hex>; its unsettled runs were cancelled.`, `REVISION_PREFIX_LENGTH` 12 for a 64-hex hash, any other marker such as a package's `<name>@<version>` in full (`formatRevision()`, public, also in the `reload: false` conflict and the app's logs), or `... was replaced; ...` for an agent without a revision) and `agent_removed` (`... was removed; ...`); a local execution keeps it on its executions entry (`cancelReason`) for `finish()`, a stored run gets it in `cancelStored`, a run on another replica with `cancelRequested` (the owner's `cancelled` settle keeps it; a `completed` settle clears `error`). `cancel(runId)` stores none. After a sweep (`syncRevision`/`dropRevision`/the replace without a revision resolve the cancelled ids, `undefined` when no sweep ran: first sight, unchanged, another revision) the engine emits `AgentRunsCancelled { type: 'agents.cancelled', name, reason, revision?, runIds }` (local, so once across replicas; also with no ids). `checkAgent(agent)` (public) throws what `putAgent` refuses before any store access (`assertRegistrable(agent, { commit: false })`) and registers nothing: its skill check (`EngineSkills.checkAgent(agent, { commit: false })`) neither selects the engine's first skill runtime nor captures the agent's skill inputs, so `putAgent()`/`prepare()` capture the definition as it is then. `putAgent(agent, { revision, reload: false })` never cancels (`claimRevision`, under `agents:<name>`): a missing marker is written (nothing cancelled), an equal one kept, a different one moved only while the agent has no unsettled run, else `InvalidRunStateError` (`Agent "<a>" runs revision <stored 12> in the store, not <loaded 12>; this process does not reload agents.`) with the agent unregistered and marker and runs untouched. `formerRevision` (both modes): a marker at it (the same content under an earlier hash algorithm) counts as equal and is moved to `revision` keeping its `changedAt`, nothing cancelled (`moveFormerMarker`). `dispatch` for an agent the engine does not hold throws `AgentNotFoundError` (`agent_not_found`, http 404).

## Models

**Models** (`model/`): `ModelRef = string | LanguageModel`; `EngineOptions.model?: ModelRef` is the default of agents without one, `EngineOptions.models?: IModelResolver { check(ref, agent?), resolve(ref) }` resolves strings `'<provider>/<model id>'` (split at the first `/`). The constructor checks the default (`checkDefaultModel`: a non-empty string or an object, a string needs `models` and passes `models.check(ref)`), and the constructor and `putAgent` check every agent (`checkAgentModel`, public: `Agent "<a>" has no model and the app sets no default (CHAMVI_MODEL).`, a ref of another shape, a string without a resolver, a string `check` refuses; objects are never checked), each `InvalidAgentDefinitionError`. At execution start the engine takes `agent.definition.model ?? options.model`, resolves a string through `models.resolve()` (`toLanguageModel`, `model/asserts.ts`; a resolver failure is wrapped as `Model "<ref>" could not be resolved: ...`) and always hands `ToolLoopAgent` an object, so the AI SDK never sees a string and its global provider is never consulted. `resolveModel(ctx, ref?)` (public) gives tool code a `LanguageModel`: `ref`, else the run's agent model from the live registry, else the default; it reads the engine's `ModelContext { model?, models?, agentModel(name) }` provided under the internal `MODEL_CONTEXT` key (`model/constants.ts`) at construction, so `ToolContext` keeps its shape; a string without a resolver is `InvalidAgentDefinitionError` (`resolveModel(): the model string "<ref>" needs a model resolver (EngineOptions.models).`), a tool error in `execute`, and a hand-built context throws `ContextNotProvidedError`.

## Agent state

`createAgentState(agent, schema, store)`: KV (`state.get/set`) plus typed collections declared as `state: Record<name, StandardSchemaV1>` in `defineModelAgent`. `upsert` validates with the collection's Standard Schema, mapped through `@validup/standard-schema` (`ValidationError` with the validup `issues` on failure, nothing stored). With a schema, the model also gets `state_<coll>_list`, `state_<coll>_upsert` and `state_<coll>_remove` tools (`createStateTools(schema)`; chamvi tools reading `context.state`, upsert and remove are effect tools); user tools win on a name clash.

## Testing

Structured instructions: Core `engine/instructions.spec.ts` covers authored mixed-role ordering across model steps, immutable native content/provider options/bytes/URLs, empty/string compatibility, prefix artifact hydration and missing files, fresh-Engine durable approval replay, example tool-call isolation, transcript-only checkpoints, untrusted system checkpoint rejection before pending tools and role-like trigger text. `agent/define.spec.ts` validates outer shapes/roles (including sparse arrays); `exports.spec.ts` checks identity with SDK message/content types. Skills runtime tests cover separate metadata system blocks and frozen/empty contributions while existing catalog/flow tests retain manual string composition. HTTP MCP tests select only nonblank system text and keep the named fallback.

- `core/test/unit/conversation/execution.spec.ts` composes mixed instructions with generic skill contributions, recalled history and fresh-engine approval resume; it checks prefix/catalog order, hydrated tool context and absence of configured blocks/bytes from checkpoints, conversation items and subsequent snapshots.
