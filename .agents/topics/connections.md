# Connections

Read before changing the keyring, the connection repository, vault or config store, a provider built on them (`@chamvi/chat-whatsapp` auth and module, the `tool-mail`, `tool-calendar`, `github` and `chat-discord` modules), the `/connections` routes or the kit's connection components.

A connection is one configured account of a provider, in three tiers: plain settings and write-only secrets (saved from any replica, loaded at the next start) and provider-written runtime entries (WhatsApp's session, held by one process). Connections belong to the app, not to an agent (owner decision 2026-11-06): one `ENCRYPTION_KEYS` per app (every replica and pod of it); per-agent isolation would be a data key per agent wrapped under the same keyring, never a second variable.

- **Keyring** (core `keyring/`): `parseKeyring(value)` reads `<id>:<base64>[,...]` (ids by the agent-name rule, 32-byte keys, the first active), strict padded standard base64 (Buffer's lenient decoder alone would accept garbage); errors name the entry index and never echo input. `seal(key, plaintext, aad)` is AES-256-GCM `iv(12) | ciphertext | tag(16)`; every `open` failure is one `DecryptionFailedError` with a fixed message, a data key under a key id the keyring lacks names that id only. Rejected: `_FILE` and `chamvi.json` forms (the chart mounts no files).
- **Encryption above the repository**: `ConnectionService` (optional, `AppToken.CONNECTION_SERVICE`, `engine.connectionService`) over `IConnectionRepository` holds sealed bytes and the wrapped data key only; sealing lives in the vault. AAD binds each value: entry `<name>\0<key>` (a value moved to another key or connection fails to open), secret `<name>\0secret\0<field>` (entry keys hold no NUL, so a secret is never an entry), data-key wrap `connection:<name>`.
- **Fenced writes**: `writeEntries(name, batch, fence)` validates the whole batch, then the connection (`RepositoryNotFoundError`), then the fence (`LeaseLostError({ lock })`, nothing written), then applies clear, set, delete atomically (a key in both ends deleted). One fence for both drivers, `ConnectionService.assertFence`: the connection row locked, then `IConnectionRepository.findFence(lock)` (the lease row `FOR SHARE` on Postgres, a registry row lock on memory), then the clock; a check before the write transaction would race a takeover between `renew` calls. Entries and secrets are child repositories rebound to the transaction (`bindChild`). The fence must name `connection:<name>` (another lock the owner holds is refused). Shared validation is core `connection/validate.ts`.
- **Lease**: `LockService.renew(key, owner, ttl)` extends a held, unexpired lease only and never recreates one. The vault acquires `connection:<name>` under a per-session owner `<owner>:<uuid>` (no other session, of this process too, passes its fence or is taken for its holder) before it creates the row (only the holder creates it; `recreate` validates the replacement, then swaps it in through the fenced `ConnectionService.replace`, never an unfenced delete: a stalled opener whose lease expired must not wipe the next holder; it recovers an unwrappable key or a type mismatch), refuses a held one with `ConnectionHeldError`, renews once more before `open` returns and then every `floor(ttl / 3)` on the `IClock` (default 60 000, 3 to 2 147 483 647), resolves `lost` for a refused renew, a fence failure, or no confirmed renew before the last confirmed expiry (a throwing renew is retried until then), serializes writes, lets reads wait for earlier writes, and `close` never rejects, keeps renewing until accepted writes settled, zeroes the data key and releases.
- **Settings and secrets** (`createConnectionConfigStore()`, `AppToken.CONNECTION_CONFIGS`): written from any replica **without the lease**, which a session holds for as long as it runs on some replica (rejected: taking it, a dashboard save would fail while WhatsApp is connected). `writeConfig(name, write, { wrappedKey, revision?, generation? })` touches settings, secrets and the revision only, never entries or the data key; the guard on the wrapped key refuses a secret sealed under a key a fenced `recreate` swapped meanwhile, the ones on the revision and the generation a write whose checks read an older state (`ConnectionChangedError`, 409). **Identity** (#199): the generation is the row's uuid v7 id (`Connection.id`, set at insert, never changed); a delete and create restarts the revision, so only the id tells the rows apart (rejected: `createdAt`, a clock going backwards collides). `replace` keeps the id and `createdAt` and bumps the revision (rejected: a new id, a primary-key rewrite or a delete and insert the in-place replace avoids). Settings values are checked in the service for every driver (`assertConnectionSettings`). `update` passes `settings` whole (no merge against a prior read); the PUT requires the `revision` and `generation` of the view the form read (#200), refuses another stored state (409 `connection_changed`, the kit keeps the input and offers a reload) and passes them on, so neither two tabs nor two concurrent saves write past a check the other invalidated. Every row has a wrapped data key (NOT NULL), so `create` always needs the keyring and a save that creates a row without `ENCRYPTION_KEYS` is refused naming the variable; `describe` never unwraps, `read` only with a stored secret. `delete` takes the lease and answers `ConnectionHeldError` while it is held; only stored accounts of a multi-instance type are deletable, and a WhatsApp session goes only through its fenced reset. A PUT changing a `bindsSecrets` field (one deciding where a secret is sent) must carry every stored secret again, else a settings editor could send them to its own host; an env or code secret cannot be re-entered, so the change answers 409 naming the field. A PUT refuses another account's `uniqueId` (409), read from the store, not the last start's list. A secret in both `secrets.set` and `secrets.clear` is 400 (the store clears after it sets); a save that changes nothing writes nothing (no revision, no row). `create`'s config write and the repair of a bare row (`repairBareRow`) both expect revision 0, so of two concurrent creates of one name one answers 409 and the row never mixes them. A `create` whose config write fails leaves the bare row for that repair (rejected: deleting it, unfenced it wipes the entries of a session that took the lease meanwhile).
- **Field resolution** (`resolveConnection()`, one implementation for every module): a code preset, then env or `_FILE` (an empty variable and a list without items are unset; the value coerced once by field kind, an invalid one refused naming the variable, never the value), then the store, recording the source. A required field missing while any field came from env fails the start naming the variable; a store-only gap stays `incomplete` (the app starts, the dashboard can repair it, `start --check` reports it); nothing set is `not_configured` and idle; an unreadable stored row is `failed` (Stored accounts below). **Store-only secrets** (#197): a mail or calendar account that exists only as a row (not listed in its accounts variable) resolves with no variable read, so `CHAMVI_<TYPE>_<ID>_*` and its `_FILE` form are ignored with a warning naming the variable; whoever created the row chose where its secrets go (rejected: refusing the create when a variable matches, the HTTP layer would need each type's variables).
- **Test** (`ConnectionTypeDefinition.test`, `POST /connections/:name/test`; a `DeclaredConnection.test` wins, since one provider serves every module of a type and its definition closes over the first module's options, so github and chat-discord declare each module's own): saved values only, env and code winning for the declaration the row belongs to (the body is never read; a connection that is not `editable` never loads the store, so its row is not read and missing values answer 409), bounded by the request signal and a 30 s deadline on the clock that also ends a test ignoring its signal; only a `ChamviError`'s message reaches the response, with the secrets removed, so a provider throws fixed sentences. `tool-mail` logs in and out without opening a mailbox.
- **Types and identity**: a package contributes `IConnectionTypeProvider` to `AppToken.CONNECTION_TYPES` (`multiple` allows several instances, `uniqueId` guards duplicates). A connection stays addressed by `name` alone, so lease keys, permissions and routes are unchanged; a multi-instance account is stored as `<type>-<account>` (`storedConnectionName()`), since mail and calendar derive the same default ids from one address. Creating needs `chamvi_connection_create` for `{ type }`; editing and deleting need `chamvi_connection_write` for `{ name, type }`, which a creator holds only through its own grants.
- **WhatsApp** (`createStoreWhatsAppAuth()`): entries `creds` and `key:<type>:<id>` (Baileys `BufferJSON`); one `keys.set` is one batch; a reset acquires with `{ reset: true }` (vault `recreate`), so only the lease holder deletes; a reset is refused while `held-elsewhere` or when its acquire is refused as held, and never queues a clear (it would wipe a healthy session once a stale lease expires). Every generation close releases the lease once the admitted writes settled, also after a failed flush or the settle bound (keeping it blocked the next session until the process exited). Held at start: `held-elsewhere`, uncapped backoff retries (the app stays up); other acquire failures: `failed`, capped at `maxAttempts`. A lost lease ends the socket without a flush and waits for the lease again.
- **Pairing material** (the QR) leaves only through the `chamvi_connection_write` API (checked for `{ name, type }`): never a log line, `onError`, error message, run, list entry or `start --check` output. The handle keeps the latest QR only while `pairing`. Write implies read on every route; `chamvi_connection_read` never reaches the QR.
- **Stored accounts**: modules read rows through `readStoredConnections()` (`app/src/module/helpers/connection.ts`), never `configs.read` directly, and resolve them with `resolveStoredConnection()`: a row whose secrets do not open (`DecryptionFailedError`, or stored secrets while `ENCRYPTION_KEYS` is unset) comes back with its settings only and `unreadable`, and degrades only that connection: unless env or code set every unreadable secret it is `failed` (its `reason` the code and fixed message, never a value), used as not configured, a `start --check` issue (exit 2, as `incomplete`), shown until a save waits for a restart; other rows and env accounts keep working (rejected: failing the start, the dashboard that repairs it would be down). A malformed keyring or another read failure still fails the start naming the connection, and a check on a store behind its migrations warns and continues env-only. **Restart to apply**: `restartRequired` is true when the row's revision or generation differs from `DeclaredConnection.loadedRevision`/`loadedGeneration`, since a delete and create again restarts the revision. Such a row (a deletable declaration whose `loadedGeneration` differs from the row's id) is not the declared connection (`isDeleted`): the test, the duplicate check and the rebinding guard see its stored values only, never the env or code values the last start resolved (#197).
- **Modes**: factories and `start --check` acquire no lease and write nothing; a check validates the keyring format only when a module resolves `AppToken.KEYRING`; a job resolves the keyring only to read stored secrets.
- **Handles**: `IConnectionHandle` (core types only) is process-local status, widgets, a change feed and `actions.reset?`; `GET /connections` also lists declared connections and stored accounts, so a replica without the handle still offers configuration (status `disconnected` with `live: false`, which says nothing: the kit reads `state` first, then `configured` for no handle, else the status). `state` is computed from the store per request; `reason` (names options or variables, never a value) is the last start's refusal, shown until a save waits for a restart. `@chamvi/http` serves them (it owns SSE framing and stream limits; `HttpRoute` cannot stream).
- **Dashboard**: `@chamvi/ui` names no provider (rejected: a form or widget per provider in the dashboard). `@chamvi/ui-kit` holds the generic pieces (`ConnectionsPage`, `ConnectionPanel` with a `widgets` slot, `ConnectionForm` rendering a type's fields), a `*-ui` package the provider's page; without one a connection is listed and cannot be edited, and an unpaired WhatsApp session shows no QR. `chat-whatsapp-ui` renders the QR in the browser (`uqr`) to an SVG `data:` URL, never as text. Reset confirms in the page, never a browser dialog.

## Testing

- The port suite runs against memory and Postgres (the fence after expiry, for another owner, a taken-over and a released lock, and another lock of the owner, all writing nothing). The vault runs on a `ControllableClock`.
- `chat-whatsapp/test/unit/auth/kill.spec.ts` SIGKILLs a child writing Baileys-shaped batches to Postgres (`test/fixtures/kill-writer.ts`, preloaded by `kill-hooks.ts`, which compiles workspace sources with swc: jiti cannot load the store-db entities); its suite has a Postgres global setup.
- ui-kit: `test/unit/connections/` (happy-dom for `form.spec.ts`, `panel.spec.ts` and `page.spec.ts`, else Node with SSR); the e2e demos of `ui` and `chat-whatsapp-ui` hold a fake handle (`POST /demo/connect` links it).
