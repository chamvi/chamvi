# Connections

Read before changing the keyring, the connection repository, vault or config store, a provider built on them (`@chamvi/chat-whatsapp` auth and module, the `tool-mail`, `tool-calendar`, `github` and `chat-discord` modules), the `/connections` routes or the kit's connection components.

A connection is one configured account of a provider, in three tiers: plain settings and write-only secrets (saved from any replica, loaded at the next start) and provider-written runtime entries (WhatsApp's session, held by one process). Connections belong to the app, not to an agent (owner decision 2026-11-06): one `CHAMVI_ENCRYPTION_KEYS` per app (every replica and pod of it); per-agent isolation would be a data key per agent wrapped under the same keyring, never a second variable.

- **Keyring** (core `keyring/`): `parseKeyring(value)` reads `<id>:<base64>[,...]` (ids by the agent-name rule, 32-byte keys, the first active), strict padded standard base64 (Buffer's lenient decoder alone would accept garbage); errors name the entry index and never echo input. `seal(key, plaintext, aad)` is AES-256-GCM `iv(12) | ciphertext | tag(16)`; every `open` failure is one `DecryptionFailedError` with a fixed message, a data key under a key id the keyring lacks names that id only. Rejected: `_FILE` and `chamvi.json` forms (the chart mounts no files).
- **Encryption above the repository**: `IStore.connections?` (optional like `conversations`) holds sealed bytes and the wrapped data key only; sealing lives in the vault. AAD binds each value: entry `<name>\0<key>` (a value moved to another key or connection fails to open), secret `<name>\0secret\0<field>` (entry keys hold no NUL, so a secret is never an entry), data-key wrap `connection:<name>`.
- **Fenced writes**: `writeEntries(name, batch, fence)` validates the whole batch, then the connection (`RepositoryNotFoundError`), then the fence (`LeaseLostError({ lock })`, nothing written), then applies clear, set, delete atomically (a key in both ends deleted). Postgres reads the lock row `FOR SHARE` inside the write transaction: a check before it would race a takeover between `renew` calls. The fence must name `connection:<name>` (another lock the owner holds is refused). Shared validation is core `connection/validate.ts`.
- **Lease**: `ILockRepository.renew(key, owner, ttl)` extends a held, unexpired lease only and never recreates one. The vault acquires `connection:<name>` under a per-session owner `<owner>:<uuid>` (no other session, of this process too, passes its fence or is taken for its holder) before it creates the row (only the holder creates it; `recreate` validates the replacement, then swaps it in through the fenced `connections.replace`, never an unfenced delete: a stalled opener whose lease expired must not wipe the next holder; it recovers an unwrappable key or a type mismatch), refuses a held one with `ConnectionHeldError`, renews once more before `open` returns and then every `floor(ttl / 3)` on the `IClock` (default 60 000, 3 to 2 147 483 647), resolves `lost` for a refused renew, a fence failure, or no confirmed renew before the last confirmed expiry (a throwing renew is retried until then), serializes writes, lets reads wait for earlier writes, and `close` never rejects, keeps renewing until accepted writes settled, zeroes the data key and releases.
- **Settings and secrets** (`createConnectionConfigStore()`, `AppToken.CONNECTION_CONFIGS`): written from any replica **without the lease**, which a session holds for as long as it runs on some replica (rejected: taking it, a dashboard save would fail while WhatsApp is connected). `writeConfig(name, write, expectedWrappedKey)` touches settings, secrets and the revision only, never entries or the data key; the guard on the wrapped key refuses a secret sealed under a key a fenced `recreate` swapped meanwhile (`ConnectionChangedError`, 409). `update` passes `settings` whole, last save wins (no merge against a prior read). Every row has a wrapped data key (NOT NULL), so `create` always needs the keyring and a save that creates a row without `CHAMVI_ENCRYPTION_KEYS` is refused naming the variable; `describe` never unwraps, `read` only with a stored secret. `delete` takes the lease and answers `ConnectionHeldError` while it is held; only stored accounts of a multi-instance type are deletable, and a WhatsApp session goes only through its fenced reset.
- **Field resolution** (`resolveConnection()`, one implementation for every module): a code preset, then env or `_FILE` (an empty variable and a list without items are unset; the value coerced once by field kind, an invalid one refused naming the variable, never the value), then the store, recording the source. A required field missing while any field came from env fails the start naming the variable; a store-only gap stays `incomplete` (the app starts, the dashboard can repair it, `start --check` reports it); nothing set is `not_configured` and idle.
- **Types and identity**: a package contributes `IConnectionTypeProvider` to `AppToken.CONNECTION_TYPES` (`multiple` allows several instances, `uniqueId` guards duplicates). A connection stays addressed by `name` alone, so lease keys, permissions and routes are unchanged; a multi-instance account is stored as `<type>-<account>` (`storedConnectionName()`), since mail and calendar derive the same default ids from one address. Creating needs `connections:create` (rejected: `connection:create`, which the read grant `connection:*` would match); editing and deleting need `connection:<name>:write`, which a creator holds only through its own grants.
- **WhatsApp** (`createStoreWhatsAppAuth()`): entries `creds` and `key:<type>:<id>` (Baileys `BufferJSON`); one `keys.set` is one batch; a reset acquires with `{ reset: true }` (vault `recreate`), so only the lease holder deletes; a reset is refused while `held-elsewhere` or when its acquire is refused as held, and never queues a clear (it would wipe a healthy session once a stale lease expires). Every generation close releases the lease once the admitted writes settled, also after a failed flush or the settle bound (keeping it blocked the next session until the process exited). Held at start: `held-elsewhere`, uncapped backoff retries (the app stays up); other acquire failures: `failed`, capped at `maxAttempts`. A lost lease ends the socket without a flush and waits for the lease again.
- **Pairing material** (the QR) leaves only through the `connection:<name>:write` API: never a log line, `onError`, error message, run, list entry or `start --check` output. The handle keeps the latest QR only while `pairing`. Write implies read on every route; `connection:*` matches no `connection:<name>:write` (segment counts).
- **Stored accounts**: modules read rows through `readStoredConnections()` (`app/src/module/helpers.ts`), never `configs.read` directly: an unreadable row (undecryptable, stored secrets without `CHAMVI_ENCRYPTION_KEYS`) fails the start naming the connection, never a value, and a check on a store behind its migrations warns and continues env-only. **Restart to apply**: `restartRequired` is true when the row's revision or `createdAt` differs from `DeclaredConnection.loadedRevision`/`loadedCreatedAt`, since a delete and create again restarts the revision.
- **Modes**: factories and `start --check` acquire no lease and write nothing; a check validates the keyring format only when a module resolves `AppToken.KEYRING`; a job resolves the keyring only to read stored secrets.
- **Handles**: `IConnectionHandle` (core types only) is process-local status, widgets, a change feed and `actions.reset?`; `GET /connections` also lists declared connections and stored accounts, so a replica without the handle still offers configuration (status `disconnected`). `@chamvi/http` serves them (it owns SSE framing and stream limits; `HttpRoute` cannot stream).
- **Dashboard**: `@chamvi/ui` names no provider (rejected: a form or widget per provider in the dashboard). `@chamvi/ui-kit` holds the generic pieces (`ConnectionsPage`, `ConnectionPanel` with a `widgets` slot, `ConnectionForm` rendering a type's fields), a `*-ui` package the provider's page; without one a connection is listed and cannot be edited, and an unpaired WhatsApp session shows no QR. `chat-whatsapp-ui` renders the QR in the browser (`uqr`) to an SVG `data:` URL, never as text. Reset confirms in the page, never a browser dialog.

## Testing

- The repository contract runs against memory and Postgres (the fence after expiry, for another owner, a taken-over and a released lock, and another lock of the owner, all writing nothing). The vault runs on a `ControllableClock`.
- `chat-whatsapp/test/unit/auth/kill.spec.ts` SIGKILLs a child writing Baileys-shaped batches to Postgres (`test/fixtures/kill-writer.ts`, preloaded by `kill-hooks.ts`, which compiles workspace sources with swc: jiti cannot load the store-db entities); its suite has a Postgres global setup.
- ui-kit: `test/unit/connections/` (happy-dom for `form.spec.ts`, `panel.spec.ts` and `page.spec.ts`, else Node with SSR); the e2e demos of `ui` and `chat-whatsapp-ui` hold a fake handle (`POST /demo/connect` links it).
