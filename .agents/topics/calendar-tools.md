# Calendar Tools

Read before changing `@chamvi/tool-calendar`.

`@chamvi/tool-calendar` holds two factories and `toolCalendarModule()` on `/module`. `calendarTools({ accounts?, client?, timezone?, timeoutMs?, fetch?, clock? })` returns two plain read-only `defineTool()` tools (`calendar_list`, `calendar_events`) over one `ICalendarClient` (`createCalendarClient(accounts, options)`). `calendarWriteTools({ accounts?, client?, timezone?, timeoutMs?, fetch?, clock?, classifier?, createLimit?, deleteLimit?, calendars? })` returns `calendar_create` and `calendar_delete` over a separate `ICalendarWriteClient` (`createCalendarWriteClient()`); an app that registers both gets two clients on the engine. It peers on core and `ai` (optional peer on app) and depends on `tsdav`, `ical.js` and `smob`, pinned to exact versions; times use Node 26's `Temporal`. Options are checked when called (`InvalidAgentDefinitionError`, never echoing a password); `accounts` and `client` together are refused.

## Invariants

- **The read client is read-only on the wire.** Every request goes through `guardedFetch()` (`client/guard.ts`) around the given or global `fetch`: only `CALENDAR_ALLOWED_METHODS` (`PROPFIND`, `REPORT`, `GET`) pass, any other method (also a `Request`'s own) throws a `calendar_request` error before anything is sent. tsdav gets this fetch for its login and every call; never hand it the raw fetch. Proven by `test/unit/client/methods.spec.ts` (the recorded methods of a full list and events call, the guard on its own).
- **Write client** (`write-client/`, never the read client): `writeGuardedFetch()` (`guard.ts`) lets only `CALENDAR_WRITE_ALLOWED_METHODS` (`PROPFIND` for login, discovery and calendar user addresses; `GET` for the backup, the ETag check and the replay lookup; `PUT`; `DELETE`) pass, never `REPORT`. A `PUT` must carry `If-None-Match: *` and no `If-Match`; a `DELETE` must carry `If-Match` with one version, never `*` or a list. Both are sent with `redirect: 'manual'` (a redirected write is `request failed`; discovery's `PROPFIND`/`GET` still follow redirects, as on the read side). A resource URL (`resourceUrlOf()`, `resource.ts`) is a name directly inside a listed VEVENT calendar's collection: names with `/`, `\`, `?`, `#`, control characters, `.`/`..` or percent-encoded `%2F`, `%5C`, `%2E` are refused before any request, and the URL must come back unchanged from URL parsing. An event id's ETag must be one concrete version (no `*`, no comma, no control character). The client trusts the calendar hrefs the server returns and discovery follows redirects, with the trust of the read side (the origin is not pinned). Proven by `test/unit/write-client/methods.spec.ts`: only `PROPFIND`, `GET`, `PUT`, `DELETE` over the whole file.
- **Event ids** (`event-id/`, internal): each `calendar_events` event carries `id` (the calendar id, resource name and ETag, round-trip checked) when its resource is a direct child of the calendar and has an ETag; otherwise it has none and cannot be deleted. Adding it needs no new read request.
- **Create** (`write-tools/create.ts`, `write-client/create.ts`, `ics.ts`): an effect tool. The UID (`<hash>@chamvi`) and the resource name (`chamvi-<hash>.ics`) derive from the effect key (sha256), not random: only that lets a replay find the resource. `PUT` with `If-None-Match: *`; any 2xx is created, and nothing throws after it (a missing ETag costs one swallowed `GET`). `412` is read with a `GET`: our UID is the replay, any other is `request failed`; `alreadyApplied` is `findCreated()` (`GET`). The wire has UTC date-times or plain dates and no `TZID` (no `VTIMEZONE` can be built from an IANA id); the configured zone governs input without an offset, approvals and results. Text values have CR and CRLF turned into LF before ical.js escapes them. Addresses are printable ASCII (`CALENDAR_ADDRESS_PATTERN`), validated in the tool and again in the client. The organizer is the first `mailto:` of the principal's calendar user addresses, else the user when it is an address; attendees without one are refused. With attendees the call always asks, showing `From: <organizer>`, every attendee and the whole description (`--- description ---`); without attendees it runs unapproved. Every create, with or without attendees, counts in its own limit (`createLimit`, default 20 an hour, bucket `creates`, `onExceed: 'approve'`); its detail is the create body and records through `once(ctx, 'calendar_create:limit-shown')` whether it showed the whole invitation (organizer known), and `execute` skips the invitation approval only when `toolLimitApproved(ctx)` and that record is true. Accepted: a create without attendees in a calendar shared with other people is visible to its members; `calendars` narrows where the tools write.
- **Delete** (`write-tools/delete.ts`, `classify.ts`, `limit.ts`): an effect tool. The limit runs first, in the effect wrapper before `execute` (`deleteLimit`, default 20 an hour, bucket `deletes`, weight 1, `onExceed: 'approve'`); then `execute`: parse the id and check the allowlist (no request), `describe` (`GET`), a changed ETag refuses, a repeating event without `series: true` refuses (a series is deleted whole or not at all and always asks, never reaching the classifier), the verdict, the approval, the backup, `DELETE` with `If-Match`. A call counts once it passed the limit, also when `execute` then refuses it (a changed ETag, a missing `series`, a calendar outside `calendars`, a malformed id or create input) or the approval is denied. The limit's `detail` records the listing it showed and its text through `once(ctx, 'calendar_delete:limit-listing')` (a detail asked again in the call shows the recorded text), and `execute` skips verdict and approval only when `toolLimitApproved(ctx)` and the record covers the event (an agent `limits.calendar_delete` entry replaces the limit whole and records none, so its approved calls still take the verdict path). The verdict (`deleteVerdictOf()`, through `once(ctx, 'calendar_delete:classify')`) asks without a model call when the event repeats, has another attendee or a foreign organizer (the listing then names them, at most 20 addresses, and says the server may notify them), lies in a calendar someone else shares with the account (read again for each delete, one Depth 0 `PROPFIND`, never discovery's cache: CalendarServer `shared`, not `shared-owner`, or a `DAV:owner` whose origin and path differ from the principal's; a failed read counts as shared), or has not ended; only the owner's own ended one-person events in its own calendars reach the classifier (`extract()`, title, times and attendee count only; any failure or timeout is `ask`). Approvals go to the source chat only when `await handle.direct()` is true, else to the inbox and API only. The backup is an artifact (`once(ctx, 'calendar_delete:backup')`, keyed `calendar_delete:<hash>`, `text/calendar`, the `GET` bytes) saved before the `DELETE`, and its id is in the result; restoring is a manual import. `DELETE` `404` is `missing` (`deleted` when this call's own backup is recorded), `412` is the changed refusal. Accepted: a server that sends weak ETags (`W/"..."`) makes every delete refuse as changed (`If-Match` compares strongly): it fails closed. A server that reports neither sharing nor an owner makes a shared calendar count as the account's own.
- **Setup and the bucket coupling.** `calendarWriteTools()` needs `engine.limitService` because both tools carry a default limit, unless `createLimit` and `deleteLimit` are `false` or the agent sets `limits: { calendar_create: false }` and `{ calendar_delete: false }`. `calendar_delete` and `mail_delete` share the bucket `deletes`: an agent that binds both needs equal `deleteLimit` settings, else core fails the run when the tools are bound, not at the factory. `calendars` is a list of calendar ids the tools may write to (default every listed calendar); a create or delete elsewhere is a `ValidationError` before any request.
- **Calendar ids**: `<account>:<last path segment of the calendar URL>`. Only calendars whose components include `VEVENT` are listed (reminder lists skipped), once per session. An unknown account prefix or calendar is a `ValidationError`.
- **Expansion here, not on the server** (`expand/module.ts`): `fetchCalendarObjects` with the time range and `useMultiGet: false`, then `expandEvents()` per resource with ical.js. Recurring events iterate from DTSTART with EXDATE and RECURRENCE-ID exceptions (a moved occurrence replaces its slot; a CANCELLED one is kept with `status`), stopping at `to` or after `CALENDAR_EXPAND_MAX_ITERATIONS` (10 000) iterations per event. An exception without its master is a single event. A resource that is no iCalendar is skipped. An event is in range when it ends after `from` and starts before `to`.
- **Zones**: every time is read and printed in the configured zone (`timezone`, default `CALENDAR_DEFAULT_TIMEZONE` `Europe/Berlin`; an IANA id or `UTC`), never the process zone. `instantOf()`: a date is midnight in the zone; a TZID ical.js resolved from a VTIMEZONE, or a floating time whose TZID is an IANA id, is read in that zone; a non-IANA VTIMEZONE keeps its own rules; any other floating time is read in the configured zone. Timed events give ISO with the zone's offset, all-day events plain dates, `end` exclusive (a derived end, from DURATION or none, uses the start's zone). The expand spec runs with `TZ=America/New_York`.
- **Caps**: `from`/`to` at most `CALENDAR_RANGE_MAX_DAYS` (92) apart, `to` after `from` (a date is midnight in the zone); `limit` default `CALENDAR_EVENTS_DEFAULT_LIMIT` (100), at most `CALENDAR_EVENTS_MAX_LIMIT` (500), `truncated` when more matched; `description` cut at `CALENDAR_DESCRIPTION_MAX_CHARS` (2 000), `title`, `location` and `organizer` at `CALENDAR_FIELD_MAX_CHARS` (500; every occurrence of a recurring invite repeats them), never inside a surrogate pair. Events across accounts are sorted by start (all-day first, then uid). `attendees` is `{ count, self? }`, `self` the PARTSTAT of the attendee whose address is the account user.
- **Sessions and errors** (`client/module.ts`): one tsdav session per account, logged in on first use (Basic auth); a failed login, or one cut by the timeout or a cancel, is not reused. `request()` races each account's call against `timeoutMs` (default `CALENDAR_TIMEOUT_MS` 30 s) on the `IClock` and the run's signal. A failure that is not a `ChamviError` becomes code `calendar_request` (`CALENDAR_REQUEST_ERROR_CODE`) with the message `<tool>: <account>: request failed` (or `timed out`): tsdav's messages can carry URLs and server text, so they are dropped. `close()` forgets the sessions.
- **Trust**: both tools taint (calendar names and invites come from other people; `taintOf(client)` is `false` only for the unconfigured client's `configured: false`, which reads nothing) and end their description with `UNTRUSTED_NOTE`.
- **Env contract** (`module/helpers.ts`, read when `toolCalendarModule()` is called): `CHAMVI_CALENDAR_ACCOUNTS` (`CALENDAR_ACCOUNTS_VARIABLE`) is a JSON array of `{ id?, url, address? }`; `id` defaults to the address with `@` and `.` as `-` and is required without one; `url` http(s); credentials `CHAMVI_CALENDAR_<ID>_USER` (default the address) and `CHAMVI_CALENDAR_<ID>_PASSWORD` (each in env or the store: checked in `setup`, missing from both fails naming the variable, never at the factory), `<ID>` upper-cased with `-` as `_` (colliding ids refused), each also as `<name>_FILE` (one trailing newline trimmed; both set is an error). `CHAMVI_CALENDAR_TIMEZONE` wins over the `timezone` option. Errors name the variable and index, never a value. In `setup` (`module/type.ts`) stored rows of type `calendar` named `calendar-<id>` are added and merged per field through `resolveConnection`, with the rules of [mail-tools.md](mail-tools.md) (a stored-only account reads no `CHAMVI_CALENDAR_<ID>_*` variable, #197); `uniqueId` is URL and user (one CalDAV URL serves many users). No accounts: the context stays provided and each tool fails with `connection_not_configured` (`calendarTools()` outside the module still fails with `context_not_provided`). Migrate mode does nothing; the client closes on `drained` and in `teardown`.
- **Privacy**: the package has no access control of its own. Events land in the run's steps and checkpoints and shape the model's answer, so whoever reads the agent's runs reads the calendar; such agents should be `private: true` (only `agent:<name>:read` reads them), as the README and examples show. Credentials never reach a tool input, a result, an error or a log.

## Testing

- No test reaches a real server. `createFakeCalDav()` (`test/utils/caldav.ts`) is a CalDAV server behind a `fetch` in the iCloud shape (`.well-known` redirect to a partition host, principal, an absolute calendar home with `:443`, `supported-report-set`, `calendar-query` REPORTs), recording every request (`requests`: method, url, depth, authorization); `hang` and `status` drive the timeout (on a `ControllableClock`) and the 401 tests. `calendar()`, `vevent()`, `BERLIN_VTIMEZONE` and `weeklyStandup()` (`test/utils/ics.ts`) build iCalendar text; `toolContext()`/`callTool()` (`test/utils/tools.ts`) call the tools as the AI SDK does.
- `createFakeCalDav()` also answers `PUT` (`412` on an existing name with `If-None-Match: *`; `putEtag: false` for no ETag), `DELETE` (`404` when absent, `412` on another `If-Match`) and object `GET`; `addresses` sets the calendar user addresses, `fail` and `before` inject a failure or a change between two requests, `writes` records the stored bodies. `createWriteEngine()` (`test/utils/engine.ts`) runs `calendarWriteTools()` on an engine with a limit service and a scripted chat source.
