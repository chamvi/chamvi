# Knowledge

Read before changing `@chamvi/knowledge`.

Reference material an agent searches by meaning through an explicit tool, never put into the model context. The boundary (docs `guide/knowledge.md`, first section): a skill is followed (procedures, loaded whole by name), knowledge is looked up (facts, a few passages by meaning), conversation memory is what was said in one chat. Knowledge never contributes system instructions, never reads or writes conversation data and reuses no skills or memory vocabulary. Core gains no knowledge or vector concept; `@chamvi/store-db`'s chain and tables are untouched; neither app nor test-kit depends on the package.

- **Embeddings**: `IModelResolver.embedding?(ref): EmbeddingModel` (core, optional, generic) is implemented by the app's resolver (`createModelResolver`: the same `providerOf(ref)` path as `resolve()`, so `models` overrides, unconfigured providers and missing packages behave alike; a throwing `embeddingModel(id)` becomes `Provider "<p>" offers no embedding model "<id>".`). The engine module registers its resolver as `AppToken.MODELS` in `setup` (start, job and check; nothing in migrate). A collection's stored model identity is the string ref, or `<provider>/<modelId>` for an object; vectors of two models never mix. Embedding is the AI SDK's `embedMany` (`maxRetries: 0`, the indexer's backoff retries), 64 values per call (`EMBED_BATCH_SIZE`).
- **Contract** (`store/types.ts`, `service/`): the ports live in knowledge (they name knowledge concepts, so never in `@chamvi/store`) on `@chamvi/store`'s generic port (#231 layering): the root `IKnowledgeCollectionRepository` (`KnowledgeCollectionRecord`: the collection plus its row `id`, a uuid v7 given at creation, and `fence`; `name` unique) with the children `documents` (`(collectionId, id)` unique) and `chunks` (`(collectionId, document, generation, index)` unique, referencing the collection only: chunks may precede their document record; the one finder `search`, cosine over vectors of the query's length only) bound to its transaction. `KnowledgeService({ repository, clock })` holds every rule (choice of error, timestamps from the clock; text sanitizing is the repository's) and is the only caller of the repositories (indexer, managed pass, tools, routes, `IKnowledge.service`): collections (`saveCollection` upsert keeping row id and fence, `advanceFence`, `findOneCollection(OrFail)`, `findCollections` in code-point order, `deleteCollection` with its documents and chunks), documents (`status` `pending | ready | failed`, `saveDocument`, `findOneDocument(OrFail)`, `findDocumentIds`, `findDocuments` (status filter, id code-point order, `total` before paging), `updateDocument(collection, id, version, patch)` (writes only while the stored hash, title and source match, atomic), `updateDetails` and `requeueGeneration` (see Managed collections), `deleteDocument` with every generation's chunks), `replaceChunks(collection, document, generation, chunks)` (atomic per document and generation; `[]` removes them), `deleteGeneration`, `deleteGenerationsExcept(collection, generation)`, `search(collection, generation, vector, { topK, minScore? })` (descending, ties by document id then chunk index, `[]` for an unknown collection, with the chunk's own copy of `title`/`source`, never the document record's: a replaced document never shows new details next to old text, so the declared sync re-writes a document's chunks when its title or source changes). Values copied in and out; a document or chunk of an unknown collection is `repository_not_found`. `describeKnowledgeRepositoryContract({ name, create })` (test-kit, structural types) takes a factory of the service over fresh repositories (test-kit cannot import knowledge) and runs every backend; `mockEmbeddingModel()` is a hashed bag of words.
- **Fence**: every pass write carries `{ fence: { id, fence } }` (`KnowledgeWriteOptions`) and, in one transaction, locks the collection row first: missing is `RepositoryNotFoundError`, another row `id` or counter is `LeaseLostError({ lock: 'knowledge:<name>' })` with nothing written (so a delete and a pass serialize and nothing is resurrected; rejected: checking the lock row itself, since the lock and the vectors may live in different backends). Every `advanceFence(name)` directly follows a successful renew (or acquire) of the lock and is directly followed by another renew; a failed one ends the pass or mark with no write, so a holder stalled past its lease never writes with the newer token it took (accepted cost: the current owner's next fenced write is `LeaseLostError` and it loses one pass, #247); a pass calls it right after acquiring the lock; a declared collection's first pass saves its record `{ create: true }` (insert only: a row another owner created is `LeaseLostError`), then advances and ends when the token is not the created row's (deleted or re-created meanwhile); `markOrphans()` and the failure record advance before writing too. The fence is no field of `KnowledgeCollection`: only `advanceFence` writes it, so saving an old read never rolls it back. API writes (`createCollection`, `deleteCollection`, `putDocument`, `deleteDocument`, `updateDetails`) lock the row and skip the compare. `runCollection` and the managed loop treat `LeaseLostError` like a lost lock: the pass ends, no `onError`, no stored failure, no backoff.
- **Declared collections**: `knowledgeCollection(name, { model, sources, trusted?, resyncMs? })` (agent-name rule, at least one source; `trusted` defaults to every source trusted; `resyncMs` a safe integer from `KNOWLEDGE_RESYNC_MIN_MS` 60 s to 2 147 483 647, the longest Node timer), declared at app level only (`knowledgeModule({ collections })` or `createKnowledge({ collections })`); agents name what they search. `createKnowledge()` checks everything when called (`InvalidAgentDefinitionError`: a name twice, a string model without a resolver or one `embedding()` refuses, prefixed `Knowledge collection "<n>": `). Sources: `folder(path)` (Markdown and text, sorted; a walk one directory at a time that never enters a symbolic link (a link to a file or a directory is reported and skipped, so no escape or loop), dot entries skipped, an unlistable subdirectory, files over 1 MiB and non-UTF-8 files reported and skipped, `O_NOFOLLOW`; a path that is no directory fails its `check()`) and `defineKnowledgeSource()` (each yielded item checked, an invalid one reported by id and skipped; an optional `check()` kept). `IKnowledgeSource.check?()` validates configuration without reading documents; `IKnowledge.check()` runs every source's (prefixed with the collection), so a missing folder fails the boot and `start --check`. Chunker `text-v1` (`chunkText`): blank-line blocks packed greedily to 2000 characters, a heading kept with the next block, ~200 characters of word-aligned overlap, never a cut high surrogate; `contentHash` is `sha256:<hex>`.
- **Generations and sync** (`indexer/`, internal): a collection serves one `generation` (0 = never indexed) at one model and chunker; `pending` holds a re-embed's target. `syncCollection` writes into the served generation when it matches the definition, else into the matching pending one, else into a new one numbered past `lastGeneration` (a number is never given out twice: documents of an abandoned generation still name it), status `stale` while a generation is served, `pending` before the first; an unchanged hash at the target generation costs nothing (a restart with unchanged sources makes no embedding call); per changed document it chunks, embeds, renews the lock again (a lease lost while embedding ends the sync before any write), `replaceChunks`, then `saveDocument`; documents the sources do not yield any more are deleted, unless a source called `ctx.incomplete(reason)` (`folder()`: an unlistable subdirectory, a file read error; never a permanent skip): then nothing is deleted (reported once), and a re-embed fails with a `ValidationError` (retried on the backoff) instead of switching; a re-embed then switches the served generation (dropping the previous model's `dimensions`) and deletes the old one; a sync at the served generation deletes every other generation (`deleteGenerationsExcept`: an abandoned re-embed, or what a crash between a switch and its cleanup left). The record's `trusted` is written conservatively at the start (`stored.trusted && definition.trusted`: a downgrade at once) and the definition's value only in the final save, after the sources' documents were replaced and the stale ones deleted. Duplicate ids across sources keep the first. A `managed` record of a declared name is refused (`managedNameError()`); `check()` (read-only) refuses it at boot.
- **Lock and loop**: one loop per declared collection runs a pass (`syncCollection`; its final save writes `syncedAt`) under the store lock `knowledge:<name>`, then idles on its wake (`createWake()`: a `notify()` while nobody waits is kept, so `IKnowledge.sync(name)` calls coalesce; cleared when a pass starts, so a call during a pass queues exactly one more) or `resyncMs`, reading its record every `KNOWLEDGE_MANAGED_POLL_MS` (`checkMs`): a record deleted elsewhere (an older replica marked it orphaned) runs a pass whatever `resyncMs` says (#120; rejected: refusing the delete while a declaring replica may hold the lock), so does one no pass completed yet (no `syncedAt`: a failed rebuild is retried after its `retryAt`), an existing synced one costs that read, no lock. An interval pass is skipped while the stored `syncedAt` is younger than `resyncMs`, checked before the acquire and again under the lock, so replicas run one pass per interval in total; a wake always runs one, after any stored `retryAt`. `sync()` is an `InvalidRunStateError` while not started and a `ValidationError` for a name without a loop here. The lock: `KNOWLEDGE_LOCK_TTL_MS` 300 s, renewed by release and re-acquire after half of it; a lock another owner took ends the sync without an error. A loser (and a sync whose lock was lost) waits `KNOWLEDGE_RETRY_MS` 5 s on the `IClock` and tries the lock again, so every replica syncs its own sources once it is free (unchanged hashes embed nothing). A failure is stored on the declared record (still under the lock) with `failures` and `retryAt` (5 s doubling per failure in a row to `KNOWLEDGE_RETRY_MAX_MS` 300 s), reported through `onError(error, { collection })`; every replica's loop waits until `retryAt` before acquiring (re-checked after the acquire), except on its own first attempt, so the backoff is per collection, not per replica; a success clears both. A store failure that left no `retryAt` falls back to the loop's own backoff. An `InvalidAgentDefinitionError` (by code) is stored and reported once and ends the loop, whose wake is then dropped, so `sync()` (and REST `.../sync`) refuses it instead of accepting a pass that never runs. Each indexing `embedMany` call is raced against `KNOWLEDGE_EMBED_TIMEOUT_MS` 60 s on the `IClock` (aborted, `ChamviError` `knowledge_request`), so a stalled provider is a reported, retried failure well inside the lock lease. A throwing `onError` is contained (`console.error`). `start()` also marks declared records without a definition `orphaned` (kept, searchable by no agent; a re-declared name re-syncs), each under its `knowledge:<name>` lock (held elsewhere: left alone) and re-read once held. `stop()` aborts and awaits every loop; a `start()` meanwhile begins once they settled.
- **Managed collections** (`IKnowledge.createCollection/deleteCollection/putDocument/deleteDocument/view`, `managed/`): always `trusted: false` (no option makes one trusted: a `chamvi_knowledge_write` holder must not launder content); the search taint and `view()` treat `kind: 'managed'` as untrusted whatever the stored `trusted` says. `KnowledgeOptions.embeddingModel` is their model, resolved in `createKnowledge()` like a declared one; without it `createCollection` is an `InvalidRunStateError`. `createCollection` checks and saves under the lock `knowledge:<name>` with an owner of its own (never releasing a lock this instance's loop holds); a declared name here or any stored record is refused (the save is `{ create: true }`, so a record created after the check is the same refusal, never replaced). `putDocument` stores changed content `pending` (the old chunks keep serving) and wakes the local loop; unchanged content and details answer `changed: false`; new details of unchanged content (metadata, and title/source of a `ready` document) are one `updateDetails` (version- and status-checked, so a document failed since the read is decided again, one transaction: the document's title, source and metadata and for a `ready` document its chunks' title/source of its own `generation` only (another generation's chunks, e.g. a re-embed's served old text, and a pending document's served chunks hold older content and keep their details: new details never next to old text, old details next to the same text are accepted while pending); #124; never a re-embed), re-read and decided again when the version moved: never an unversioned write of details after a versioned one (a racing PUT would leave the document and its chunks disagreeing for good). A `pending` document with a new title or source is stored `pending` again. Status is per document; `stale` is computed by `view()` (another default model or chunker) and never stored. The pass (`syncManaged`) never writes the record except in a re-embed, which runs only on `sync(name)` (or to finish the re-embed the record names as `pending`), or to abandon a `pending` re-embed whose model or chunker is not the default (#123: first `requeueGeneration` sets that generation's documents `pending` at the served one, a page per transaction (never the whole generation under the row lock), then `deleteGeneration`, then `pending` cleared, so a pass ending in between repeats it; clearing alone would leave documents `ready` without served chunks), re-reading the record before every record write; a stale record whose served model is not available keeps documents pending. Per pending document (id order) it embeds, renews the lock, re-reads the collection (same `createdAt`, so a delete or re-create during the pass writes nothing back) and the document, then `replaceChunks` with the stored title/source and `updateDocument(…, { hash, title, source }, …)`: new content PUT during the embedding leaves the new version `pending` for the next round; new details only (also an `updateDetails` during a re-embed) have the chunks written again under them until the ready write's version matches, so neither the old content nor the old title/source is ever `ready` under the new version (a skip would lose a `ready` document at the re-embed's switch). A provider rejection (`APICallError` 400, 413 or 422; a 401/403 key or 404 model problem fails the pass) marks the document `failed` and removes its chunks of that generation; any other error fails the pass (the loop's own backoff: a failure is never stored on a managed record). Loops: `managedPoll` (a hubwire interval component, run by `start()`/`stop()` unless `runManagedPoll: false`; idle while not indexing) polls `findCollections()` at once and every `KNOWLEDGE_MANAGED_POLL_MS` 60 s, starting a loop (idle 60 s) per managed record and stopping loops of vanished ones; `createCollection` starts its loop at once, `deleteCollection` aborts it.
- **Search and taint** (`tools/`): `knowledgeTools({ collections, topK?, minScore? })` gives `knowledge_search({ query, collection?, topK? })`, a plain `defineTool()` reaching the knowledge through the context pair. A collection outside the options, and an orphaned or `declared` record this app does not declare, is refused before any read or embedding (an orphaned record of a name this app declares is served: an older replica of a rolling deploy may have marked it); a missing record or generation 0 is `ValidationError` `Knowledge collection "<n>" is not ready.` (never empty results). Every served model is resolved first through `IKnowledge.embedding()`; one that does not resolve is a `ValidationError` naming the collection (during a re-embed: `... is being re-embedded; its previous model "<id>" is not available here, ...`: an object model the definition dropped, or a removed provider, leaves the served generation unsearchable until the switch). The query is embedded once per model, each collection searched at its served generation, merged by score (ties: collection, document, chunk index), cut to `topK` (default 5, max 20) and at whole matches past 20 000 characters (`truncated`). `trust.taint` is a predicate: a search over any collection untrusted by its record or its declaration, or without a record unless this app declares it trusted (that one only answers "not ready"), taints the run `tool:knowledge_search`; the predicate's answer is kept per input object, and after the searches every record is read again: a changed `generation`, or a collection untrusted now that the call was not tainted for, is a `ValidationError` `Knowledge collection "<n>" changed while it was searched; search again.` instead of a result; checkpoints and replay apply as for any tool.
- **REST** (`routes/`, main entry, `knowledgeRoutes(knowledge)`): `@chamvi/http` is an optional peer used by `import type` only (as `@chamvi/ui`), so `dist/index.mjs` stays http-free and a standalone `createHttpApp({ routes })` can mount them. One `prefix: true` route per method on `/knowledge`; every handler calls `request.authorize()` first (`Permission.KNOWLEDGE_READ` of `@chamvi/access` for `GET`, `KNOWLEDGE_WRITE` else; `{ name }` when the path names one collection, else a `canSome` gate whose listing keeps rows passing `can` and whose create re-checks the body's `name`), before reading the body, then dispatches on the subpath split at raw `/` and each segment `decodeURIComponent`d once (an encoded `/` stays in a document id; a bad escape is 400). Views go through `IKnowledge.view()` (`stale` never stored); `sync()`'s `ValidationError` (no loop here) answers 404; errors map by core code (400/404/409).
- **Module** (`/module`, `knowledgeModule({ collections?, repository?, owner?, embeddingModel?, env?, routes? })`, name `chamvi:knowledge`, dependencies config, store, engine, optional `chamvi:knowledge-repository`): options checked and `CHAMVI_KNOWLEDGE_MODEL` (wins over `embeddingModel`) read when called; `setup` (not in migrate) builds `createKnowledge()` over the repository (the `repository` option, else the one a backend module registered under `KnowledgeToken.REPOSITORY`, an eldin token created in `/module` only, else memory with `MEMORY_KNOWLEDGE_WARNING` outside dev; the backend takes the module name `KNOWLEDGE_REPOSITORY_MODULE_NAME`, so it sets up first and a second one is a duplicate module), the app's lock service, resolver, clock and logger; a configuration error fails the setup (`assertEnvModel()`: an unresolvable variable is named, its value never echoed); in start mode outside a check, unless `routes: false`, it registers `knowledgeRoutes()` on `AppToken.HTTP_ROUTES`. `onReady` runs `check()` (also in a check). The lifecycle hook provides the context in `engineCreated`; in start mode outside a check only, the module contributes `knowledge-managed` (`runManagedPoll: false`; its start runs `start()` first and never awaits the poll's first pass, so the app start and the listen never wait on the repository: the components start before the `started` hooks) and `stopping` awaits `stop()`; `teardown` stops too. A job or a check never indexes and serves no routes.
- **pgvector** (`@chamvi/store-db-vector`, see [store.md](store.md)): `vectorStoreModule()` is that backend. Search is exact (no ANN index: tens of thousands of chunks per collection; rejected for now: an HNSW index per collection, a follow-up), filtered by `vector_dims` so a mixed-length collection never throws. It sanitizes text on write (NUL, lone surrogates to U+FFFD); knowledge applies the same replacement to every document where it enters (`storedDocument()`: a source's yield in `syncCollection`, `putDocument`), so all backends hold the same text and a document compares equal to its next yield (rejected: comparing through the replacement while memory keeps the raw text, which lost a NUL-to-U+FFFD edit there). A memory lock store beside a shared vector database is single-replica: each process's locks are its own, so replicas fence each other out (no module check).
- **Downstream contract**: `CHAMVI_KNOWLEDGE_MODEL` (optional, read only by `knowledgeModule()`) and the routes under `<basePath>/knowledge` are part of the env and route contract checked against chamvi/helm (carried by the chart's generic `env` map; no owned variable) and chamvi/agent-template (no knowledge usage); see both reference maps. `AppToken.MODELS` is additive app API neither repository uses.

## Testing

- `@chamvi/knowledge` tests never reach an embedding provider: `mockEmbeddingModel()` from `@chamvi/test-kit` is a hashed bag of words (64 dimensions by default, normalized; `calls` records every `doEmbed` call's values). `KnowledgeService` over the memory repositories runs `describeKnowledgeRepositoryContract()` (`test/unit/store/memory.spec.ts`), which every knowledge backend must pass. `test/utils/indexer.ts` holds `createIndexerSetup()` (a `ControllableClock`, a `KnowledgeService` over memory repositories, recording locks over a `createTestEngine()` lock service, collected `onError` calls), `mapSource()` (a source over a mutable map), `embeddingResolver()`, `gatedModel()` (embedding calls that block until opened, rejecting on abort), `waitForCollection()`/`waitForReady()`; `test/utils/tools.ts` holds `toolContext()` (a `ToolContext` with the knowledge bound as the engine would), `callTool()` and `seedCollection()` (a record with documents and chunks written straight through the service). Indexer timing (backoff, lock renewal, the embed timeout) is driven by advancing the `ControllableClock`; tests that move the clock past `KNOWLEDGE_EMBED_TIMEOUT_MS` while an embedding call is open hold the source between documents instead. The trust regressions drive a real `Engine` with `mockModel` (`test/unit/tools/trust.spec.ts`); the module spec runs on `buildModuleHarness()`/`createModuleHarness()` from `@chamvi/app/testing` and asserts the registered `chamvi:knowledge` lifecycle hook instead of waiting on real timers. The route spec mounts `knowledgeRoutes()` on a real `createHttpApp()` with `staticTokens()` and sends requests through `app.fetch`. The folder specs use real temporary directories (symbolic links, a `chmod 000` subdirectory, skipped as root).
