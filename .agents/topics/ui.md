# UI

Read before changing `@chamvi/ui` (serving, SPA, approvals), `@chamvi/ui-kit` (shell, API, auth, connection components) or a `*-ui` page.

`@chamvi/ui` is the dashboard: a Vue 3 + vuecs SPA (`app/`, Vite root, built to `dist/app`) and a Node entry (`src/`, tsdown) with `uiRoutes()`. It peers on core (its `InvalidAgentDefinitionError`) and http (the static helpers of `http/src/static/` and types); `@chamvi/http` never imports it. Every SPA library is a bundled devDependency; the SPA imports core and http types only, never their runtime. It names no provider.

`@chamvi/ui-kit` is what the dashboard and every `*-ui` page build on (API client, session, `AppShell`, connection components, `mountPage()`, and `/vite`'s `definePageConfig()` with Tailwind, the Vue plugin and the bundled Lucide icons); a page bundles it at build time, so nothing but the built page reaches the app. The five pages `tool-mail-ui`, `tool-calendar-ui`, `github-ui`, `chat-discord-ui` and `chat-whatsapp-ui` each hold `app/` (Vite root, built to `dist/app`) and `src/module/` (`<name>UiModule({ uiBase? })` over `uiPageModule()`, [app.md](app.md)); their only peer is the optional `@chamvi/app`.

- **Pages** (`/ui/ext/<slug>`): separate builds under the same `script-src 'self'` CSP, with no shared Vue at runtime; one origin and one `sessionStorage`, so nobody signs in twice. A page's `uiBase` must equal `uiModule({ basePath })`: nothing checks it, and a mismatch serves the page under another path while `config.uiBase` sends sign-in to a path the dashboard does not answer. A signed-out page goes to `<uiBase>/login?redirect=<its path>`, validated by `safeReturnPath` (it allows `<uiBase>/ext/*`). A sidebar item shows when `GET /connections` lists a connection of one of its `types` or the session is allowed the name `chamvi_connection_create` (`visibleUiPages`, synchronous over `session.allowed`). `ConnectionPanel` treats the caller as a writer of a connection only when the name `chamvi_connection_write` is allowed and `GET /connections/:name` sent the writer-only `widgets`; otherwise it polls as a reader and never opens the stream.

- **Serving** (`src/routes/`): `uiRoutes({ basePath? = '/ui', auth?: { tokens? = true, authup? }, root? })` returns an `HttpRoute[]` holding one route (`GET`, `prefix: true`, `rateLimit: false`, unauthenticated), spread into `createHttpApp({ routes })`. `resolveBuildPath(subpath)` decodes the raw subpath once and refuses a decode failure, NUL, backslash, `%` left after decoding (double encoding), a `.`/`..` or empty segment (one trailing `/` allowed), answering 404 (`{ status, code: 'not_found', message }`). `ext` and `ext/*` answer 404 here (the registered `*-ui` pages' own routes answer first; the dashboard's fallback must never swallow them). `''`, `index.html` or any unknown path without an extension in its last segment answers the rendered `index.html` (`DOCUMENT_CACHE_CONTROL` `no-cache`); a build file its bytes (`ASSET_CACHE_CONTROL` `public, max-age=31536000, immutable` under `assets/`, else `no-cache`); anything else 404. The build (`loadBuild`, a `Map` of every file outside a dot-named entry, so a `.env` or `.git` in the root is never served) loads on the first request and is memoized; a failed load (no `index.html`) throws `InvalidAgentDefinitionError("... build @chamvi/ui first.")` (500, `onError`) and is remembered for `BUILD_RETRY_MS` (5 s, on the route context's clock): meanwhile requests answer the same 500 without reading the folder or reporting, then the next one loads again. `loadBuild` follows symbolic links (a dangling one skipped, a directory reached twice read once). `renderIndex` replaces `CONFIG_MARKER` (`<!--chamvi-config-->`) with `<base href="<uiBase>/">` and a `<script type="application/json" id="chamvi-config">` holding `UiConfig { apiBase, uiBase, auth: { tokens, authup? } }` (`apiBase` = the route context's `basePath`, `uiBase` = `apiBase + basePath`; `<`, `>`, `&`, U+2028, U+2029 escaped). Every answer carries `SECURITY_HEADERS` (`nosniff`, `referrer-policy: no-referrer`, `x-frame-options: DENY`) and the CSP of `buildCsp` (`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self' <authup origin>; form-action 'self' <authup origin>; base-uri 'self'; frame-ancestors 'none'; object-src 'none'`). Options are validated at construction (`basePath` `^(?:\/[a-z0-9._~-]+)+$`, lower case since routup matches case-insensitively; authup URL absolute http(s); non-empty `clientId`; `tokens: false` needs `authup`; non-empty `root`). `defaultRoot()` is the first of `dist/app` beside the built entry or seen from `src/routes` holding an `index.html`.
- **App shell**: `readConfig(document)` (else `DEV_CONFIG`), `createUiRouter(config, guards, history?)` (`createWebHistory(uiBase)`, lazy views, the global `beforeEach` guard `createAuthGuard`), vuecs with the Tailwind theme and the Lucide preset; the Lucide icons the preset names are bundled through the `virtual:chamvi-icons` Vite module (`addCollection`), since Iconify would fetch them from its API, which the CSP refuses. Fonts are self-hosted (`@fontsource-variable` Instrument Sans and JetBrains Mono, one variable file each for every weight, bundled by Vite, so `font-src 'self'` holds). The styling is the approved mockup version 3: the Glacier token set (`--ch-bg`, `--ch-canvas`, `--ch-surface`, `--ch-sunken`, ..., the status pairs `--ch-run`/`--ch-wait`/`--ch-ok`/`--ch-fail` with their tints, light on `:root`, dark on `.dark`), a sidebar on the page ground and the work on one raised canvas, square tinted status chips with a shape per status, trigger chips, stat tiles, approval cards with a tinted head and a footer bar, empty states (`EmptyState`). The tokens, the `--vc-color-*`/`--vc-radius-*` overrides and every view class are unlayered (`@layer vuecs` comes after Tailwind's layers, so a layered override would lose); vuecs controls get the mockup look through classes (`btn`, `btn-primary`, `textarea`) and the `vc-form-input`/`vc-form-select-trigger` rules; forms are `VCFormGroup` + `VCForm*` controls on a validup `Container` (`useValidup`, ebec codes, server `issues` into `setExternalIssues` by their last path segment) with `<IFieldValidation>` into `:validation` (ilingo translates by code: a catalogued code shows the catalog's text, not the server message); the group's label has no `for`, so a `#label` slot holds a `<label for>` under `label-tag="span"` (`getByLabel` needs it); `mountPage` installs ilingo before `@ilingo/validup-vue` and stacks the internal `FORM_THEME` (`.field`, `.field-msg*`, `is-invalid`) on Tailwind; Reka's select has no empty item value, so unset is `null`; `VCTable` runs without its `responsive` mode, the `.stack` class stacks rows below 760 px. Dark mode is `useColorMode()`'s `.dark` class (system by default), bound in `App.vue` so the login follows it too. `App.vue` renders nothing before the first navigation resolved and mounts the shell (which polls the inbox) only for a signed-in principal. The `AppContext { config, client, session, storage }` is provided once (`context/`).
- **API and stream** (`ui-kit/src/api/`, `ui-kit/src/sse/`): `createApiClient({ apiBase, token, refresh?, onUnauthorized?, fetch? })`, every non-2xx answer an `ApiError { status, code, message, retryAfter? }` (`http_<status>` for a non-JSON body); a 401 asks `refresh` once and retries, else calls `onUnauthorized` (sign out, back to login with the current path); `me(token)` with an explicit token never refreshes or signs out (credential checks). `openRunStream` reads `GET /runs/:id/stream` with fetch (bearer header, `Last-Event-ID` = the last step index seen), reconnects after a drop (`RECONNECT_DELAYS_MS` 1, 2, 5, 10 s, the last repeating, reset by any event; the `Retry-After` of a 503 or 429), stops after a stream that ended on a settled run (`onSettled`) and on 400/401/403/404 (`onError`).
- **Navigation**: the shell is `AppShell` of `@chamvi/ui-kit` (one sidebar on the dashboard and every `*-ui` page: the fixed items, then one plain-link item per `GET /ui-pages` entry the principal may see, an `accounts` slot for the second column; `app/components/dashboard-shell` adds the inbox badge and router navigation). Agents (first; `/` and every unknown path redirect to `/agents`, so a sign-in without a return path lands there), Runs (`/runs`), Approvals, Schedules, Connections (`/connections`, `/connections/:name`; in the sidebar only while `GET /connections` lists one, polled every `CONNECTIONS_POLL_MS` 15 s; invariants in [connections.md](connections.md)). There is no top-level state page: state is the agent page's State tab. Agent names link to `/agents/:name` from the runs tables, the run page, the approval cards and the schedule cards.
- **Agents** (`app/agents/`, `AgentsView`, `AgentView`): `/agents` is a card per agent (`useAgentRollups`, every `AGENTS_POLL_MS` 15 s, four requests whatever the agent count, since `@chamvi/http`'s limiter allows 300 per minute per IP: `GET /agents`, `GET /schedules`, the app's newest `ACTIVITY_LIMIT` 100 runs and up to `ACTIVE_LIMIT` 100 `running`/`waiting` runs, split per agent by `buildRollups`; an agent without a run among the newest 100 reads "None among the newest 100 runs" (`lastBeyond`), and a 429 or 503 waits out its `Retry-After` (a bare 429 `RATE_LIMIT_BACKOFF_MS` 60 s) through the poller's returned delay) with channel chips (`channelChips` from `AgentSummary.channels`: the events of a GitHub subscription, the cron expression from `GET /schedules`, the hook path of a webhook), the next cron fire, the 24 h activity strip, the last run, the budget and the state collections, and a name filter; above the cards a notice (`data-testid="agent-issues"`) lists `GET /agents` `issues`, the agent folders that failed to load (`IApiClient.listAgents()` answers `AgentList { data, issues }`). `/agents/:name` (`useAgentDetail`) has the header (budget, state collections, channel chips), Start run (only with an `http.on()` subscription and `chamvi_agent_run` for `{ name, private }`, `canStartAgent`: a payload dialog, `parsePayload`, `POST /agents/:name/runs` via `IApiClient.startRun` with an `idempotencyKey` from `createStartKeys` (kept for a retry of the same payload text, so a start whose answer was lost dedupes), then a refresh) and View all runs (`/runs?agent=`), and the tabs (`?tab=`) Overview (Runs, Failed and Tokens over 24 h, Waiting with the oldest request; recent runs, this agent's waiting runs, subscriptions with next fire or route/hook), Runs (`AgentRuns`: the status filter and page in the query), State (`AgentStatePanel`) and Schedules (`ScheduleCard` with the subscription's newest run among the runs read). The API has no time filter, so every 24 h figure (`summarizeActivity`, also the runs page's Failed and Tokens tiles via `useRunActivity`) is counted from the newest 100 runs read (the overview: of the whole app, the agent page: of the agent) and marked `100+` (`saturated`) when that limit is reached inside the window.
- **Live state** (`app/runs/`): `mergeRunEvent` inserts steps by `index` (a known one ignored) and keys streamed text by the delta's model step (the checkpoint index, which is the ordinal of the run's `llm` steps; a resume rewrites the same checkpoint index), dropping text once that `llm` step landed or the run settled. The runs list (`useRunList`, newest first, filter in the route query) and the inbox poll every 5 s, the runs page's Running and Waiting counters (`useRunCounts`, `limit: 1` queries on one poller) and its 24 h window (`useRunActivity`) every 15 s, all through `createPoller` (never overlapping; a tick due while the page is hidden waits until it is shown); the run page (`useRunDetail`) loads, then streams after the last step (not for a settled run).
- **Auth** (`ui-kit/src/auth/`): `createSession` keeps a pasted token in `sessionStorage` (`chamvi.token`) only after `GET /me` accepted it, or an authup session (`authup.ts`, loaded only when configured: `@authup/client-web-kit` with its own pinia, installed before vuecs, its cookies replaced by `createSessionCookies` over `sessionStorage` (`chamvi.authup.*`, so no token reaches `document.cookie`), code flow with PKCE, redirect URI `<origin><uiBase>/login/callback`, the return path in `chamvi.return`; `refresh()` is true whenever `store.resolve()` leaves a token, so a 401 that raced another refresh retries once); `signOut` removes every `chamvi.` key. `restore()` drops a stored token only on a 401 (a network error, 503 or 429 keeps it). The guard restores on the first navigation, and again on the next one while no principal was found and sends a visit without a principal to `login?redirect=<fullPath>` (`safeReturnPath` only follows `/...` paths; with `uiBase` a path below `<uiBase>/ext/` must pass `isPagePath`, no dot segments or encoded separators, and only those get a full navigation, every other path stays in the router; a `*-ui` page's `mountPage` sends a signed-out visit to `<uiBase>/login?redirect=<its path>`). Gates evaluate nothing locally (#215): the session asks `POST /authorization/check` once a principal is in place and every `VERDICT_REFRESH_MS`, keeps the names as `session.permissions` (`session.allowed(name)`, closed until the first answer, a failed refresh keeps the last), so a control can show on an item the route then refuses (403, shown inline with the permission name). The approve gate (`approvableAgents`) is every run's agent while `chamvi_agent_approve` is allowed, and the server decides per agent; a page answering 403 shows the grant it needs.
- **Lineage** (`app/runs/`, `RunView`): `useRunChildren` lists `filter[parent]` (one page of `RUN_CHILDREN_LIMIT` 100) and refetches when the viewed run updates over its stream (a settling child changes the parent's `subtreeUsage`); a 403 sets `forbidden` and the panel shows `Listing dispatched runs needs chamvi_run_read.` (agent-scoped tokens cannot list children, see http.md). `parentOf` labels only known `trigger.parent.kind`s (`PARENT_LABELS`). Narrow `run.waiting` on `kind === 'approval'` everywhere approval fields are read; a dispatch wait shows the `Waits for N dispatched runs` callout and stays out of the inbox; status counts stay status-based (#129).
- **Approvals** (`app/approvals/`): the inbox lists the runs waiting on an approval (`status=waiting` plus `filter[waiting]=approval`, server side like the agent page's waiting list, so dispatch waits never fill a page; the `ApprovalCallout` shows the wait point's `title` and `body`, the tool and the channel; a body that is a JSON object or array (`jsonBody()`, `approvals/helpers.ts`), as a trust approval's private `{ tool, input, taint, detail? }`, is pretty-printed through `JsonBlock` in `div.callout-json`, so the final tool input shows only there; any other body stays text) and answers by approval id (`POST /runs/:id/approve`; 409 reads `already-answered`, 403 `forbidden`, the list refreshes). **Approval links carry ids only** (owner decision 2026-10-21; resume tokens are gone): the link channels put into approval messages is `<origin><uiBase>/approvals?run=<runId>&approval=<approvalId>` (`approval` optional). The auth guard keeps the query in `login?redirect=` and the authup return path (`chamvi.return`), so a signed-out visit comes back to the same URL. `readApprovalLink(query)` reads it (a repeated key's first non-empty value), `useLinkedApproval` loads the run (`getRun`, steps dropped) on every link change and inbox poll and pins the approval a link without one found first, and `linkedApprovalState` decides: `pending` (the highlighted `ApprovalCallout`, `highlight` scrolls it to the centre and focuses it, kept out of the inbox list), `forbidden` (403 notice plus a read-only card), `moved-on` (`not-waiting`, `other-approval`, `expired`: a notice linking the run), `unreadable` (403 on `getRun`), `not-found`, `failed`, or `answered` once this page answered it. The run page and the agent page link waiting runs with `approvalLinkQuery(run)`. `pendingApprovals` hides an inbox run answered here only while it still waits on that approval id.
- **Choice approvals**: `ApprovalCallout` renders `run.waiting.options` in a `fieldset.callout-options` (`data-testid="approval-options"`), a `VCFormRadioGroup` (`name` `option-<runId>`) or `VCFormCheckboxGroup` around the rows, one `VCFormRadio`/`VCFormCheckbox` per row (Reka buttons, ids by position) in the row head (`data-testid="approval-option"`, `data-option` the id, its parent the row), a `detail` in a closed `<details>` holding `pre.option-detail` (`white-space: pre`, scrolling inside the card), its lines `diff-add`/`diff-del`/`diff-hunk` when `isDiffDetail()` (`detailLines()`; builder's call: added lines take `--ch-ok`, removed ones ink on `--ch-fail-tint` with a `--ch-fail` bar (fail-coloured text on the dark tint is only about 3:1), hunks `--ch-run`); Approve is disabled until `canApprove(waiting, selected)` (core's rule), Deny sends no selection; it emits `answer(approved, reason, selected)` and `useApprovals().answer(run, approved, reason?, selected?)` sends `selected` only on a non-empty approval. The run page's wait step shows `Selected: <labels>` (`selectedLabels()`, `step-item/helpers.ts`, ids as fallback). e2e: the demo agent `release` (`pick_version`).
- **Approval artifacts**: `waiting.artifacts` render as an `ArtifactStrip` above the options, each option's `artifacts` under its label and above `Details`; `useArtifactTiles` (`app/artifacts/`) reads the metadata once per approval id and the bytes through the bearer client (`readArtifact`, an `<img>` cannot send the header) as object URLs (hence `blob:` in `img-src`), revoked on an approval id change and on unmount, a read landing after the change dropped before any URL is made. Only `INLINE_IMAGE_TYPES` (png, jpeg, gif, webp, exact match) render inline; anything else (SVG included: it can carry script) is a download through a temporary `<a download>`, never a blob URL in a tab, which would run in the UI origin. A missing or unreadable artifact is a placeholder with its name, never an error for the approval. The full-size `ArtifactViewer` is a `VCModal` (Escape, backdrop).
- **e2e**: `test/e2e/smoke.spec.ts` (Playwright, Chromium) against `test/e2e/demo/server.ts` (a `deploy` agent whose tool calls `approve()`, on a stateless mock model, a `digest` agent on `cron.on()` with state, static token `E2E_TOKEN`) on port 4173: dispatch, live run, approve, completed; opening an agent and starting a run from its page (then its run, the agent link back, the digest agent's State tab); fonts served by the app, dark mode and no sideways scroll at 390 px (screenshot-free); the run page following a run live; an approval link opened signed out, signed in, the highlighted and focused card approved, the run completed, and the same link afterwards showing the moved-on notice; a choice card's option image (thumbnail as a `blob:` URL, the viewer opened and closed with Escape); a `*-ui` page (`test/e2e/connections.spec.ts`, the page in `test/e2e/demo/page` built by the web server command); a connection pairing live (the demo handle `whatsapp`: QR, `POST /demo/connect`, QR gone, reset confirmed in the page, a new QR). CI job `E2E (Chromium)` caches `~/.cache/ms-playwright` per Playwright version.
- **Module**: `uiModule()` on `@chamvi/ui/module` (named `ModuleName.UI`) contributes `uiRoutes()` (auth from `@chamvi/app`'s `readUiAuth()` of `CHAMVI_UI_AUTHUP_*`/`AUTHUP_URL` when called, unless `auth` is given) and registers that auth as `AppToken.UI_AUTH`, which every `*-ui` page serves (one session, one sign-in); it provides no context.

## Testing

- `nx` runs `@chamvi/ui:test` after its build (`dependsOn: ["build"]`): `readme.spec.ts` serves the real `dist/app`. Running vitest by hand needs `npx nx run @chamvi/ui:build` first.
- Unit tests live in `test/unit/routes/` (the route against `test/fixtures/build/`, a fake build with the config marker) and `test/unit/app/<module>/` (the SPA modules, in Node: fake `fetch` (`test/utils/fetch.ts`), fake client (`test/utils/client.ts`), in-memory `Storage` (`test/utils/storage.ts`), fake timers for the poller (`test/utils/timers.ts`), composables run inside `effectScope()`, routers on `createMemoryHistory`). The vitest config has the Vue plugin so a module that lazily imports a `.vue` file loads; `app/tsconfig.json` (vue-tsc) typechecks `test/unit/app`.
- e2e: `npm run build && npm run test:e2e -w @chamvi/ui` (once: `npx playwright install chromium`). Playwright starts `node test/e2e/demo/server.ts` (type stripping, so Node >=26.0.0; no `enum`, explicit `.ts` imports) on port 4173 against the built packages and reuses a running one outside CI. The specs fail on any console error, which is how a CSP violation shows up. `test/e2e/**` never runs under vitest (its `include` is `test/unit/**`).
