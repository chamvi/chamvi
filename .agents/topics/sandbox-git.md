# Sandbox Git Credentials and Tools

Read before changing workspace git credentials, the redactor, `gitArgv()` or `git_fetch`/`git_pull`/`git_push`.

- **Git credentials**: `IGitCredentials { get({ url, host, path, access: 'read' | 'write', runId, signal? }) -> { username, password, expiresAt? } | undefined }` (`credentialRequest()`: host lower-cased with port, path without `/` ends and `.git`, empty for the host itself); `resolveGitCredential(sources, request)` asks in order, the first answer wins, an answer with NUL, CR, LF or tab is a `SandboxError`, a throwing source a `SandboxError` naming the URL. `staticGitCredentials([{ host, path?, username?, token }])`: host case-insensitive, `path` a whole-segment prefix, compared case-insensitively (longest wins), default username `oauth2` for a host containing `gitlab`, else `x-access-token`; `InvalidAgentDefinitionError` naming the entry, never a token. `gitArgv(url, args, credential?)`: without one `git -c credential.helper= -c core.hooksPath=/dev/null <args>`; with one `sh -c GIT_AUTH_SCRIPT sh <url> <origin> <path> <args>` with `<user>\n<pass>\n` on stdin, piped to a one-shot helper on fd 3 that answers only when git asks for exactly that origin and path (a rewritten URL never gets it), every other helper reset, `credential.useHttpPath`, hooks off. git's URL matching lets a URL-specific key of the repository's or global config beat any generic `-c` (verified with git 2.45), so the script checks the config for `<url>` before git runs (`git config --get-urlmatch`) and exits `GIT_AUTH_REFUSED_EXIT` (3; `runGit` turns it into a `SandboxError` naming the keys) for `http.proxy`, `http.sslVerify` false, `http.sslCAInfo`, `http.sslCAPath`, `http.curloptResolve`, any non-empty `remote.*.proxy` and any `url.*.insteadOf`/`pushInsteadOf` (the last so the URL checked is the URL git uses). git hands fd 3 to every helper it spawns, so the script also exports `GIT_ALLOW_PROTOCOL=https`, which beats any config (a repository's `protocol.<name>.allow=always` beats `-c protocol.allow=never`): a transport the config names for the URL (`remote.<url>.vcs`, run as `git-remote-<vcs>`) never starts and cannot read the credential. The script only runs for https URLs, so `allowFileRepos` is unaffected. Manager options: `credentials` (one source or a list), `depth`, `author` (`GIT_AUTHOR_*`/`GIT_COMMITTER_*` merged over `env`), `push`. With sources (`createCredentialSupport()`): every create of an https repo gets `checkout.credential` (read; a failing source fails the create), and `acquire`/`get` hand out a memoized view per workspace whose exec results, `readFile`, `readBytes` and errors pass through a `Redactor` of every password issued so far (`[redacted]`, values shorter than `REDACT_MIN_LENGTH` 4 skipped; an error with a secret becomes a `SandboxError` without cause; `createRedactor({ clock })` drops a secret added with an `expiresAt` `REDACT_GRACE_MS` (1 h, public) after it, static tokens stay; the credentials file of a workspace found again is never read back, since it is model-writable and a common string written there was redacted in every run; the first install overwrites or clears it) and whose `readFileRaw(path)` is the unredacted text for tools that write it back (coding's `edit_file`/`multi_edit` through `readRawText()`; with `redactedSpans(text)` they match oldString against the redacted text the model read (`redactedSpans`), refuse an edit that touches a `[redacted]` span and put every untouched token back byte for byte, so an oldString can neither probe a token nor write `[redacted]` back) and whose `redact(text)` covers what a tool decodes itself (coding's `bash` excerpts and `bash_output`). Workspace credentials: after the create, and before an exec of a view whose workspace this process has not written yet (found again after a restart) or whose earliest token expires within `CREDENTIAL_REFRESH_MS` (10 min), `INSTALL_CREDENTIALS_SCRIPT` writes `$HOME/.chamvi/credentials` (0600, through a temporary file; `<origin>/<path>\t<user>\t<pass>` lines: the repository's write credential, else (none, or a failing write lookup, reported to `onError`, e.g. an App without `contents: write`) its read one, plus the host's) and `$HOME/.chamvi/git-credential` (`CREDENTIAL_HELPER_SCRIPT`, set as the global `credential.helper` with `credential.useHttpPath`), concurrent execs sharing one write; a failure goes to `onError`, the exec runs anyway and the next attempt waits `CREDENTIAL_RETRY_MS` (60 s); the next rewrite is at least `CREDENTIAL_RETRY_MS` away, since `IGithubApp.repositoryToken` keeps answering its cached token until 5 minutes before expiry, inside the 10-minute window. No sources: no view, the provider's workspace itself. Residual risks (documented): sandbox code can read and transform the token (redaction replaces whole values only; a token split across two `bash_output` reads passes), the push policy binds `git_push` only, and the `Redactor` is process-local: a workspace adopted after a restart or on another replica redacts only the tokens this process issued, so a token another process installed (still in `$HOME/.chamvi/credentials`, logs or files until the next install overwrites it) reaches results unredacted. `write_file` of UTF-8 text through the view restores tokens like the edit tools (`restoreRedacted()`, `coding/src/tools/edit.ts`): each `[redacted]` of the content maps in order onto the `[redacted]` the model read of the file (a token's span back byte for byte, a literal one kept), a count that does not line up, or `[redacted]` content over an existing file that cannot be read as text (any read failure but `file not found`), is a `ValidationError` and nothing is written, a file without a token (or missing) is written as given. Structured Git tools can be offered without bash, but writable Git configuration and indirect execution mean they are not a hardened arbitrary-code boundary. Token scope and forge rules enforce authorization.
- **Git tools** (`manager/git-tools.ts`, in `manager.tools()` beside the workspace tools; plain `defineTool()` tools): every remote call through `runGit()` with the repository URL on the command line and the credential looked up for that URL (`git_fetch`/`git_pull` read, `git_push` write), never a remote name; `remote` (another repository) passes `normalizeRepo` with the manager's rules, the same repository spelled differently (`credentialKey`) is still `origin`, another one's branches land under `refs/remotes/<path>/` (`remoteName`). `git_fetch { remote?, refspec?, workspace? }`: default `+refs/heads/*:refs/remotes/<name>/*`, a branch name maps to its remote-tracking ref, a full `refs/...` refspec passes (`REFSPEC_PATTERN`, no `..`/`@{`), anything else `ValidationError`. `git_pull { remote?, branch?, rebase?, workspace? }`: fetches the branch (default the current one, `symbolic-ref`; detached without `branch` `ValidationError`) into its remote-tracking ref, then `merge --no-edit` or `rebase` onto it; a failed fetch or a conflict is the result (`step`). `git_push { remote?, branch?, force?, setUpstream?, workspace? }`: branch default the current one (detached without `branch` `ValidationError`); `force` without `push.allowForce` `ToolDeniedError`; `push.allowBranch(branch, ctx)`, by default every branch but the remote's default branch (read with `ls-remote --symref` at push time for every remote, origin included, since a found workspace's `info.defaultBranch` comes back from the model-writable `chamvi.defaultBranch`; a remote whose HEAD cannot be read is a `SandboxError`, nothing pushed), else `ToolDeniedError`; pushes `refs/heads/<branch>` when the local branch exists, else HEAD, as `<sha>:refs/heads/<branch>`, force as `--force-with-lease=refs/heads/<b>:<remote-tracking sha or empty>`; `push.mode: 'approve'` first asks `approve()` with the title `Push <n> commits to <branch>` and the `git log --format='%h %s'` of at most `PUSH_LOG_MAX_COMMITS` (50) commits, through `push.channel` (`findOneOrFail`), else the run's source channel when it has an `out` (`findOne()`), else core's `approve()` (inbox), a denial a `ToolDeniedError` with the reason; in a tainted run `git_push` (`guardWhenTainted`) asks once: its `trust.approvalDetail` first runs the push policy (force, `allowBranch`; a refusal is a `ToolDeniedError` before the gate asks) and, with `push.mode: 'approve'`, puts the same title and log into the outbound gate's private body (and binding), and `outboundApproved(ctx)` skips the tool's own approval, so `push.channel` is not asked in a tainted run (the gate's decision is answered in the inbox/API, the source channel gets the generic notice); after a push `update-ref refs/remotes/<name>/<branch>`, with `setUpstream` (origin, a local branch) `branch.<b>.remote`/`merge`; a rejected push is the result (`pushed: false`). coding's `bash` description points at them.
