# Skills

Read before changing the skill seam of core, `@chamvi/skills` or skill preparation in app/cron.

## First-class passive skills

`@chamvi/skills` owns `SkillIdentity`, `SkillMetadata`, immutable `Skill` snapshots, `ISkillSource`, `SkillCatalog`, `LoadedSkill`, `createSkillCatalog()`, all content validation and scoped `load_skill` construction. Core owns only `SkillInput`, `ISkillRuntimeProvider`, `ISkillRuntime`, `ISkillPreparation`, `PreparedAgentSkills` and `SkillContribution`. This follows sandbox's contract/implementation ownership split, but uses a dedicated preparation/contribution seam: no app module or context registration is needed. Among Chamvi packages, skills' main entry depends only on core; core/app never depend on skills, including in tests or fixtures.

`EngineOptions.skills` supplies additive defaults for every agent; `AgentDefinition.skills` adds scoped extras. `gitSkills()` and `loadSkillBundle()` carry their runtime automatically. Custom ready values/loaders use `defineSkill()`/`defineSkillSource()` from skills; these validate/copy supplied contents/declarations, while custom loaders own retrieval and pin verification. Core captures opaque inputs once per actual `Agent` in a weak map, including empty scopes. Synchronous provider snapshots validate without I/O; `checkAgent(agent, capturedInputs)` must not re-read mutable definitions. The optional runtime validates each effective scope (at most 16 names, exact deduplication, no name/content conflicts) and static tool collisions. A candidate selects a previously absent per-engine runtime only after all synchronous checks succeed, including model/channel checks. Matching protocol descriptors interoperate across package copies; incompatible protocols reject before I/O. A first skill can arrive after an empty engine has started without invalidating earlier captured empty contributions.

`Engine.prepare({ signal?, agents? })` prepares registered agents plus optional unregistered candidates without store writes. The internal `EngineSkills` module (`engine/skills/`, `IEngineSkills`) owns input capture, provider/runtime selection, validation, preparation/commit and the `WeakMap<Agent, SkillContribution>` for readiness through `checkAgent()`, `prepare()` and `get()`. It has no engine dependency. `Engine` selects the agents and owns the task before invoking runtime code, cancellation and actual-settlement waiting, and start/stop/drain ordering. The runtime resolves globals even for an empty agent list and returns a transaction. With no await between the final abort check, synchronous single-use `commit()` and contribution publication, cancelled work publishes neither contributions nor attestations. A transaction checks all staged fingerprints against the live ledger before any publication. `start({ channels?, signal? })` prepares before recovery, queue admission or channels; a call while a start is in flight joins it, and its `signal` only rejects that call (`untilAborted`), never the joined attempt, which only its own caller's signal or `stop()` cancel; `putAgent(agent, { signal? })` forwards caller cancellation into preparation and checks combined caller/engine cancellation before revision markers, run cancellation or registry changes. The folder watcher rechecks the app signal after legacy hashing and forwards it into this second preparation. Once registry work starts it finishes with local publication, even if cancellation arrives, to keep the marker, run sweep and registered agent consistent. Each active execution retains its actual Agent's immutable contribution across replacement. Instructions and tools join ordinary execution, policy, hooks, durable approvals and pending-call replay; skills owns reserved tool names and collision checks.

The optional runtime owns per-engine weak source/agent caches and historical identity fingerprints across stop/start. Source copies preserve the original loader receiver and stable structural source identity token, including across package copies. Reachable original sources reuse successful results across scopes, discarded candidates and restart; failures are evicted only after their actual owned work settles. Retired sources/content can be released once agents/candidates/active executions do not retain them any more. The lifetime ledger keeps only SHA-256 fingerprints of complete copied skills, never historical bodies or catalog snapshots. Each preparation stages only its delta and rechecks it synchronously at commit, without cloning/scanning history. Core contains no skill names, hashes, content or source caches.

`stop()` aborts preparation/startup immediately and joins actual standalone/candidate provider work and channel starts before cleanup returns. A channel resolving after cancellation is recorded and stopped; startup failure uses internal channel cleanup to avoid joining itself. `drain()` waits for stop before halting the queue. Deliberate restart reuses successful snapshots and retries settled failed/canceled providers; stop can wait for a provider that ignores cancellation. This adds no store fields or stronger revision/recovery guarantee. Saved tool-result bytes remain in their original checkpoints; pending/future loads follow the newly configured prepared corpus after restart.

`AppOptions.skills` forwards through `AppContext` to Engine. EngineModule retains its instance before awaiting `prepare({ signal: context.signal })`, then exposes the engine and runs `engineCreated` only after success. The actual start step forwards the signal too. Folder loading applies contributed and synchronous engine checks before candidate preparation outside tolerant definition-error handling; a folder agent whose preparation fails, at boot as while polling, is an agent issue (`watcher.preparationFailure(name)` keeps the error): not registered and no revision written at boot, the prior agent/revision kept on a reload, the other agents start. A job of that very agent fails with the error (`AgentsModule.onReady` throws it: exit 2 for `InvalidAgentDefinitionError`, else 1); a job of another agent runs. The preparation of agents passed in code still fails setup. Preparation retries use twice the poll interval, doubling up to the larger of 60 seconds or the poll interval; retries run on regular polls. Changed folder content resets the delay after the normal stability check; successful reload, removal or reversion clears the issue and retry state. Transient provider failures and verification failures share this retry policy; only a job's exit code tells them apart (`@chamvi/skills` throws `InvalidAgentDefinitionError` for configuration and a `ChamviError` `skill_preparation_failed`/`skill_preparation_locked` for retryable failures). Unrelated store failures retain their next-poll retry behavior. Check skips providers and installation, validating static headers only; migrate skips preparation. App run-job prepares during setup. Direct cron runJob calls `engine.prepare({ signal })` before it dispatches the tick, so a failed preparation rejects with no queued run and a caller cancellation meanwhile fires nothing (`skipped`); it forwards caller cancellation into engine.start too and only matching cancellation uses its normal drain/status mapping; independent verification errors propagate.

Global skill pin changes do not change folder hashes. Existing saved load results retain their original bytes; pending/future loads use the current snapshot. Finish or cancel unsettled runs before global upgrades if mixed-version disclosure is unacceptable. Startup Git sources require network/credentials, writable managed directories/tmp and Git (not present in the base Node 26 image). Startup probes must allow clone/verification latency. Stop joins cleanup and can wait for a noncancelable SDK clone.

## Source preparation

Optional `gitSkills({ source, revision, directory, approved })` supplies engine-owned startup preparation; `prepareSkills({ source, revision, names, directory, verify?, signal? })` also supports explicit setup/build. It privately uses the `skills` SDK (`resolveSource` with `ref` at the pin, then `installSkills` per name into explicit staging, universal/copy mode); options, pre-checks, local-path handling and the symlink policy are in `.agents/references/vercel-skills.md`. The cloned commit must equal the pin. Discovery reads the SDK's standard locations (no `fullDepth`; the whole tree only when those hold nothing), so a vendored copy or an SDK-initialised submodule declaring a selected name deeper does not make it ambiguous, while a name declared by several standard-location folders is refused. SDK calls run under `withoutYamlWarnings()`, which drops the `YAMLWarning`s quoting source text that the SDK's frontmatter parse sends to `process.emitWarning`. Chamvi owns its public options/results; skills has no app dependency. Using Git providers adds skills/Git at runtime; all packages require Node >=26.0.0. All staged verification precedes promotion. A dedicated corpus ownership marker permits replacement; nonempty unowned/symlink targets are refused. The sibling guard `.<name>.chamvi-skills-lock` (`prepare/lock.ts`: atomic `mkdir`, an `owner.json` with host, pid, process start, token, creation time) refuses concurrent same-target preparation with a `ChamviError` `SKILL_PREPARATION_LOCKED_ERROR_CODE` naming the guard path; a stale guard (its process gone on this host, the same pid of an earlier process start, this process's pid and start but not in its in-process set of held guards (a failed release), or older than `guardStaleMs()` on any host: `SKILL_PREPARATION_LOCK_STALE_MS` 1 h, or twice `SKILLS_CLONE_TIMEOUT_MS` when longer; without an owner record by the guard's mtime) is removed once under a second `<guard>.recover` guard (stale after 60 s) that re-reads the owner, then taken; release removes only a guard holding the own token. Failures are classified (`toPreparationError()`, `prepare/helpers.ts`): `InvalidAgentDefinitionError` (generic message) for invalid options, a commit other than the pin, a selected skill containing a symlink, discovery, selection, an install result other than one expected directory, verifier refusals, unowned targets and the configuration diagnostics of the SDK (authentication, which covers GitHub's missing repository, and a clone failure whose raw git answer names a missing repository: a `file://` path or an https 404); a retryable `ChamviError` `SKILL_PREPARATION_FAILED_ERROR_CODE` (generic message) for clone timeouts and other clone or fetch failures (a missing pinned commit and a network failure look alike), unknown codes, non-diagnostics and filesystem failures (staging, promotion, cleanup). The code-by-code mapping is in the reference. Checkout/stage/guard cleanup runs on success/failure (a cleanup failure is the retryable error only when the preparation itself succeeded, never replacing a configuration error or a cancellation); a backup survives if rollback itself fails. The SDK's clone falls back to the host's `gh` login and SSH agent/keys after an HTTPS GitHub authentication failure (documented in the skills reference for servers). Source/profile/pin configuration belongs to the consuming app, with reviewed hashes checked by callback before replacement and by `loadSkillBundles()` at runtime. No CLI, cwd mutation, import-time installation or script execution. See `.agents/references/vercel-skills.md`.

`gitSkills({ source, revision, directory, approved })` is a pure main-entry factory for an `ISkillSource & SkillInput`. It copies configuration and reviewed headers, derives the grouped names, retains singular-loader snapshots during staged verification, and returns them only after promotion and cleanup. `prepareSkills` accepts `signal`; both SDK calls receive it, a running SDK clone (not interruptible) is joined before cancellation cleanup, and promotion/rollback cannot be interrupted by cancellation. Independent verification or cleanup failures remain errors even when the caller also cancels.

## Approved local skills

The optional `@chamvi/skills` package owns filesystem helpers. `hashSkillBundle(directory)` validates and hashes passive UTF-8 bundles; it is a separate review aid, never dynamic approval. `loadSkillBundles(approved)` synchronously verifies explicit `{ name, version, directory, hash }` descriptors and returns an immutable `SkillCatalog` (`skills`, metadata-only `instructions`, ordinary SDK `tools`). No I/O on import. Operators append instructions and compose tools explicitly, checking for a `load_skill` collision. `SkillMetadata.ignoredFields` reports extra frontmatter keys; settings such as `allowed-tools`/`model` have no effect.

The fixed `load_skill({ name, reference? })` returns `LoadedSkill` (identity, `reference: null` for body, exact decoded content and sorted supporting paths) from private snapshots, with no runtime filesystem reads or activation state. Normal tool policy, hooks, approvals and checkpoints apply; repeated/parallel disclosure and approval recovery use existing engine behavior. `InvalidAgentDefinitionError` rejects invalid setup, `ValidationError` rejects model requests, and neither diagnostic exposes bodies. Core has no dependency on bundle filesystem code.

Pins cover every supported regular file with length-framed SHA-256, including README/references that agent-folder hashing may ignore. Bounds: 16 bundles, 64 files, 1 MiB total, 4 KiB frontmatter, 64 KiB body, 128 KiB/supporting file, 1,024 inventory entries including root/directories and 64 directory levels. All regular UTF-8 files inside the bundle can be passive references regardless of extension, including source code and scripts; no reference is executed. Reject symlinks, special/hidden files, malformed UTF-8, NUL text and control-bearing paths, metadata keys or trimmed descriptions. Surrounding description whitespace is trimmed before nonblank/1,024-character/control checks; internal controls remain invalid. YAML references, including agent metadata, are opaque text and are never parsed as configuration. Versions are exact reviewed identifiers, not rolling labels/ranges. Keep operator directories immutable and not attacker-writable during setup; filesystem checks are not a malicious-host-writer security boundary.

Disk edits cannot alter an existing catalog; recreation with changed bytes under the old pin fails closed. Upgrade reviewed assets and the tracked descriptor pin together. External directories have no watch or automatic revision integration. Skills grant no tools, permissions, scripts, subagents or sandboxing. Repository instructions ([coding.md](coding.md)) and issue text cannot add approvals. Complex third-party workflows, including Cloudflare audit scripts and independent subagents, require an explicit passive adaptation and separately supported capabilities. Credential isolation/private disclosure, future compaction retention and delegation remain separate work. Public usage and complete bounds live in `packages/docs/src/guide/skills.md`.

## Module map

`prepare/` owns `prepareSkills()` (`module.ts`), the target guard `acquireGuard()`/`releaseGuard()` with stale recovery (`lock.ts`, internal), the error helpers `invalid()`, `unavailable()`, `locked()`, `toPreparationError()` (`helpers.ts`, internal), `SKILL_PREPARATION_FAILED_ERROR_CODE`, `SKILL_PREPARATION_LOCKED_ERROR_CODE`, `SKILL_PREPARATION_LOCK_STALE_MS` (`constants.ts`, public) and Chamvi-owned `PrepareSkillsOptions`/`PreparedSkill` (`types.ts`). The `skills` SDK supplies cloning, discovery and copying; no SDK types or app imports reach the package main entry.

`packages/skills/src/bundle/` owns all filesystem hashing, verification and immutable bundle loading. `source/` exports pure `gitSkills()` from the main entry. `prepare/` accepts owned cancellation and joins SDK cloning before cleanup. App exports no filesystem skill helpers and has no dependency on the optional skills package. `catalog/` owns `Skill`, identities/metadata, `ISkillSource`, `SkillCatalog`, `LoadedSkill`, validation, `createSkillCatalog()` and scoped `load_skill`. `runtime/` owns `defineSkill()`/`defineSkillSource()`, the provider and per-engine weak caches/fingerprints. Core owns only the generic preparation/contribution protocol and lifecycle orchestration, with no skills package dependency.

## Testing

Tests use the real SDK and `createGitFixture()`, with no external network or providers; SDK spies delegate to the real calls and are overridden only to inject failures or answers, hold a resolve open or observe call options. They cover standard-location discovery (a deep duplicate ignored, the deep fallback, a deep-only name refused, a local `file://` submodule), the YAML warning filter (only `YAMLWarning` dropped, restored after success, failure and overlap), the symlink policy (a selected skill with a link refused, a linked skill folder not selectable, an unrelated tracked link tolerated and not copied), the pin (a HEAD moved past it still yields the pinned bytes), local path forms, the pre-checks before any fetch, install results other than one expected directory, the diagnostic mapping without leaked messages, duplicate/missing selection, retained assets, staged hash verification, managed replacement/rollback, same-target exclusion and cwd stability. The typed README consumer preserves its manual catalog behavior with helper imports migrated to `@chamvi/skills` in a real `prepareSkills` -> `hashSkillBundle`/`loadSkillBundles` -> `Engine` proof of metadata-only initial context and pinned body/reference results. Real remote selected-profile preparation is a separate manual proof.

Test-kit process specs cover exact 1 MiB allowances separately per stream/command, SIGINT-resistant overflow termination, raw NUL/newline output, silent `git diff --quiet` failure, external signals, subsequent command recovery and replacement of hostile inherited environment/config with the fixture identity.

Core's skill tests exercise only the generic protocol with a private fake runtime: provider selection/compatibility, captured input identity, late first runtime, preparation/commit publication, cancellation with actual settlement and contributed-tool execution. Core/app source and tests must not import skills. Shared `fakeSkillRuntime()` lives in `@chamvi/test-kit` for app/cron tests; core keeps a private copy to avoid a dependency cycle. Fakes implement the generic seam without reproducing skill business logic.

Real skill validation, catalog/tool, source, retention and Engine integration suites live under `packages/skills/test/`. They cover independent same-protocol provider copies, bound source receiver/cache identity, weak retention, restart, concurrent commit conflicts, cancellation without attestation publication, policy, durable approvals and replay. App lifecycle/backoff tests use the generic fake; real app+skills integration belongs to skills, preserving the package graph.

Skills bundle tests and utilities live under `packages/skills/test/`. Source/cancellation tests cover pure copied configuration, grouped identity results, retained snapshots, cleanup ownership, noncancelable clone settlement, promotion/rollback and independent error precedence during cancellation. App exports/graph tests prevent helper compatibility re-exports and dependency cycles.

App skill lifecycle tests (`app/skills.spec.ts`, `modules/agents/skills.spec.ts`) prove default propagation to code/folder agents, preparation before hooks/HTTP/channels/model execution, static check/migrate provider exclusion, boot preparation failures as agent issues (skip, retry with backoff, a job of the failing agent keeping its error class, a job of another agent running), tolerant definition errors, failed hot reload retention and stop joining ignored cancellation. `@chamvi/cli`'s `commands/run-job.spec.ts` pins the exit codes over `test/fixtures/skilled` (folder agents whose skill preparation throws): 1 for `skill_preparation_failed`/`skill_preparation_locked`, 2 for `invalid_agent_definition`, 0 for a job of another agent. Cron `run-job/signal.spec.ts` covers caller cancellation during preparation, independent verification failure precedence and a failed preparation rejecting before the tick is dispatched (no queued run). Skills `prepare-failures.spec.ts` covers the target guard (held, dead pid, restarted pid, a guard this process left but does not hold, other host, age only, a crashed recoverer's `.recover`, the stale bound stretched by `SKILLS_CLONE_TIMEOUT_MS`) and the error classes, including the real SDK clone whose sha fetch fails (a bad client git setting through `GIT_CONFIG_*`) and a missing pinned commit, both retryable, a missing `file://` repository as configuration, and a configuration error kept when cleanup also fails. The docs skills snippet compiles with core `SkillInput` and skills-owned domain types, default providers plus ready agent extras; the existing manual catalog fixture remains unchanged apart from its approved helper-import migration.

- Caller cancellation across folder preparation/hash/registration is covered by app `modules/agents/skills.spec.ts` and core `skill/runtime.spec.ts`: preserve the old agent, marker and queued run before mutation; join ignored provider cancellation; finish already-started registry work consistently for caller and engine stop.
