# Chat Channels

Read before changing `@chamvi/chat`, `@chamvi/chat-whatsapp` or `@chamvi/chat-discord` (the pages `chat-whatsapp-ui` and `chat-discord-ui`: [ui.md](ui.md)).

`@chamvi/chat` (#106, #109) adapts Chat SDK (`chat` ^4.45.0) adapters to `IChannel`; peer on core, http (`readRequestBody`) and `chat`, optional peer `@chamvi/app`, runtime dependency `smob` only, no platform SDK (owner decision 2026-11-02: platforms ship as their own packages on the public seam below, WhatsApp as `@chamvi/chat-whatsapp`). Entries: main (generic), `/module` (the only importer of `@chamvi/app`).

- **Ingress** (`ingress/`): `createChatIngressAdapter(adapter)` returns a branded wrapper; its `initialize(chat)` hands the real adapter a `Proxy` facade of the `ChatInstance` whose `processMessage` routes into the receiver `chatChannel` binds (every other member read from and bound to the real chat), so messages bypass the SDK's handlers and its pre-handler `state.setIfNotExists` dedupe (which would drop a redelivery after a failed handler). No private SDK field, no prototype patch. `chatChannel` checks `chat.getAdapter(name) === wrapper`, owns the `Chat` and each wrapper exclusively, registers no SDK handler; `processAction` is unsupported (never an approval), `history` only `0`.
- **Lifecycle**: start initializes the `Chat`, binds receivers, then `connect({ signal, clock })` (must settle on abort); stop (memoized, shared with a failed start) closes admission, aborts, `disconnect()`, waits for in-flight accepts at most `CHAT_STOP_TIMEOUT_MS` 30 s (`chat_stop_timeout`), `chat.shutdown()`, unbinds.
- **Intake** (`intake/`, policy first): own messages skipped; ids checked (`CHAT_ID_MAX_LENGTH` 1024, `ValidationError` without ids or text); `allowMessage` (required for every adapter; a refusal is silent); attachments or empty text refused (`ValidationError` to `onError`, no download), except a voice message with `voice` (see Voice); `resolveInvoker`; then per live agent its first matching subscription: an agent with `conversation` through `ctx.dispatchConversation(envelope, conversationOf(...))` (`{ account (alias, default the adapter name), chat: threadId, audience: direct:<author> | group:<channelId>, text }`, no concurrency key; the platform's `conversationTarget` may answer `undefined`, a terminal `ValidationError` for that agent), else `ctx.dispatch` with `concurrencyKey` hash(channel, adapter, thread). Idempotency key hash(channel, adapter, thread, sender, message id) for both (the in-flight key the same without the channel); payload `ChatPayload` (no raw provider object); address `chat:` + base64url JSON `[adapter, threadId]` (refused above 255, never hashed). Concurrent deliveries of one message share an in-flight promise; transient failures retry after `CHAT_INTAKE_RETRY_DELAYS_MS` (1 s, 2 s) on the engine clock, accepted agents skipped; terminal codes (`validation_error`, `invalid_agent_definition`, `agent_not_found`) are not retried; the rest is one `chat_intake_failed` naming channel, adapter, agents and attempts. `untrusted` default true (taint `channel:<name>`).
- **Answers** (`answer/`, opt-in `answers: { model?, timeoutMs? }`, refused without `resolveInvoker`): runs after `allowMessage`, the text/attachment checks and `resolveInvoker`, before any dispatch; only a `direct` message with an invoker. A message it handles (an answer, a notice, a reply that already answered) starts no run; anything uncertain dispatches as usual, and so does any failure before `engine.approve` (reported to `onError`: WhatsApp and Discord never redeliver, the dispatch keeps its retry). Open approvals: waiting approval runs of this channel and address with no options, no trust-gate `notification` (the owner never saw its arguments in the chat), delivered (`notifiedAt`), not expired, paged `CHAT_ANSWER_SCAN_MAX` 100 at a time up to `CHAT_ANSWER_SCAN_PAGES_MAX` 10 pages (internal; each later page re-reads the previous page's last run, a moved one means the pages shifted); a budget run out with rows left, or a shift, is truncated: never auto-picks. Rejected: filtering after one capped app-wide read (unrelated chats hide this one's approvals).
  - Pick: a quote matches only through `platform.sentMessageId({ key })`, which must return the id `prepare` sends for the key `<runId>:<approvalId>`; a quote that matches no open approval, an unusable quote id (WhatsApp: a quote whose `stanzaId` is missing is `replyTo` with id `''`; Discord: a `reference` becomes `replyTo`, the pinned adapter sets none), or any quote on a platform without the hook never answers (never falls back to the one open), so a Discord native Reply never answers. Rejected: an in-memory record of sent approvals to tell a closed one (per replica, lost on restart). A plain reply answers only the single open approval; with several, a notice, sent only when the sender may approve one of them.
  - Guards before the model: `can(invoker, chamvi_agent_approve, { name, private })` (an agent the engine does not hold counts private), the approval must render whole under the channel's current options (`renderChatMessage()` to a direct chat; raising `maxTextChars` or dropping `approvalUrl` can make one sent cut before the change answerable, so change them with no approvals open), and the reply's `sentAt` must exist and be at or after `waiting.notifiedAt` (strict: platform/engine clock skew errs towards not answering; a tolerance was rejected, it would accept replies sent before the delivery).
  - Classifier (`classifyChatAnswer()`): `engine.resolveModel(answers.model, run.agent)`, tool-less, sees only the approval title and the reply as JSON strings; a failure, timeout or unparsable output is `unclear` and reported to `onError` (an `unclear` decision is not), and unclear dispatches. Rejected: fixed answer words (any language, owner decision 2026-11-24); answering through the agent's own model (an injected message steers it).
  - A durable claim per reply (`IdempotencyService.claim`, scope `chat_answer:<channel>`, TTL `CHAT_ANSWER_CLAIM_TTL_MS` 7 days, which no `<agent>:<channel>` dispatch scope can equal; key hash(adapter, thread, author, message id)) right before `engine.approve(run, { approver: invoker, reason: text })`: a reply answers at most once. A held claim (`IdempotencyService.findOne`) is looked up before the scan, so a redelivery of an answered reply is handled (no run) even once nothing is open; an approve failure other than `invalid_run_state` releases the claim (`release`, owner-checked by run id) before rejecting, so a redelivery may answer; a failed release (reported) or a crash between claim and approve leaves the reply consumed. An approval settled meanwhile (`invalid_run_state`) gets the closed notice; other approve failures are intake failures. Notices go through the channel's own `out`, keyed `answer:<hash>:<notice>`, failures to `onError`.
- **Voice** (`voice/`, opt-in `voice: { model, maxBytes?, maxSeconds?, timeoutMs?, label? }`): `isChatVoiceMessage()` takes exactly one `type: 'audio'` attachment with `fetchData` (else the attachment refusal, Discord included); `transcribeChatVoice()` runs after `resolveInvoker`, before answers, so the classifier and the conversation see `label + transcript` (`ChatPayload.voice` `{ mediaType, bytes, seconds? }`, bytes never stored). Bounds before download: reported `durationSeconds` (`ChatAudioAttachment`) and `size`; then one clock timer of `timeoutMs` over `fetchData()` and `transcribe()` (`maxRetries: 0`: AI SDK retries wait on real timers), fetched size re-checked. A refusal is a fixed notice through `out` (the reason to `onError` is a chamvi error naming only the original's name and message: an AI SDK error may carry the audio in its request body) keyed `voice:<hash(adapter, thread, message id)>:<long|unclear>`, the reason to `onError`, no run; a channel stop rejects instead. At most `CHAT_VOICE_CONCURRENCY` 2 per channel (one limiter across starts). `start` resolves the model (`engine.resolveTranscriptionModel`) before binding anything, so a bad ref fails the app start. Not skipped for a handled message: a redelivery dedupes at dispatch.
- **Outbound** (`outbound/`): `out` decodes the address (adapter membership), lets the platform `prepare` (WhatsApp: decode the jid, derive the message id), requires started plus the platform's `online()`, posts within `timeoutMs` (default `CHAT_TIMEOUT_MS` 30 s, at most 2^31 - 1) on the clock; a timeout is `chat_request` ("may still be delivered"), a late completion or failure is reported, retries may resend (at least once). Plain text `title\n\nbody`, refused above `maxTextChars` UTF-16 units (an integer of 1 to the default `CHAT_TEXT_MAX_CHARS` 4096, also the approval budget), never split; approvals cut only the prose (surrogate-safe, at least 32 characters left, else `ValidationError`), then options (no detail), `Expires`, `Approve or deny: <approvalUrl>` (with options `Choose and approve or deny: <approvalUrl>`; ids only; required for approvals). An answerable approval (`answers`, a destination the adapter's `isDM` calls direct, as intake's `direct`, no options, not `generic`) is never cut (prose that does not fit is a `ValidationError`: the owner must see what they approve), ends with `CHAT_ANSWER_HINT` and needs no `approvalUrl`; options and `generic` approvals still need it, get no hint and are cut as without `answers`. `ChannelMessage.slot` ignored. Sends during drain fail. Core journals bound runs' source-address emits; nothing transport-specific.
- **Platform seam** (public, `channel/types.ts`): `chatChannel({ ..., platform })` takes `IChatPlatform { online?(), prepare?(ChatPlatformSend), conversationTarget?(incoming, payload), sentMessageId?({ key }) }` (the last: see Answers), every hook optional and called on the platform object (`this`), checked by `resolveOptions()` (`assertPlatform()`: an object whose given hooks are functions, else `InvalidAgentDefinitionError`). `prepare({ adapter, threadId, text, key })` runs per send after address decode and render, before the online check: a throw refuses the target as is, else it returns the post (default `adapter.postMessage(threadId, { raw: text })`); `online()` runs after it, only while started (default true; false is `chat_request`); `conversationTarget` runs per `conversation` agent after `allowMessage`, the text checks and `resolveInvoker` (default from the payload). The intake stays internal (`createChatChannel(options, intake)`), so a platform package needs no deep import. The socket lifecycle stays with `connect`/`disconnect`, the message policy with `allowMessage`/`resolveInvoker`.
- **Webhooks** (`channel/webhook.ts`): `webhooks: [adapter]` gives the channel an `in` at `POST /channels/<name>/<adapter>` (other subpaths 404); `readRequestBody` at `CHAT_BODY_LIMIT_BYTES` 1 MiB (413 before the adapter); the adapter's `handleWebhook` verifies; acceptance promises are collected through an `AsyncLocalStorage` scope (`trackIngress()`) plus the channel's `waitUntil`, awaited at most `CHAT_WEBHOOK_TIMEOUT_MS` 30 s; a failure a redelivery may fix (a transient intake failure, the channel not accepting, a failed adapter task) or the timeout is 503 (platform redelivery); a message only refused (`isRetryableIntakeError()` false: a terminal code, or `chat_intake_failed` without a transient failure) is reported once and gets the adapter's answer, as does success. Untracked: messages an adapter hands to a consumer in a pre-request async context (its own 2xx stands). GET challenges unsupported. Under the http app's general limiter unless `channelRateLimits` names the channel.
- **Module**: `chatModule({ channel })` contributes a prebuilt channel to `AppToken.CHANNELS` (`chamvi:channel:<name>`); no env variable, start step or route of its own.

## WhatsApp

`@chamvi/chat-whatsapp` (`src/whatsapp/`) builds on `@chamvi/chat`'s public API only; peer `baileys` exactly `7.0.0-rc14` (see [references/chat-sdk.md](../references/chat-sdk.md)). Owner decision 2026-11-01: a chamvi-owned adapter on Baileys' public API, not `chat-adapter-baileys`, which lacks a socket factory, reconnect, status and send ids.

- `createWhatsAppChat({ account, auth, policy, resolveInvoker, state, approvalUrl, onPairing, ... })` builds adapter, ingress, `Chat` (`concurrency: 'concurrent'`) and a `chatChannel()` with `platform` hooks (`online` = status `connected`, `prepare`, `conversationTarget` = `toConversationTarget(identity)`: audience `direct:<sender phone jid>` or `group:<group jid>`). Factory and `start --check` acquire nothing. `setup.conversation({ chat })` (`toConversationRef()`, a normalized phone or group jid) builds a `ConversationRef` through that same `toConversationTarget()`, address `channel.to()` of the jid's thread, so a cron run and a message there share one conversation (pinned per platform).
- `connect`: `auth.acquire(signal, { reset })` (raced against the abort; a late lease released at once), an abort check, then `makeWASocket` (or `socketFactory`) with the lease's creds and `guardKeys()` (get/set/clear admitted only while the generation admits, `InvalidRunStateError` after; Baileys adds its own transaction buffer) and a silent logger; each connect holds the reference-counted console guard (`console.ts`: drops console calls from a `libsignal` stack frame, which logs session keys, #183) until its close or failed start. An aborted `connect` throws before it becomes the current generation. `connect` resolves once the first acquire settled: a `connection_held` refusal (matched by `code`) is status `held-elsewhere`, retried with `WHATSAPP_RECONNECT` without a cap; another acquire failure is `failed`, capped at `maxAttempts`; the status stays put during retries (no flapping to `connecting`). A provider's `lease.lost` ends the socket without a flush and waits for the lease like a start; a late `lost` of a closed generation is ignored. `reset()` (refused without the provider's `supportsReset` and while `held-elsewhere`) closes the generation, clears a retry the close scheduled, acquires again with `{ reset: true }` and saves the fresh creds before the socket; `establish` never builds a second live generation, and a lost close's retry is skipped while a reset runs (see [connections.md](connections.md)).
- Statuses `stopped | connecting | pairing | connected | disconnected | logged-out | held-elsewhere | failed`, each reported to `onStatus` (a throw reported, the change stands). Socket status only from `connection.update`; 401 `logged-out` (`whatsapp_logged_out`), 440 replaced (`whatsapp_connection`), neither reconnects; other closes reconnect with `WHATSAPP_RECONNECT` (2 s x1.8 up to 30 s, ±25 %, 12 attempts, reset on open).
- `close`: stop admitting, clear the timer, detach, `socket.end()` bounded by `WHATSAPP_SHUTDOWN_TIMEOUT_MS` 30 s, then pending writes plus `flush()` under a fresh 30 s bound (nothing is admitted after the fence, so a dead link's 30 s `ws` close never eats it), then `release()`; a flush failure is reported (`whatsapp_auth`) and released all the same, past the bound released once the writes settle.
- A `messages.upsert` batch (`notify` only) is handled sequentially, so runs follow message order; a WhatsApp author has no name (`userName`/`fullName` empty).
- Media: only `audioMessage` gets `size` (`fileLength`, a Long or number), `durationSeconds` (`seconds`) and a lazy `fetchData` (`downloadMedia`, default Baileys' `downloadMediaMessage` with `updateMediaMessage` and the silent logger), called only by `voice` after `resolveInvoker`; other media carry none and stay refused.
- Identity (`policy.ts`): `fromMe` ignored, group sender = participant only, LID resolved only through `participantAlt`/`remoteJidAlt` (stanza attributes) or `lidMapping.getPNForLID` (content path self-only in rc14), else denied; `allowMessage` = identity, policy (`senders` phone jids or `open`, `groups`, `requireGroupMention` default true) and a defined `resolveInvoker(identity)`.
- Sends carry `3EB0` + 36 hex of sha256(channel, key) as message id (dedupe by WhatsApp unverified); `sentMessageId` returns the same id, so a swipe reply (its `stanzaId`) answers the approval it quotes; a quote is `quotedMessage` or a `stanzaId` (a mention-only `contextInfo` is none). The quoted `participant` is a display value, never used for a trust decision. QR pairing only. One connector per account (Recreate); no lossless/offline ingestion.

## Discord

`@chamvi/chat-discord` (`src/discord/`, the only folder importing `discord.js` and `@chat-adapter/discord`) builds on `@chamvi/chat`'s public API and the adapter's public members only (no protected member, subclass or fork); peer `@chat-adapter/discord` exactly `4.45.0`, checked by `test/unit/discord/upstream.spec.ts` (see [references/chat-sdk.md](../references/chat-sdk.md)). Owner decisions 2026-11-03: chamvi owns the Gateway client and the REST send; the adapter's `startGatewayListener` (auto-creates a thread per top-level mention, swallows login errors) and `postMessage` (no `allowed_mentions`, no nonce, no `AbortSignal`) are rejected.

- The adapter gets every env-backed option explicitly (`apiUrl`, `mentionRoleIds: []`, `respondToChannelIds: []`, `respondToGlobalMentions: false`, a refusing `webhookVerifier`, a `botToken` that always rejects), so it reads no `process.env` and never calls Discord itself. No Interactions endpoint.
- Inbound (`module.ts`): `captureInitialize()` is a `Proxy` over the adapter that keeps the `ChatInstance` (chamvi's ingress facade) handed to `initialize`; per `messageCreate`: own, bot and webhook authors and system messages (only types Default and Reply pass) dropped, `identityOf()` + `isAllowed()` on ids only (refusal before parsing and without any Discord call), `toChatMessage()` rebuilds the adapter's `parseMessage()` result (always the 3-part id, `isMention` unset) with the 4-part thread id and chamvi's mention verdict, then `facade.processMessage`, chained per Discord channel/thread id (at most `DISCORD_HANDOVER_MAX_PENDING` 100 waiting, more dropped and reported; a disconnect drops what waits, so nothing reaches a later connection). Identity and invoker ride `WeakMap`s keyed by the `Message`. A thread whose parent is unknown is fetched once (`channel.fetch()`, only when everything but the channel passes) and refused if that fails, so one thread never gets two chat ids; private or unknown thread type `thread:`, public/announcement `channel:<parent>`, DM `direct:<user>`.
- Connection (`connection.ts`): one discord.js client per generation, intents exactly `Guilds`, `GuildMessages`, `MessageContent`, `DirectMessages`, `partials: [Channel]`; discord.js reconnects established sessions, chamvi only re-creates a client after a transient login failure (`DISCORD_RECONNECT`, as WhatsApp's). Token invalid/empty or a throwing provider `discord_auth`, disallowed intents/invalidated/unrecoverable closes `discord_connection`; neither retries. A login that settles after stop never sets `connected`; `destroy()` bounded by `DISCORD_SHUTDOWN_TIMEOUT_MS`.
- Outbound (`send.ts`, through `platform.prepare`): `POST {apiUrl}/channels/<thread or channel>/messages`, body `{ content, allowed_mentions: { parse: [] }, nonce, enforce_nonce: true }`, nonce = 25 hex of sha256(JSON [channel name, target channel or thread id, key]) (a tool's explicit key reaches the platform unscoped, so the target keeps one key sent to two channels from colliding in Discord's per-author nonce dedupe) (at least once beyond Discord's nonce window), the deadline's signal on `fetch`; non-2xx `chat_request` with status and Discord code, body at most 200 characters, never the token; no own retry. `online()` true while started (REST is independent of the Gateway). `maxTextChars` `DISCORD_TEXT_MAX_CHARS` 2000.
- `toChatMessage()` drops the `fetchData` the pinned adapter sets on every attachment (an unbounded global-fetch download), so Discord audio stays refused also with `voice` (passed through); rejected for now: transcribing Discord voice messages without a bounded download.
- No `sentMessageId` (Discord assigns message ids) and no quote matching: the pinned adapter never sets `replyTo` (pinned in `message.spec.ts`), `toChatMessage()` sets it from `message.reference`, so with `answers` a native Reply never answers and a plain DM message answers only the single open approval; the hint and the several-open notice say so (`CHAT_ANSWER_HINT_PLAIN`, `CHAT_ANSWER_NOTICE_SEVERAL_PLAIN`, chosen by the absence of `sentMessageId`), never telling the user to reply.
- `setup.conversation({ threadId, user? })` (`toConversationRef()`): a DM `discord:@me:<channel>` with `user` the author, or a guild channel `discord:<guild>:<channel>`; no thread (its audience needs its type). Built through `toConversationTarget()` as intake's identity.
- The token (string or provider, read per login and per send) never reaches a store, run, payload, log, `onError` or error message; tests assert with `SENTINEL_TOKEN`. One connector per bot token (Recreate).
- **Module** (`discordModule()`, `@chamvi/chat-discord/module`; id `chamvi:discord:<name>`, default name `discord`, the connection, channel, account and env prefix): env `CHAMVI_DISCORD_*`, named `CHAMVI_DISCORD_<NAME>_*` (upper-cased, `-` as `_`), suffixes `TOKEN`, `APPLICATION_ID`, `GUILDS`, `CHANNELS`, `USERS`, `ROLES`, `DM_USERS`, `REQUIRE_MENTION`, then the store, with [partial-env resolution](connections.md); code options win, and a given `policy` fixes all its fields. Format errors throw at the factory; a required value missing while any field came from env fails `setup` naming the variable (a store-only gap stays `incomplete`), and nothing set leaves the module idle (below). A not configured connection, or a refusal of a stored field (attributed by the option the message names; a missing approval URL only when the store holds every required field), leaves an idle channel so subscribed agents start, while a refused code or env value fails `setup`; idle, it never logs in and `out` throws `ConnectionNotConfiguredError`. Names `dm` and `*-dm` are refused at the factory: `<NAME>_USERS` would read another instance's `DM_USERS`.

## Testing

- `@chamvi/chat` tests never reach a chat platform: `createFakeAdapter()`/`createTextMessage()` (`test/utils/adapter.ts`, a transport-free Chat SDK adapter whose `deliver()`/`deliverIgnored()` hand messages to the chat, `onWebhook` for the webhook path), `createMemoryState()`/`createRecordingLogger()` (`test/utils/chat.ts`), `createIntakeFixture()` (`test/utils/intake.ts`: the real intake over the fake adapter on an `Engine` with a memory store, a `store` hook to wrap repositories, `flush()`; platform hooks go in through `patch.platform`, the public `chatChannel({ platform })`). `test/unit/channel/platform.spec.ts` drives a class platform through all three hooks of the public seam.
- `@chamvi/chat-whatsapp` tests never reach WhatsApp and use `@chamvi/chat` through its public API only: `createFakeSockets()`/`waMessage()`/`createWhatsAppFixture()` (`test/utils/whatsapp.ts`: fake Baileys sockets the test drives through `open()`, `close(status)`, `deliver()`, `emit()`, `onEnd`; `settle()` lets queued promise work run; also a copy of `createMemoryState()`) and `createRecordingAuth()` (a trace of acquire, load, saveCreds, flush and release, with holds) plus `createFileAuthProvider()` (`test/utils/auth.ts`). `test/unit/whatsapp/module.spec.ts` checks the exact `baileys` version and the `start --check` of a WhatsApp setup over `@chamvi/app`.
- `@chamvi/chat-discord` tests never reach Discord: `createFakeClients()` (discord.js client fakes with a login the test settles, `emit()`, a destroy recorder, `destroyHangs`), `discordMessage()` and channel builders, `createFakeFetch()`/`bodyOf()`, `createMemoryState()` and `createDiscordFixture()` (an `Engine` on a memory store and `ControllableClock`) in `test/utils/discord.ts`; `test/unit/discord/upstream.spec.ts` (`native:` tests) pins the adapter version, the single `chat` copy, its env reads and `parseMessage()` ids.
