# HTTP

Read before changing `@chamvi/http` (routes, auth, channels mount, SSE, MCP, plugins, shutdown).

`@chamvi/http` is one routup v6 `App` per chamvi app, a peer of core like the channel packages.

- `createHttpApp({ engine, agents?, auth, basePath?, trustProxy?, shutdown?, bodyLimit?, stream?, mcp?, cors?, rateLimit?, metrics?, readyTimeoutMs?, onError?, routes?, channels? })`. The store (`find`, `find`, state), the agents (all current and future registered agents when `agents` is omitted; an explicit `agents` list is a fixed name allowlist validated by `selectAgents()` in `app/helpers.ts` at construction: a missing or duplicate name is `InvalidAgentDefinitionError`, and names outside the list have no routes or MCP tools in this app, while a mounted channel serves every agent subscribing to it) and the clock come from the engine (`engine.store`, `engine.listAgents()`, `engine.clock`); `buildContext()` copies the store and clock into the internal `HttpContext` and reads the agents live (see Live agents). `basePath` loses its trailing slashes (`normalizeBasePath()`, `app/helpers.ts`; `/` is no prefix), so every reader sees one prefix. An empty `auth` array, a `basePath` that is then no static path (the extra routes' shape) and a `stream.maxOpen` that is no positive integer throw `InvalidAgentDefinitionError`. Order: plugins, health, agents (incl. `/schedules`), runs, channels, extra routes, MCP, a trailing catch-all 404, the error handler. Route modules share one internal `HttpContext` (`app/types.ts`). **Live agents**: `HttpContext.agents` is `HttpAgents { get, list, names }` (`createLiveAgents()`, `app/helpers.ts`), reading `engine.getAgent`/`listAgents()` on every call (filtered by `agents`), so routes, `GET /agents`, `/schedules`, `GET /runs` agent filters, extra routes (`HttpRouteContext.agents` is a getter) and MCP follow `putAgent`/`removeAgent` at once; a named agent removed from the engine answers 404. `agentIssues?: () => readonly AgentIssue[]` (the app's load issues) is read per `GET /agents`, filtered by `agents`.
- **Channels** (`channels/`, `subscriptions/`): `httpChannel({ untrusted? })` (name `http`) and `mcpChannel({ untrusted? })` (name `mcp`) have no `in` and no `out` (`untrusted: true` taints every run they start); they are registered so `http.on({ schema? })` subscriptions (id `http`, at most one per agent) validate and `ctx.dispatch` scopes REST runs as `http` and MCP `run_<agent>` runs as `mcp` (separate idempotency scopes). `webhookChannel({ auth, name?, bodyLimit? })` has an `in` serving `webhook.on(path, { schema?, idempotencyKey?, concurrencyKey? })` (id `webhook:<path>`, many per agent, `path` starts with `/`) at `/channels/<name>/<agent><path>` (`parseWebhookSubpath`): a principal of its own `auth` (required, the app never authenticates channel routes) holding `agent:<agent>:run` checked before the body is read, JSON only (415), `readRequestBody` with `bodyLimit` (default 1 MiB, 413), the whole body is the payload through the schema, `Idempotency-Key` header else `idempotencyKey(payload)`, `202 { runId, deduplicated }`, no invoker on the run. `createHttpApp({ channels })` mounts `POST /channels/<name>` and `/channels/<name>{/*rest}` (`registerChannelRoutes`) for exactly the listed channels, each validated at construction (`validateChannels`: it has an `in` and is the object the engine holds under its name, else `InvalidAgentDefinitionError`); `channels` is a `RESERVED_ROUTE_SEGMENTS` entry, so any other `/channels/...` path is 404 and no `in` runs. The mount is rate-limited but never authenticated; `in` gets `{ request: event.request, subpath }` (raw, percent-encoded, `''` for the bare path) and a `ChannelContext`, its `Response` is returned as is and a thrown error renders through the JSON error handler (a 413 also sets `connection: close`). `readRequestBody(request, { limit })` (public, `request/helpers.ts`, exported next to the channels) is a channel's bounded body read: content-length check, then a bounded read; above `limit` a `RequestEntityTooLargeError` (413). Media-type checks stay with each channel. `GET /agents` summarizes subscriptions as `AgentSummary.channels: [{ channel, id, hook? }]` (`hook` the URL of a webhook subscription of a channel this app mounts, `webhookUrl()`); `routeLabel` labels the mount `/channels/:name/*`.
- Routes: `POST /agents/:name/runs` (the agent's `http.on()` subscription, channel `http`, 404 without one; body `attachments?: Array<{ mediaType, filename?, data }>`, at most `MAX_ATTACHMENTS` 16 (`runs/constants.ts`), validated by `isArrayOf(<attachment Container>, { max: MAX_ATTACHMENTS })` (length checked before any item, item issues prefixed with their index) with `isMediaType` (core's `isArtifactMediaType`, one rule for both packages), `isString` (1 to 255) and `isBase64` (strict RFC 4648 base64, canonical, decoded to a plain `Uint8Array`, never echoing the input in the issue; the other validators pass `boundReceived(value)`, the value only when its JSON has at most `RECEIVED_MAX_LENGTH` 256 characters) from `request/validators.ts`, unknown item keys dropped, passed to `dispatch`; size bounded by `bodyLimit`), `GET /runs/:id/artifacts` (`{ data: Artifact[] }`), `GET /runs/:id/artifacts/:artifactId` (the bytes; `content-type` the stored media type, `content-length`, `content-disposition: attachment` plus `filename`/RFC 5987 `filename*` when named, `x-content-type-options: nosniff`, `cache-control: private, no-store`; both under the run read rule via `loadReadableRun`, an artifact of another run 404 `artifact_not_found`), `GET /runs` (rapiq URL query via `@rapiq/codec-url` 2.4: `filter[agent]`, `filter[status]`, `filter[waiting]` (`approval` or `dispatch`, else 400; `RunFindOptions.waitKind`, store-db `JsonContains` on `waiting`), `filter[parent]` (one run id, else 400; mapped to `RunFindOptions.parentRunId`, since `find` ignores a field named `parent`; the unchanged `assertCanListRuns` rule, so an agent-scoped reader adds `filter[agent]`: post-query filtering would break `total`, limit and offset; #129), `page[limit]` default 50 max 100, `page[offset]`, `sort=createdAt` (oldest first, the default) or `sort=-createdAt` (newest first, `RunListQuery.order` `desc`, passed to `find`); only `and`-joined leaf filters; page values must be plain integers, as rapiq reads them with `parseInt`; rapiq coerces `123`, `007`, `true`, `null` even when quoted, so a non-string `filter[agent]` maps back to the registered agent whose name coerces to it, 400 when two do), `GET /runs/:id` (run plus steps), `GET /runs/:id/stream` (SSE), `POST /runs/:id/cancel`, `POST /runs/:id/approve` (body `ApproveBody { approvalId, approved, reason? }`, `approvalId` 1 to `APPROVAL_ID_MAX_LENGTH` 255, `reason` at most `APPROVAL_REASON_MAX_LENGTH`; `engine.approve()` with the principal as `approver`, `202 { runId, status: 'queued' }`, `InvalidRunStateError` 409 for a stale `approvalId`, an expired wait point, a dispatch wait or a run not waiting), `POST /channels/<name>[/...]` (the mount, see Channels), `GET /me` (`me/module.ts`: any authenticated principal, `MeView { id, kind, name?, permissions }` from `toInvoker(principal)`, the one place a principal sees permissions, its own; never the claims), `GET /agents` (`{ data: AgentSummary[], issues: AgentIssue[] }`, `AgentIssue { agent, message, at }`: agents that failed to load), `GET /schedules` (cron definitions with `nextAt`, not scheduler health), `GET /agents/:name/state/kv` (`state:read`, `find` in key code-point order as `{ data: Array<{ key, value }> }`, `parseKvListQuery`: `page[limit]` default 50 max 100, `page[offset]`, no filter or sort), `GET/PATCH /agents/:name/state/kv/:key`, `GET /agents/:name/state/collections/:collection` (top-level `eq` filters as `findDocuments` `where`, a double-quoted value kept as a string because rapiq coerces `42`/`007`/`true`/`null`, `filter[id]` 400 since `id` is the store id, `page[limit]`, a `page[offset]` above 0 is 400; documents as `{ id, ...fields }`, a non-object as `{ id, doc }`), `/mcp`, `GET /healthz`, `GET /readyz` (503 `shutting-down`, `draining` or `store-unreachable` within `readyTimeoutMs`), `GET /metrics`.
- Errors: every route under `basePath` answers `{ status, code, message, issues? }`, built by the error handler (never `toJSON()`, which would send `cause`); `withIssues` runs every issue tree through `boundIssues()` (`request/helpers.ts`), dropping a `received` value over `RECEIVED_MAX_LENGTH` whatever produced it (validators, a subscription schema, a core `ValidationError`), so a 400 never echoes a large body. `@ebec/http` errors keep their status (code lower-cased), validup errors are 400 `validation_error`, core codes map `RUN_NOT_FOUND` and `ARTIFACT_NOT_FOUND` 404, `INVALID_RUN_STATE` 409, `VALIDATION` 400 (`INVALID_AGENT_DEFINITION` at request time comes from an authenticator or `oidc()` mapper that resolved an invalid principal: 500 and `onError`); anything else is 500 `Internal Server Error` and goes to `onError`. Every 401 gets `WWW-Authenticate: Bearer`. Error responses start from `event.response.headers`, so CORS, `RateLimit-*` and `Retry-After` survive.
- Auth: `Authenticator = (request) => Promise<Principal | undefined>` (`undefined` lets the chain continue, a throw is a 401 remembered while later authenticators run; a resolved principal without a non-empty `id` and `kind` and a `permissions` array of strings is `InvalidAgentDefinitionError`, 500 and `onError`, and ends the chain); the chain runs once per request (memoized on `event.store`). Built-ins: `staticTokens({ tokens: [{ value, id, permissions }] })` (sha256-indexed, `value` at least 16 characters and unique, a non-empty `id` that several tokens may share), `authup()` (`@authup/server-adapter-web` `verifyRequest`; grants only from tokens whose `scope` has `global`), `oidc()` (vouchly; `principal` mapper and a non-empty `audience` per issuer required, as vouchly skips `aud` without one; untrusted issuer or malformed token passes on, unreachable issuer 503, an unknown `kid` 401; a mapper result without a non-empty `id` and `kind` or with `permissions` that are no string array throws `InvalidAgentDefinitionError`, a 500 reported to `onError`). Permissions `agent:<name>:run`, `agent:<name>:approve`, `agent:<name>:read` (a private agent's runs and state), `run:read`, `run:cancel`, `state:read`, `state:write`, `tool:<agent>:<tool>` (read by core's `requireToolPermission()`, never checked by a route), `*`; a `*` segment matches one segment, segment counts must match. Routes match with core's `hasPermission(principal.permissions, wanted)`; http exports only `agentPermission()`, no matcher of its own.
- Reading runs (`canReadAgentContent()`, `runs/helpers.ts`): a private agent (`definition.private`) and, failing closed, an agent the app does not hold (a removed private agent's runs stay protected) need `agent:<name>:read` (`run:read` and `agent:<name>:run` do not grant it); any other agent `agent:<name>:read`, `run:read` or `agent:<run.agent>:run` (a read grant reads every agent, so list and detail access agree). Single-run reads (`GET /runs/:id`, the stream, `/artifacts*`, MCP `get_run`) answer a protected run the principal may not read with the unknown-run 404 (`RunNotFoundError`), so private run ids are not probed; other 404 comes before 403 (run ids are random UUIDs). `GET /runs` and `list_runs` stay one store query (`total` exact): `agent:*:read` lists everything, `run:read` adds `RunFindOptions.agents = readableAgents()` (the readable registered agents plus unregistered ones a grant names explicitly), without either they must filter to one agent the principal can read; a `filter[agent]` of a protected agent without its grant is 403 `Reading runs of agent "<name>" needs agent:<name>:read.` MCP `run_<agent>` with a wait answers `{ runId, status, deduplicated }` only when the principal cannot read the run's agent or the agent of the descendant approval run (`toRunToolResult(..., readable)`). State routes: a private agent also needs `agent:<name>:read` after `requireAgent` (403). Approve and cancel need no read grant.
- Body after authorization: every protected `POST`/`PATCH` authorizes before `readJsonBody` (so an unauthenticated client cannot make the server buffer `bodyLimit`). `POST /runs/:id/approve` authenticates, loads the run (`loadApprovableRun`, 404, no read permission needed), requires `agent:<agent>:approve` (403), then reads the body. Bodies: JSON media types only (415 at the first non-empty chunk), `bodyLimit` (413; a `content-length` above it is refused unread, which Node discards; a body refused part-way is drained up to `bodyLimit` more bytes, else answered with `connection: close`, because an unread remainder stalls the next request on a keep-alive socket), objects only for REST bodies (validup `Container` with chamvi's own `isString`/`isBoolean`/`isDefined` validators; unknown keys dropped), subscription payloads through the subscription's Standard Schema (`validatePayload`). U+0000 is refused as 400 at the edge (`assertNoNul` on path and query before any route, `isString`, webhook-derived keys and addresses, MCP `pattern`s), since Postgres varchar columns refuse it and a lookup would otherwise be a 500.
- Invoker: `toInvoker(principal)` (`auth/helpers.ts`) snapshots `id`, `kind`, `permissions` and a `name` from the claims (`name`, then `preferred_username`; never `email`, which every reader of the run would see; static tokens have none), never the claims themselves. `POST /agents/:name/runs` and MCP `run_<agent>` dispatch with it as `invoker`; `POST /runs/:id/approve` and MCP `approve_run` pass it as `approver`. Webhook and GitHub deliveries dispatch without one; it never comes from a body.
- `serializeRun()` drops `claim` and the invoker's `permissions` (keeping `id`, `kind`, `name`) from every run that leaves the package (REST, SSE, MCP), `serializeStep()` drops the `permissions` of a `wait` step's `output.approver` (`GET /runs/:id`, SSE): a `run:read` holder must not learn another principal's grants. Wire types `RunView` and `InvokerView` (`runs/types.ts`).
- SSE: subscribe to `engine.on` before the snapshot, send `run.updated` then steps after `Last-Event-ID` (`id` = step index) or `?after=<step index>` (non-negative integer, given once, else 400; a valid `Last-Event-ID` wins, a malformed one reads as absent), then live events (`run.delta` of the run as `event: delta`, `data: { step, kind, text }`, **no `id:`** so `Last-Event-ID` stays a step index; live only, local replica only, never replayed); a store poll every `stream.pollMs` (2 s, on the `IClock`) covers runs executing on another replica and sends `ping` when idle; the stream ends after a settled run. A failing snapshot is an error response (500, 404 for a run gone meanwhile), never an empty 200 stream. Cleanup (unsubscribe, clear the timer, leave `ctx.closers`) runs once: on end, when `write()` returns false, or on `event.request.signal` abort (srvx aborts it on client close). `maxMessageSize` is never passed (an oversize write reads as a disconnect). Bearer auth only: browser `EventSource` cannot send `Authorization`, so browsers use a fetch-based SSE reader that sends `Authorization` and `Last-Event-ID` (or `?after=`).
- **Connections** (`connections/`): `connections?: () => readonly IConnectionHandle[]` is read per request; `GET /connections` lists `{ name, type, status }` (never widgets) for `connection:<name>:read` or `:write`, the detail adds `widgets` (a pairing QR) only with `:write`, and `/events` (SSE `status`/`widgets`, a `ping` every `stream.pollMs`, the run stream's slot and shutdown rules) and `POST /reset` (202) need `:write`; order 401, 403, 404 (permission before lookup, so a refusal says nothing about the name), so a QR never reaches a reader, a list or `onError`. `GET /connections/:name` also answers a declared or stored connection with no handle (`disconnected`; to a writer `live: false`, and `/events` stays 404 for it, so the dashboard polls instead of streaming). The configuration routes (`connections/config.ts`): `/connection-types`, `POST /connection-types/:type/connections` (`connections:create`, 201), `GET`/`PUT /connections/:name/config`, `DELETE /connections/:name`, `POST /connections/:name/test`, `/ui-pages`, the permission checked before any lookup (403 whether or not the name exists) and before the body is read. A deletable declared connection whose row is gone counts as not declared (a provider's list is the last start's). **Never echo a submitted value**: a body may hold a secret anywhere, so these validators and field issues carry no `received`, unknown fields are not named, and a test's message is only a `ChamviError`'s with the secrets removed (nothing goes to `onError`). `GET` config reports env and code fields by source only. A keyring failure on save is a 409 naming the variable (`refuseWithoutKeyring`), never a 500. Without `connectionConfigs` (a store without `connections`) types list read-only and every write is 409.
- Stream cap: one counter per app (`ctx.openStreams`, cap `stream.maxOpen`, default 1000) over open SSE streams and MCP `run_<agent>` waits (`waitSeconds > 0`); `acquireStreamSlot(ctx)` (`app/helpers.ts`) returns an idempotent release or `undefined`. The stream takes its slot after the `?after` check and the shutdown 503, releases it in its one-time cleanup (end, failed write, request abort, failed snapshot or poll, shutdown); over the cap it renders `503 service_unavailable` with `Retry-After: 5` (`STREAM_RETRY_AFTER_SECONDS`) through `renderError`, not reported to `onError`. An MCP wait over the cap answers at once like `waitSeconds: 0` (the run is dispatched, never failed); a wait releases in `finally`.
- MCP: `createMcpHandler()` from `@modelcontextprotocol/server` 2.3 (stateless legacy fallback), `maxRequestBodySize: bodyLimit`; the route reads a `POST` body itself (`readBodyBytes`, same limit and drain) and hands the SDK a buffered `Request`; one `McpServer` per request whose tools depend on the principal, passed with `event.request.signal` in `authInfo.extra` (the SDK's own `ctx.http.req.signal` never aborts on disconnect). Tools: `run_<agent>` per agent with an `http.on()` subscription the principal may run, its definition (payload JSON Schema with `$ref`s re-rooted at `#/properties/payload`, compiled by `fromJsonSchema`) built once per agent object by `buildRunTool` through `createRunToolSource` (a `WeakMap`, so a replaced agent, a new object, is rebuilt; the agents held at construction eagerly, where a failure fails the app, a later one on the first request that sees it, where a failure goes to `onError` once and its tool is skipped), which throws `InvalidAgentDefinitionError` for an uncompilable schema or a name above 64 characters (channel `mcp`; `waitSeconds` clamped to `maxWaitSeconds` 60; `waitForRun` resolves on `completed | failed | cancelled`, on the run's own approval wait, or when `findWaitingApproval` (core's `findApprovalWaitBelow()`: breadth-first, per level one `find({ parentRunIds })` plus one `find({ ids })` of the runs dispatch wait points name not found as children, a deduplicated run another run owns included; visited set, at most `DISPATCH_DEPTH_MAX` levels) finds a descendant waiting on an approval (`waiting.runId` names it), never on a dispatch wait alone, via `run.updated` or a 1 s store poll, or with the stored run on timeout or abort, signal = request signal plus `mcpReq.signal` plus the app's shutdown; ), `get_run`, `list_runs`, `approve_run` (`{ runId, approvalId, approved, reason? }`, `loadApprovableRun` then `engine.approve()`, like `POST /runs/:id/approve`). Tool failures are `isError` results; non-HTTP, non-core errors go to `onError`. Idempotency scopes differ per transport and principal (`<agent>:mcp:<kind>:<id>` vs `<agent>:http:<kind>:<id>`, see Intake).
- **Choice answers**: `ApproveBody.selected?` (`isStringArray({ max: APPROVAL_OPTIONS_MAX, item: { min: 1, max: 128 } })` in `request/validators.ts`, `APPROVAL_OPTION_ID_MAX_LENGTH` in `runs/constants.ts`) and MCP `approve_run`'s `selected` (`maxItems` 20, the same item rule) are passed to `engine.approve()` only when given, which checks them against the wait point (400 `validation_error`); `GET /runs/:id`, SSE and `get_run` carry `waiting.options`/`multiple`/`artifacts` (option artifacts inside `options`) as stored, `RunToolResult.waiting` spreads them in when present.
- Extra routes (`routes: HttpRoute[]`, `routes/module.ts`; served most specific first, so a prefix route may nest inside another (`uiModule()` plus any `uiPageModule()`, either registration order), and an exact route under a prefix route is refused): the extension point other packages plug into (`@chamvi/ui`'s dashboard, a `*-ui` page at `<uiBase>/ext/<slug>` through `staticRoutes()`) without routup in their types; run intake belongs in a channel on the mount, not here. `HttpRoute { method, path, rateLimit?: false, handler(request, ctx) }`; the handler gets `{ request, authorize(), readBody() }` (`request` a body-less copy with URL, method, headers and signal, so the limited path is the only way to the body; `readBody` = content-length check plus `readBodyBytes` with the JSON media type rule: 413, 415, raw bytes, memoized per request) and `HttpRouteContext { engine, agents, clock, onError }`, and returns `{ status, body? }` (`null` sent for a missing body, since routup hangs on `undefined`). Not authenticated by the app's authenticators unless the handler calls `request.authorize(permission?)` (`authorize()` of `auth/helpers.ts`: the chain memoized on `event.store` like the built-in routes, 401/403 alike); thrown errors render like any route's. `buildContext` refuses (`InvalidAgentDefinitionError`) a path without a leading `/`, with `:`, `*` or `{`, a duplicate method and path, a first segment in `RESERVED_ROUTE_SEGMENTS` (`app/constants.ts`) and the metrics path when metrics are on, all compared lower-cased because routup matches paths case-insensitively (`plugins/helpers.ts` lower-cases the request path the same way for the limiter skips, the stream check and `routeLabel()`). `rateLimit: false` routes skip the limiter; `routeLabel()` labels each route by its path. A string `body` is sent as `text/plain`, a `Uint8Array` as is (a `Response` built from `event.response.headers` like the artifact route, `application/octet-stream` unless the result's `headers` name a `content-type`), everything else but `null` as JSON; `HttpRouteResult.headers` are set on `event.response.headers` first, so a `content-type` there wins. `HttpRoute.prefix: true` registers `path` and `${path}{/*rest}` (routup's optional-group syntax, as the channel mount) and hands `HttpRouteRequest.subpath` (`routeSubpath()`, `routes/helpers.ts`: the raw, percent-encoded rest of the URL pathname after `basePath` and `path`, case kept, `''` for the path itself and for a plain route); `validateRoutes` also refuses a route of the same method at or under a prefix route (lower-cased) and a prefix route at or above the metrics path; `isUnlimitedRoute` and `routeLabel` (which takes the routes, labelling a prefix route `<path>/*`) match a prefix route on `path` and below `path/`. `HttpRouteContext.basePath` is the app's `basePath` (`''` by default).
- Plugins, in order: `@routup/cors` only when `cors` is given; `@routup/rate-limit` 300 per 60 s keyed by `getRequestIP(event)` (honours the App's `trustProxy`; the library default would trust any `X-Forwarded-For`), skipping `OPTIONS`, `/healthz`, `/readyz` and the metrics path, rendering 429 through the error handler; `@routup/prometheus` at `/metrics` with a fresh `prom-client` `Registry` per app, skipping `GET /runs/:id/stream`, its `path` label the route template from `routeLabel()` (`plugins/helpers.ts`, unknown paths `/_unmatched`; keep it in step with new routes). The limiter runs first so a 429 is not timed. `/healthz`, `/readyz`, `/metrics`, the channel mount and the extra routes (unless they call `request.authorize()`) are the only routes the app's authenticators do not guard.
- Shutdown: `createShutdown({ engine, server?, readinessDelayMs?, drainTimeoutMs?, closeTimeoutMs?, onError? })` (time from `engine.clock`); `shutdown()` is idempotent and runs: `shuttingDown` (readiness fails), wait `readinessDelayMs` (0), the `onShutdown` callbacks in the order added (`@chamvi/app` registers the `stopping` hooks first; the http app registers one that sets `ctx.closed`, ends SSE streams, aborts MCP `run_<agent>` waits (they answer with the stored run) and closes the MCP handler; new streams and MCP requests then answer 503 without `onError`), `server.close()` (not awaited yet), `engine.drain({ timeoutMs: 30 s })` (channels stopped first), then at most `closeTimeoutMs` (5 s) for the close before `server.close(true)`. With srvx pass `gracefulShutdown: false` to `serve()`.

## Module map

Folders without an `index.ts` export nothing public; other modules import the file they need.

| Path | Purpose |
|------|---------|
| `app/` | `createHttpApp()` (`module.ts`), `HttpAppOptions` (incl. `channels`), the `HttpRoute*` types and the internal `HttpContext` (`types.ts`), defaults and `RESERVED_ROUTE_SEGMENTS` (incl. `channels`) (`constants.ts`), `buildContext()` (incl. `validateRoutes()`) and the JSON error handler (`asserts.ts`) |
| `auth/` | `Principal`, `Authenticator` (`types.ts`), `Permission` (`constants.ts`), `agentPermission()` (`module.ts`; permission matching is core's `hasPermission(principal.permissions, ...)`), `authenticate()`, `authorize()`, `readBearerToken()`, `toInvoker()` (`asserts.ts`, internal; display name from `name` or `preferred_username`, never `email`); `static-tokens/`, `authup/`, `oidc/` hold the built-in authenticators |
| `request/` | No barrel: `readJsonBody()`, `readRequestBody()` (public through `channels/`), `validateBody()`, `validatePayload()`, `decodeQuery()` (rapiq), `readIdempotencyHeader()`, `boundReceived()`, `boundIssues()` (`asserts.ts`); `KEY_MAX_LENGTH`, `RECEIVED_MAX_LENGTH` (`constants.ts`); validup validators `isString()`, `isBoolean()`, `isDefined()`, `isArrayOf()`, `isStringArray()`, `isMediaType()`, `isBase64()` (`validators.ts`) |
