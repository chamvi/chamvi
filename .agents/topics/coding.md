# Coding Tools and Repository Instructions

Read before changing `@chamvi/coding` or repository instruction collection/delivery in `@chamvi/sandbox`.

- **Repository instructions**: `@chamvi/sandbox` exports `readRepositoryInstructions(workspace, paths?, { signal?, clock? })`, `RepositoryInstructions` and its source/diagnostic/options types. `instructions/` uses fixed `IWorkspace.exec` scripts in the physical workspace cwd, trusted `/usr/bin:/bin` utilities, bounded framed reads and strict UTF-8; no repository code or Markdown commands run. It reads root and requested ancestors (existing directories include themselves, files/missing targets use parents), root first then depth/JavaScript string order, `AGENTS.md` before `CLAUDE.md`. Standalone `@relative/path` includes expand depth-first outside backtick/tilde fences; includes inherit entrypoint scope, deduplicate content by path and retain all scopes/parents. Returned sources carry canonical relative `path`, exact-byte `sha256`, redacted `content`, `scopes`, `includedBy`; the result has recorded checkout `commit` or `null`, normalized `paths`, bounded `diagnostics` and `complete`. Redaction precedes include parsing and covers outward paths/diagnostics; digests describe original bytes. Sources are whole or omitted, never silently truncated: 32 KiB each, 128 KiB total, 32 sources, 8 include edges, 32 targets, 64 distinct ancestor directories including root, 512 inspections/include references, 4096 UTF-8 bytes/path, 64 diagnostics/8 KiB paths+messages, 30 s/request and 5 s/exec. Optional missing entrypoints are normal; missing includes, unreadable/invalid/refused sources, cycles or bounds make `complete: false`. Cancellation, transport/protocol failures, exec timeouts and missing utilities reject through existing errors. Every observed symlink component (also in-workspace aliases), special file, `.git` path and escape is refused best-effort, not race-free against concurrent mutation ([#92](https://github.com/chamvi/chamvi/issues/92)).
- **Instruction delivery and recovery**: the manager's default-on `repositoryInstructions` adds root `WorkspaceToolResult.instructions: RepositoryInstructions | null` on repository-backed `create_workspace` (also reused/adopted); repo-less/disabled results use `null`; a collection failure (a missing utility, a stray stderr line, an exec timeout) degrades to `instructions: null` plus `instructionsError` (the redacted reason, `collectInstructions()` in `manager/helpers.ts`; a cancelled run still rejects), so the acquired workspace stays usable and a retry does not fail again on reuse. Disabling it omits `read_repository_instructions({ paths?, workspace? })` (default `['.']`). `sandboxModule` forwards the option without a new env variable. Coding's separate default-on `repositoryInstructions` attaches optional context only to ordinary UTF-8 workspace `read_file` of a repository-backed workspace (a repo-less one runs no collector), never base64/images/HOME logs; a collection failure answers the file with `instructions: null` and `instructionsError`; either flag can remain enabled independently. Context remains ordinary model tool messages, steps and checkpoints through pauses/restarts; a new create/scoped call/file read collects current files without a cross-call cache or rewriting old messages. `commit` is checkout metadata, not necessarily current HEAD or an atomic snapshot. Tools are plain, not effect tools. Downstream prompts must request scoped guidance before direct edits or shell work in a new subtree and resolve incomplete guidance that could change the task. Repository text and system prompts grant no operator authorization, permissions, credentials, skill installation or publication; writes/edits and arbitrary bash do not enforce scope, and bash bypasses file-tool-only enforcement.
- **Tools**: `manager.tools()` = `create_workspace { repo?, ref?, image? }` -> `{ workspace, root: '/workspace', repo, ref, commit, defaultBranch, image, expiresAt, reused }` (another image of a held repository is a `SandboxError` asking for a dispose, like another ref) , `dispose_workspace { workspace? }` and the git tools. `codingTools(manager)` (needs only `get`) = `read_file`, `write_file`, `edit_file`, `multi_edit`, `grep`, `glob`, `list_files`, `bash`, `bash_output`, `bash_kill`, `git_diff` (`status --short` plus the diff, `staged?`); each takes an optional `workspace` id resolved with `context.run.runId`; camelCase result keys. Everything a POSIX `sh` script through `exec` with exact bytes as base64, state under `$HOME/.chamvi/` (outside `/workspace`):
  - **Stateful `bash`** (`shell.ts`, `BASH_SCRIPT`/`INNER_SCRIPT` in `constants.ts`): an outer `sh` holds the exec's pipes; an inner shell (`bash` when present, else `sh`) writes only to `~/.chamvi/out/<12 hex>.{stdout,stderr}.log`, so a plain `cmd &` never holds the call open. The inner shell sources `~/.chamvi/shell/env` (`export -p`; a file that fails `sh -n` is removed instead, since a syntax error in a sourced file ends dash before the command ran), enters `~/.chamvi/shell/cwd` (an explicit `cwd` wins for that call and is not kept), runs the command with `eval` without positional parameters and saves `pwd -P` and `export -p` (through a temporary file per process, `cwd.t.$$`/`env.t.$$`, then an atomic `mv`, so the parallel calls of one step never tear the file) after it and in an `EXIT` trap, so `exit` and `set -e` keep the state (a command's own `EXIT` trap replaces it and drops that call's state, which the tool description says); functions, aliases, options and the `unset` of a variable the workspace started with are not kept, a timed-out call keeps the state from before it. The outer prints a report (status, the next call's cwd as `/workspace/...`, sizes, the first `EXCERPT_HEAD_BYTES` 8 KiB and last `EXCERPT_TAIL_BYTES` 24 KiB of each stream as base64; stdout's on stdout, stderr's on stderr, each under the 64 KiB exec cap) and keeps the newest `OUTPUT_LOGS_KEPT` 100 logs, then, while `du -sk` finds `~/.chamvi/out` above `OUTPUT_LOGS_BUDGET_CAPS` (4) times `outputLogMaxBytes` (256 MiB by default; `HOME` shares the workspace's disk, on k8s its `ephemeral-storage`), deletes the oldest past that budget (counted newest first), both before it writes the report and both sparing every call still running or reporting (its marker `.active.<id>`, written at the start, removed once the report files are written, dropped after `ACTIVE_MARKER_MAX_MINUTES` 35 when no report ran; a step's parallel calls never delete each other's logs); the report goes to two files first, checked whole (two `BLOCK_END` lines each) before the header is printed, else a stderr line and exit `REPORT_FAILED_EXIT_CODE` 125 (also for a `mkdir` of the state folders that failed). After a timeout or the log cap killed it, or without a report, `REPORT_SCRIPT` reads the logs in a second exec (`REPORT_TIMEOUT_MS` 30 s); no report then is a `SandboxError` (`reportError()`, for 125 naming `$HOME/.chamvi` with no space left or not writable), never a result built from the raw exec. `BashResult { exitCode, stdout, stderr, stdoutTruncated, stderrTruncated, stdoutBytes, stderrBytes, stdoutLog, stderrLog, cwd, outputCapped, timedOut, durationMs }`, a cut stream reading `[... <n> bytes cut, full output in <log>]` between head and tail, never splitting a UTF-8 character. **Log cap** `codingTools(manager, { outputLogMaxBytes })` (default `OUTPUT_LOG_MAX_BYTES` 64 MiB per stream, a positive integer else `InvalidAgentDefinitionError`): no capping pipe (it would hold a `cmd &` call open and lose its tail on a kill); instead a watchdog of the outer `sh` (`watchdogPart()`: its `sleep` runs in the background, so the TERM trap kills and reaps it and the outer `wait`s for the watchdog, since an orphaned sleep stays a zombie under a PID 1 that reaps nothing) checks both logs with `find -size +<cap>c` every `OUTPUT_LOG_CHECK_SECONDS` 0.2 s while the outer shell runs and, past the cap, leaves `<id>.capped` and kills the exec's process group (`kill -KILL 0`, like a timeout); the report then cuts each log back to the cap (`head -c`) and reads `chamvi-report - capped` (`outputCapped: true`). A process the command left running (`cmd &`) that still holds a log open (`held`: `/proc/<pid>/fd` links, also deleted ones, on Linux; `lsof -g <pgid>` elsewhere) keeps the watchdog alive past the call (the outer `sh` kills it only when nobody holds the logs): every `JOB_OUTPUT_CHECK_SECONDS` 1 s it ends once nobody does, and kills the group once a log passed the cap (cut back first) or a later call's rotation deleted it, so such a writer never grows a log past the cap. **Timeout**: the inner shell runs in the background and the outer `wait`s with `trap 'kill -KILL 0' TERM`, so a TERM to the outer shell alone (BusyBox `timeout`, which execs the command and signals that process only) still kills the whole group (exit 137, `timedOut`); the inner shell and its commands start with SIGINT ignored, as every async command of a non-interactive shell (also background jobs).
  - **Background jobs** (`jobs.ts`): `bash({ background: true })` runs `JOB_START_SCRIPT` in an exec of its own, so the job lives in that exec's process group (local: the detached spawn, tracked by the lingering-group logic and killed on dispose; Docker/k8s: GNU `timeout`'s group, dying with the container) and the exec returns at once (the job's pipes are files: no `EXIT_DRAIN_MS` wait). `~/.chamvi/jobs/<12 hex>/` holds `pgid`, `pid` (the wrapper waiting for the command), `command`, `output` (stdout and stderr together), `status` (exit code), `killed` and `capped`. A watchdog of the wrapper (`watchdogPart()`, the same as the foreground's, its `sleep` in the background so the TERM trap kills and reaps it) checks the output every `JOB_OUTPUT_CHECK_SECONDS` 1 s; past `outputLogMaxBytes` it leaves `capped`, cuts the file back to the cap (`head -c` into a new file, so the job writes on into the replaced one until the kill) and kills the job's group (`kill -KILL 0`): status `killed`, `outputCapped: true`. `bash_output({ job, offset? })` returns at most `JOB_OUTPUT_MAX_BYTES` 32 KiB from a byte offset with `nextOffset`, `size` and the status (`running` while the wrapper lives in the job's group, so a reused pid or group never reads as running; `exited` with `exitCode`; `killed`; `lost` when it ended without a status, a container restart); `bash_kill` sends TERM to the group, waits up to 3 s, then KILL, only for a running job.
  - **Files**: `read_file` reads `readBytes`: `encoding: 'base64'` any file up to `BINARY_MAX_BYTES` 1 MiB; a png, jpeg, gif or webp (by magic bytes, `imageTypeOf()`) up to `IMAGE_MAX_BYTES` 5 MiB as `ReadFileImageResult`: the bytes go to `context.artifacts.put()` (filename the basename) and the result holds `artifactId` only, which `toModelOutput` hands the model as core's `artifactFilePart()` (the marker), so the tool step and every checkpoint keep the id, never the image; else UTF-8 text by line range (a non-UTF-8 file names `encoding: 'base64'` in its error); it also reads the logs `HOME_LOG_PATTERN` allows (`~/.chamvi/out/<id>.<stream>.log`, `~/.chamvi/jobs/<id>/output`) with `awk` in the workspace. `write_file({ encoding: 'base64' })` writes bytes (strict base64). `multi_edit({ path, edits })` applies 1 to `MULTI_EDIT_MAX_EDITS` 100 edits in order to the content (`edit_file`'s rules each, errors prefixed `edit <n>: `) and writes nothing when one fails.
  - **Search** (`search.ts`, `GREP_SCRIPT`): ripgrep when the image has it (`--hidden --glob '!.git'`, `--no-ignore` for `includeIgnored`), else `git grep -E --untracked` (`--no-exclude-standard`), else `grep -rE` without `.git`; else, for a grep without `--null` (BusyBox), one `grep -n` per file of `find` that prints `path NUL line:text` itself; one `path NUL line (: or NUL) text` record per match, each line cut at `GREP_LINE_MAX_BYTES` 2000 in the workspace (ripgrep `--max-columns --max-columns-preview`, the others `cut` with the exit status kept, only when the image's `cut` keeps NUL bytes: BusyBox's turns each into a newline, so there a minified line costs the 64 KiB cap and reads `truncated`), so a minified line cannot fill the output (compact over `rg --json`, which would fill the 64 KiB cap at about 150 matches); `GrepResult.engine` names it (regex syntaxes differ); `parseMatches()` is line-based (a line without a record, such as ripgrep's `path: WARNING: stopped searching binary file ...` notice on stdout, is skipped), and output that holds lines but no record is a `SandboxError` (`grep output could not be parsed`), never an empty success; a log path searches with grep or ripgrep. `list_files({ includeIgnored })` and `glob({ pattern, path?, includeIgnored?, limit? })` are `git ls-files` with a `:(literal)` and a `:(glob)` pathspec.
  - **The tools stay plain `defineTool()` tools, not effect tools**: a workspace can die (removed, expired, collected) while an effect record survives, so a redone step on a fresh workspace would skip a recorded write, and two identical `bash` calls of one step would merge; re-applying is safe (`write_file` idempotent, `edit_file` fails with "oldString not found", `bash` in a disposable sandbox, nothing outside the workspace changes).
- **Coding backend**: `ICodingBackend { code({ workspace, task, budget?, signal? }): Promise<{ status: 'done' | 'stuck', summary, diff }> }`, contract only (no backend implements it yet).
