# GitHub

Read before changing `@chamvi/github` (App auth, channel, tools, credentials, proposals).

`ChannelMessage.slot?: string`, chosen per `emit({ body, slot })` or channel `approve({ title, slot })`, opts into one persistent GitHub comment per normalized repo, issue/PR, channel, agent and explicitly named slot. Slots must be non-empty, well-formed strings without NUL characters, preserving exact names across database JSON storage; omission keeps append behavior. A single channel/agent can mix ordinary comments and multiple slots. Approval slot travels through the suspension request and stored WaitPoint to recovery delivery; emit effect identity includes the slot when present without changing existing unslotted keys. Stable SHA-256 comment markers are separate from per-delivery effect markers; the existing safe renderer reserves both in its footer. Persistent lookup pages all comments without `since`, requires the renderer-owned final marker footer (`hasFooterMarker()`, the tools' rule: trailing whitespace ignored) plus authenticated App bot (quoted body markers never qualify), skips a retry of the current message, otherwise PATCHes the whole body. Failed lookup/PATCH never POSTs; a subsequent send recreates a deleted comment. The slot identity hashes the App id, normalized repo, issue/PR number, channel name, agent and slot, so two Apps never update each other's comment (two deployments sharing one App, channel, agent and slot name do share it). Slot lock owner is a fresh UUID, lease `2 * timeoutMs`; a busy lock is asked again with backoff (`SLOT_LOCK_RETRY_MS` 50 ms doubling to `SLOT_LOCK_RETRY_MAX_MS` 1 s, on the channel's clock) inside the send's `timeoutMs`, then a retryable `github_request` (`... stayed busy for <ms>ms ...`); the owner-qualified release starts in `finally` without the send's abort and is not awaited, a failure (also a synchronous throw) goes to `onError`, a throwing `onError` is contained, and the lease ends a release that never answers, so a delivered comment is never reported as a timeout. The slotted lookup pages every comment of the issue (no durable comment-id cache), so a thread of many thousand comments can outlast `timeoutMs`. Standalone `githubChannel({ locks?: ILockRepository })` defaults to channel-local memory; `githubModule()` lazily resolves `AppToken.STORE.locks` only when a slotted send needs it, without changing append-only module setup or ordering. Shared locks coordinate replicas, not noncooperative clients or remote requests surviving cancellation/lease expiry. No freshness ordering or duplicate cleanup is provided.

`@chamvi/github` connects a GitHub App through the `github` channel (deliveries in, comments out); it depends on `@octokit/core` with `plugin-paginate-rest`, `@ebec/http` and `smob`, peers on core and `ai`, and needs `@chamvi/http` only for its tests (nx stays acyclic).

- `createGithubApp({ appId, privateKey, webhookSecret, installationId?, slug?, baseUrl?, clock?, fetch? })` validates eagerly (`InvalidAgentDefinitionError`: empty `appId`, a key that is no RSA private key, empty secrets, an `installationId` that is no positive integer, a non-empty `baseUrl` that is no absolute https URL without query or hash (`normalizeBaseUrl`; empty is the default API), a `slug` that is not `^[a-z0-9]+(-[a-z0-9]+)*$`, since a miscased slug would silently disable the self guard); literal `\n` in the PEM become newlines. App JWT: RS256 via `node:crypto`, `iat = now - 60 s`, `exp = now + 540 s`, `iss = appId`. Installation tokens are cached per installation and replaced when `now >= expiresAt - 5 min` on the `IClock`; concurrent callers share one exchange, a failure is not cached. `octokit(id)` builds a `PaginatedOctokit` per call with the cached token; `botLogin()` is `<slug>[bot]` from `slug` or one `GET /app` (single-flight, a failure not cached; an answer without `slug` is a failure, never a `[bot]` login); logins are compared case-insensitively (`isSameLogin`). Tokens, the key and JWTs are never logged or stored; a failed exchange rejects with Octokit's `RequestError` (its authorization header redacted).
- `github.on(events, { id?, filter?, idempotencyKey?, concurrencyKey?, selfEvents? })` (`subscription/`): channel `github`, id `github:<events joined by ','>`, events `name` or `name.action` (`^[a-z0-9_]+(\.[a-z0-9_]+)?$`, digits for `projects_v2_item`), default concurrency key `<full_name>#<number>` (the number as for the address), else `<full_name>`, else none. The payload is a `GithubEvent { name, action?, delivery, installationId?, payload }`. `github.to({ repo, number })` builds the address `<owner>/<repo>#<number>`; the channel instance has both bound to its own name.
- `githubChannel({ app, name?, mention?, approvalUrl?, timeoutMs?, bodyLimit?, onError?, clock? })` (`channel/`, every option checked when called): **`in`** (`receiveDelivery()`, `webhook/module.ts`), served by `createHttpApp({ channels })` at `POST /channels/<name>`: a subpath below it 404; `X-Hub-Signature-256` missing 401; `X-GitHub-Event` not `^[a-z0-9_]+$` or `X-GitHub-Delivery` not 1..255 characters without NUL 400; `@chamvi/http`'s `readRequestBody` with `bodyLimit` (default 1 MiB, 413), a non-JSON media type 415 (a form-encoded hook); HMAC-SHA256 over the raw bytes under every secret (constant time, all checked) else 401; non-JSON or non-object 400. Then per agent its first matching subscription of this channel and keys `subscription.idempotencyKey?.(event) ?? delivery`, `subscription.concurrencyKey(event)` and the address `<full_name>#<number>` for an event with an issue or pull request, or a `check_suite`/`check_run` whose `pull_requests` holds exactly one entry with `base.repo.id` equal to `repository.id` (`eventAddress`; zero, several, a foreign or unreadable entry: none, since the address exempts that PR from the outbound gate), all computed before any dispatch; a throwing `filter` or key function fails that agent only (`onError`, the others continue, answer 500), and `dispatch` refuses a key or address over 255 characters or with NUL (`assertTriggerKey`) the same way. With a match and a `Bot` sender whose login equals `botLogin()`, nothing is dispatched. Dispatch is sequential in agent order through `ctx.dispatch` without invoker; a failing agent goes to `onError` and the rest are still dispatched, then the answer is 500; else `202 { delivery, runs: [{ agent, runId, deduplicated }] }` (`runs: []` for ping, unmatched and self-sent events). The signature covers the body only, neither `X-GitHub-Delivery` nor `X-GitHub-Event`: a captured signed body replayed under fresh delivery ids (or under another event name an agent listens on, so `GithubEvent.name` is untrusted too) starts new runs (bounded per key by `concurrencyKey`, not in number), so exposed deployments give the subscription an `idempotencyKey` from body fields only and a `filter` that checks the body matches the event name.
- **`out(message, address)`** (`createCommentSender()`, `channel/out.ts`): `address` parsed as `owner/repo#n` (`parseAddress`, `REPO_PATTERN`, a positive number; else `ValidationError`); the installation is the event's for a run this channel started on the address's repository, else `app.installationFor()` of that repository (inside the send's timeout and signal; a failure `github_request`), else the event's for a run this channel started, else `app.installationId`, else `InvalidAgentDefinitionError` before any comment request. Per send: `app.octokit(installationId)` with the signal bound through `hook.before('request')`, page `GET .../issues/{n}/comments` (`since` = `receivedAt - 1 h`, `RECONCILE_SKEW_MS`, 100 per page) and resolve when a `Bot` comment whose login `isSameLogin(botLogin())` holds `effectMarker(markerKey(message.key))` (`markerKey`: the key when `^[\w:.-]{1,255}$` without `--`, else `sha256:<hex>`); else `POST` the comment: mention line (`@<login>` per `mention`, `LOGIN_PATTERN`), `### <title>` (when given; `neutralizeTitle`: whitespace runs collapsed, a zero-width joiner after every `@` and `#` and in `GH-<n>`, since titles come from tool code, so no mention or reference in it fires), the body cut to `COMMENT_BODY_MAX_LENGTH` 60 000 inside a fence one backtick longer than its longest run (at least three; runs over 31 broken with zero-width spaces), so mentions and `#123` inside notify nobody; for an approval `Waiting for approval until <ISO>.` plus `Approve or deny: <approvalUrl({ runId, approvalId, agent })>` (ids only) or the hint "Answer it in the chamvi UI or through POST /runs/:id/approve." (never the token; the comment is public), the run line, the marker. A send is bounded by `timeoutMs` (30 s, `GITHUB_CHANNEL_TIMEOUT_MS`) on the `IClock` (an `AbortController` armed before the first `await`, its reason the timeout error), below the 60 s notify lock. Failures: `GitHub <status>: <message>`, `GitHub request failed: <message>`, `GitHub did not answer within <ms>ms.` (code `github_request`). The token exchange and `GET /app` are bounded by `APP_REQUEST_TIMEOUT_MS`, so a cold app on a stalled GitHub can outlive the lock; the marker keeps a concurrent replica's send at one comment.
- **Choice approvals**: `renderOptions()` (`channel/helpers.ts`, internal) puts `Options (choose one):` (or `choose one or more`) and a fenced `- <id>: <label>` list (no detail) after the body, cutting the body to `COMMENT_BODY_MAX_LENGTH` minus the list's length; the link line reads `Choose and approve or deny: <link>`, without a link `Choose in the chamvi UI or through POST /runs/:id/approve with selected.` A plain approval renders as before.
- Tools act as `installationOf(app, ctx, target)` (`tools/helpers.ts`), per repository the tool names: (1) the event's `installationId` for a run of the channel `github` or of any name a `githubChannel({ app })` of the same app took (`registerChannelName`/`isChannelOf`, a `WeakMap` per app in `app/helpers.ts`; a payload of another channel never picks the installation) when the event's `repository.full_name` is the target (case-insensitive, no request); (2) `IGithubApp.installationFor(target)` (App JWT `GET /repos/{owner}/{repo}/installation`, cached per lower-cased `owner/repo` for `INSTALLATION_CACHE_TTL_MS` 10 min on the `IClock`, single-flight, a 404 `undefined` and not cached, a failure a `github_request` error and not cached; `repositoryToken` shares the cache); (3) the event's installation for any repository, else the app's `installationId` (a public repository the App is not installed on stays readable); else a `github_request` ChamviError, a tool error (never `FatalToolError`). `github_search_issues` targets the single `repo:` qualifier of its query (`searchTarget()`), else (3). The lookup is shared, so a caller only stops waiting on its run's signal (`untilAborted()`). `IGithubApp.installations()` lists `GET /app/installations` (paginated, not cached). Every installation request carries the run's `signal` (an Octokit `hook.before('request')` in `withOctokit`), so cancel, drain and the run timeout abort a stalled GitHub call. App-authenticated requests (the shared, single-flight token exchange and `GET /app`) carry no run's signal; `tokens.app()` wraps each in an abort after `APP_REQUEST_TIMEOUT_MS` (30 s) on the `IClock` (setting `options.request.signal` in place, since before-after-hook binds the same options object for every hook), so a stalled exchange rejects all waiters and is not cached. Repository names match `REPO_PATTERN` (GitHub's `[A-Za-z0-9_.-]`, each segment with a non-dot character, so `.`/`..` never fold the URL into another API path; `parseRepo` builds its regex from it). Inputs use `jsonSchema` with `additionalProperties: false` and are re-checked in `execute` (`ValidationError` tool errors); every GitHub failure goes through `toolError()` (`GitHub <status>: <message>`, a `ChamviError` with code `github_request`, never the request). Read: `github_get_issue`, `github_search_issues` (`advanced_search: true`, at most 20), `github_list_labels` (paginated, 100 per page), `github_get_pull_request`, `github_get_file` (65 536 characters, directory listing), `github_get_latest_release` (`{ none: true }` on 404), `github_list_releases` (`{ repo, from?, to?, tagPrefix?, exhaustive? }`: pages `GET .../releases` 100 at a time, at most `RELEASE_PAGES_MAX` 10 pages, stopping after a page that holds a release at or below `from` (unless `exhaustive: true`, which reads every page, since releases come by publication date and a later page can still hold one in range); drafts skipped; the version is the tag minus `tagPrefix` and a leading `v` (`versionOf`, `compareVersions` in `tools/helpers.ts`: semver order, missing components 0); with a bound only version tags count, sorted by version, the oldest `RELEASES_MAX` 20 after `from` (so `from` = the last tag pages on), without `from` the newest 20, without bounds publication order; bodies cut at `RELEASE_BODY_MAX_CHARS` 8 000), `github_compare` (`GET .../compare/{base}...{head}`, refs `REF_PATTERN` without `..`; first lines of at most `COMPARE_COMMITS_MAX` 100 commits cut at 300 characters, at most `COMPARE_FILES_MAX` 300 files, `truncated`). Write (effect tools): `github_add_labels` (default key), `github_create_comment` (key `<runId>:github_create_comment:<owner>/<repo>#<n>:<stepOf(options)>` with owner and repo lower-cased, body plus `effectMarker(key)`; `alreadyApplied` pages the issue's comments `since = trigger.receivedAt - 1 h` and returns `{ id, url }` of the App bot's comment whose body ends with the marker as its final line (`hasFooterMarker()`, `tools/helpers.ts`, trailing whitespace ignored; a quoted marker never counts, as for the channel; the same rule for `github_create_issue` and `github_create_pull_request`)), `github_close_issue` (`alreadyApplied` when `GET` shows it closed; meant to be gated in `hooks.beforeToolExecution` with `ctx.channels.findOneOrFail('github').approve(...)`). `stepOf` counts the assistant messages before the one carrying a tool-call with `options.toolCallId` that has no `tool-result` in the tool messages after it (a call whose messages already hold its assistant message, as on the pending-call path after an approval; position-aware, so a provider reusing call ids across steps never points at an earlier step), else all of them, so one comment per issue per model step and a recovery that regenerates the text still finds the marker.
- Context and module: `provideGithubContext(engine, app)` (one App) / `injectGithubContext(ctx)` (`context/`, key `github`, resolves by `ctx.run.agent`) in the main entry; `githubModule({ name?, agents? })` on `@chamvi/github/module` (`src/module/`, the only folder importing `@chamvi/app`; id `chamvi:github:<name>`, default name `github`, the connection and default channel name, env `GITHUB_*` or `CHAMVI_GITHUB_<NAME>_*`) resolves env, then the store, in `setup` (format errors at the factory, a partial env fails naming the variable, nothing set is idle: tools report not configured, deliveries answer 503). `.app` is a facade (`app/deferred.ts`) bound in `setup` (or at once when env and options are complete), a given `app` is listed but not editable. It contributes `githubChannel()` (`options.channel`, the approval link from `CHAMVI_PUBLIC_URL`, the app's clock) to `AppToken.CHANNELS` (the http module mounts it). An agent uses the module with it in `agents`, else the one without `agents` (at most one; two targeting one agent fail at startup), else a not-configured facade; a subscriber outside the module's `agents` is refused, and so is a subscriber of the fallback's channel another module targets (its tools would act as the targeted App); `GIT_CREDENTIALS` come from the fallback only, unless a targeted module sets `credentials`; the collection is per app, so an opted-in module's credentials serve the clones of any agent, not just its `agents` (the sandbox picks by host, never by run). Modules of one app share a `WeakMap` collection by container, for one connection provider and the resolver the first `engineCreated` provides, guarded per engine. Tools reach the channel with `ctx.channels.findOne('github')`; the notify-github context pair is gone.
- **Git credentials**: `IGithubApp.repositoryToken({ owner, repo }, { permissions })` finds the installation (`GET /repos/{owner}/{repo}/installation` with the App JWT, 404 `undefined`) and exchanges a token with `repositories: [repo]` and `permissions` (`createInstallationTokens().repository()`, cached per installation, lower-cased repository and sorted permissions until `TOKEN_REFRESH_MARGIN_MS` before expiry, single-flight, failures not cached, App requests bounded by `withAppTimeout()`); `botIdentity()` is `{ name: '<slug>[bot]', email: '<user id>+<slug>[bot]@users.noreply.github.com' }` from one public `GET /users/<login>` (memoized, a failure not cached). `githubAppCredentials(app, { permissions?, host? })` is structurally `@chamvi/sandbox`'s `IGitCredentials` (`IGithubGitCredentials`, no package edge): for its host (default `DEFAULT_GITHUB_GIT_HOST` `github.com`) and an `owner/name` path `x-access-token` (`GITHUB_TOKEN_USERNAME`) with `contents: read`, or `contents: write` plus `permissions` for write; nothing for another host, the host itself (empty path) or an uninstalled repository. `githubModule({ credentials?: false | GithubAppCredentialsOptions })` builds it when called and contributes it to `AppToken.GIT_CREDENTIALS` in `setup`.
- **Pull request tools**: read `github_list_repositories` (`tools/repositories.ts`: every `installations()` item in id order, `GET /installation/repositories` with each installation's token, archived ones dropped unless `includeArchived`, sorted by lower-cased `repo`, at most `REPOSITORIES_MAX` 1000, `truncated`), `github_list_issues` (open, `pull_request` items dropped, `labels` joined by `,`, at most `ISSUES_MAX` 100), `github_list_pull_requests` (`tools/pulls.ts`, open, `base` a `REF_PATTERN` ref, at most `PULL_REQUESTS_MAX` 100), `github_get_pull_request` extended through `toPullRequest()` (`headSha`, `headRepo` null for a deleted fork, `fork` when the head repository differs case-insensitively or is gone, `authorType`, `labels`, `mergeable` null while computed, `mergeableState` `unknown` when absent, `maintainerCanModify`, `mergeCommitSha`), `github_get_pull_request_checks` (`tools/checks.ts`: `readChecks()` pages the head's check runs with `filter: latest` up to `CHECKS_MAX` 300, reads the combined status, the base branch (`protection.required_status_checks.contexts` and `.checks[].context`) and its rules (`required_status_checks`); required is the union, a 403 or 404 on either protection read sets `required.known` false; `summarizeChecks()`: a check run `completed` with `success`, `neutral` or `skipped` is success, any other conclusion failure, else pending; a status `success`, `failure`/`error`, else pending; `missing` the required contexts no check carries; `state` `failure` with any failing, else `pending` with any pending or missing, else `none` without any check (a push seconds ago never reads green), else `success`), `github_get_push_target` (the head repository's `repositoryInstallation()`, its `contents`/`workflows` from the same cached `GET /repos/{o}/{r}/installation` answer, never the installation list; `canPush` only with contents write, never for an uninstalled fork: App tokens cannot use maintainer edits). Write (effect tools, `tools/write.ts`, `tools/merge.ts`): `github_create_issue` and `github_create_pull_request` (keys `<runId>:<tool>:<sha256 of the input>` from `inputEffectKey()`, so `execute` embeds `effectMarker(key)` in the body; `alreadyApplied` pages the bot's issues since `receivedAt - 1 h` or the pulls of the head `owner:branch`; `head` matches `HEAD_PATTERN`, `base` defaults to the repository's default branch, GitHub's 422 a tool error) and `github_merge_pull_request` (`{ sha }` required, `SHA_PATTERN`; refuses with `ToolDeniedError` before the PUT: closed or merged (`alreadyMerged: true` when merged at `sha`), head moved, draft, `mergeable` null, `mergeable` false or a `mergeable_state` outside `MERGE_STATES` (`clean`, `unstable`, `has_hooks`), any required check not success or missing, `required.known` false (fail closed: a token on a bypass list may not see what binds others), `state` `none` (CI has not reported) and any check pending, required or not, so a token on a bypass list never bypasses (a failing check that is not required passes); the PUT sends only `sha`, `merge_method`, `commit_title`, `commit_message`; 405/409 tool errors; `alreadyApplied` reads the pull merged at `sha`). `IGithubApp.writeTools({ mergeMethod })` (`GithubWriteToolsOptions`, default `DEFAULT_MERGE_METHOD` `squash`, outside `MERGE_METHODS` `InvalidAgentDefinitionError`). The merge policy (authors, semver) lives in the agent, never in a tool.
- **Self guard opt-in**: a delivery whose sender is the App's bot dispatches only to subscriptions whose `selfEvents` (event specs, `assertSelfEvents()`) name it (`acceptsSelfSent()`: `receiveDelivery` takes each agent's first matching subscription, for a bot-sent delivery the first matching one that accepts it), so the bot's own `pull_request`, `check_suite` and `check_run` events can start the maintainer; `issue_comment`, `issues` and `pull_request_review_comment` are refused (`SELF_EVENTS_REFUSED`, `InvalidAgentDefinitionError`), so a bot comment never re-triggers the agent; a bare `pull_request` still takes the bot's own `labeled`, `closed`, `synchronize` (documented loop: name the actions).
- Deferred: a `repos` restriction on the tools.
