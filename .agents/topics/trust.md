# Untrusted Content and Outbound Gates

Read before changing run taint, tool trust classifications, the outbound gate, channel destination exemptions or `extract()`.

## Taint and gates

Run taint is durable provenance, not a prompt-injection detector. `Run.taint?: { at: Date; source: string }` records the first exposure; the engine persists it before exposing an untrusted tool result or execution error, including recorded/streamed results, to the model. Parallel calls share the first write; persistence failure fails execution rather than exposing an unrecorded result. Existing taint survives restart and approval replay. A dispatched child inherits its parent's taint, and a tainted child taints the parent (`dispatch:<childId>`) before `waitForDispatch()` returns its outcome (immediate, resumed and replayed); recalling conversation messages or notes conservatively taints the run (`conversation:recall`), without claiming per-item provenance.

- **Ingress**: `IChannel.untrusted?: boolean` opts a channel into tainting new runs (`channel:<name>`). Channels without the flag remain trusted. The shipped GitHub and generic webhook channels opt in; `httpChannel({ untrusted? })` and `mcpChannel({ untrusted? })` (`@chamvi/http`, `HttpChannelOptions`, a non-boolean `InvalidAgentDefinitionError`) are trusted unless given `untrusted: true`. `@chamvi/app`'s `httpModule({ untrusted: { http?, mcp? } })` (`HttpModuleUntrustedOptions`, checked when called) forwards the flags to the two channels it registers, stripped from the `createHttpApp` options. This classification is distinct from engine-owned "trusted intake", which authenticates conversation routing metadata, not the content's trustworthiness.
- **Tool classification**: `defineTool()` and `defineEffectTool()` accept `trust: { taint?, guardWhenTainted? }`. Each flag is a boolean or `(input, ctx) => boolean | Promise<boolean>`; predicates use the final input after `beforeToolExecution`. Any other key or value is `InvalidAgentDefinitionError` (`assertToolTrust()`, `trust/asserts.ts`), from `defineTool()`/`defineEffectTool()` and, for a hand-built chamvi tool (`contextSchema === toolContextSchema`) carrying `trust`, from `wrapToolsForRun`; a third-party tool's own `trust` field is neither validated nor interpreted. `taint` marks the run before a result or execution error is exposed to the model (`tool:<name>`); `guardWhenTainted` requires approval or denies execution when taint already exists. Third-party/unclassified tools remain trusted by default. `AgentDefinition.trust.tools` overrides either flag by tool name with booleans only, including `false`; factories' names are checked after resolution. `trust.onTainted` is `'approve'` by default or `'deny'` (a `ToolDeniedError`).
- **Final-input gate**: calls classified with `guardWhenTainted` are checked for existing taint after the before hook and its input validation, but before effect lookup or execution. Approval decisions are bound to the operation and final arguments, so a changed destination or payload needs a new decision on replay. For these trust approvals, full arguments and taint belong in the private approval inbox/API; source-channel notifications are generic and contain no arguments. Do not forward approval bodies to an untrusted source channel.
- **Channel destinations**: `ChannelHandle.emit()` and `ChannelHandle.approve()` resolve their destination before gating (`isFixedDestination`, `channel/helpers.ts`). A send to the run's original source channel/address, to a dispatched run's `trigger.parent.source` (`dispatch(ctx, { source })`, the code-level API only: generated dispatch tools and role hooks never set it, `engine.dispatch()` strips `parent`, so the model cannot pick it; its safety rests on the agent author taking the address from trusted data), or to a channel's configured `defaultAddress`, is exempt. The source comes from a snapshot of the trigger `createToolChannels()` takes for every run (`structuredClone`, also outside conversations), and `bindTrust()` snapshots the channel and address the gate's notification goes to, so tool code writing to `ctx.run.trigger` moves neither. The exemption fixes the **destination**, not the content: it does not sanitize the message or prevent sensitive content from being sent there. The `defaultAddress` exemption holds on every channel, also one the run did not come from: each channel's default recipient (`consoleChannel()`'s name, `openclawChannel()`'s `deliver.to`) is an ungated sink for a tainted run, so register such a channel only when that recipient may receive whatever a tainted run produces. Other resolved destinations pass through the same durable outbound gate (operations `channel.emit`, `channel.approve`) before send effects; for `approve()` the gate's approval comes first, then the request itself to the target, whose plain ordinal `ChannelHandle.approve()` reserves synchronously before the gate's awaits (`reserveApproval()`, `approval/request.ts`), so parallel gated requests keep their ids across replays whatever the gate lookups' latency.
- **Shipped classifications**: web fetch and GitHub reads return untrusted content. `web_fetch` only taints (`trust: { taint: true }`): a fetch on a tainted run is not gated, although its URL can carry data out; agents opt in with `trust.tools: { web_fetch: { guardWhenTainted: true } }`. The gating of GitHub merge/issue/PR creation in event-started (tainted) runs is intended; `trust.tools: { <tool>: { guardWhenTainted: false } }` opts out per tool. GitHub issue/PR/file-proposal creation, merge and sandbox git push are outbound. Git push output and GitHub label-addition results also taint the run, since remote hooks and existing label names can be externally controlled. Structured git pull/fetch results are always untrusted, including for initially empty workspaces and errors; model-selected non-origin remotes are also outbound, while normalized workspace-origin targets are exempt. GitHub comments exempt the source issue/PR, read through core's `runSource(ctx)` (the source channel and address `bindTrust` copied at execution start, `undefined` for a context the engine did not build), never the mutable `ctx.run.trigger`, so tool code rewriting the trigger cannot move the exemption; label addition exempts names already present in the repository (lookup failure or any unknown name remains outbound). Closing an issue is not classified outbound. Coding reads/search/diff (`read_file`, `grep`, `glob`, `list_files`, `git_diff`) and shell/job output (`bash`, `bash_output`) always taint (`trust: { taint: true }`), in repo-less workspaces too: such a workspace can fetch anything (`curl`, `git clone`), so its content is no more trusted than a checkout's. Shell execution itself and local file edits are not automatically outbound. These are declared classifications, not inference from tool descriptions or effect-tool status.

## Quarantined extraction

`extract(ctx, { schema, content, instructions?, model? })` returns validated structured output from a separate, tool-less model call. It requires an executing tool-call frame for that run and a schema with an output validator; model resolution uses `resolveModel()`. Versioned raw model JSON is memoized in effects, keyed by run, content, schema, instructions and model identity; replay validates that raw value again instead of double-transforming an already validated result. Both fresh and replayed values also pass an independent structural output check when the schema is in the allowlist. Raw content, the helper's messages and provider error details do not enter the parent transcript through this helper; model and validation failures become a generic `ValidationError`. Outside an executing tool call of the run it throws `InvalidRunStateError`; a trust failure (no execution-bound trust context, a failed taint write) and the run signal's abort reason (cancel, drain, timeout) propagate as they are.

The conservative JSON Schema allowlist accepts literal enums/constants, booleans/null, numbers, closed objects with allowed properties (at most `EXTRACT_OBJECT_MAX_PROPERTIES` 32), bounded arrays (at most 10 items) and strings with `maxLength` at most 200 and an anchored `pattern` (`^` first, an unescaped `$` last; the output check tests `^(?:pattern)$`), with at most `EXTRACT_TEXT_MAX_LENGTH` 1000 free-text characters over the whole schema (string `maxLength` times the enclosing arrays' `maxItems`, summed) and a serialized output of at most `EXTRACT_OUTPUT_MAX_LENGTH` 16 384 characters (`extract/constants.ts`, internal). Unknown keywords, references, combinators and unrestricted strings do not establish this boundary. A schema outside the allowlist taints the run as `extract` before producing or replaying its result; extraction never clears prior taint. This is a structural restriction, not a guarantee that allowed values are truthful or safe for every use. A caller that subsequently returns raw content still exposes it to the parent model.

## Boundary limits

Shell execution is **not gated** by run taint and can read, write and exfiltrate; shell command policy and classifier work (#88) are separate. Agent state remains trusted for now; state provenance/taint is deferred. Raw content still reaches the selected model provider, including during extraction, and that provider is outside this boundary. Provider-executed tools have no local `execute` and are not locally gated. GitHub readers send model-selected queries, paths and refs to the API without an outbound gate; operators can classify them outbound when the API operator or its logs are not trusted recipients. Do not describe these gates as a sandbox, DLP system or complete injection defense. The opt-in GitHub file-proposal implementation is completed in this working tree, pending review/release, not a shipped release claim. `GithubAppOptions.proposals` allowlists repositories/paths; `github_propose_change({ repo, path, content, reason })` updates an agent/path branch and open PR without merging or hot reloading config; closed/merged proposals get a fresh branch suffixed with the previous PR number. PR history scans are independently bounded and short-circuit marker matches; new updates stop at 249 commits until the PR is closed or merged. Missing markers in already-capped PR histories fail closed. Unpublished ownership chains terminate at the pinned comparison's merge base, not today's base tip. `.github/**`, `.husky/**`, `CODEOWNERS` and `.gitmodules` in any folder, Unicode format characters (category Cf: bidi overrides, zero-width characters) in a path (and so in the PR title built from it) and unsafe paths are forbidden, for the allowlist globs and every call. The effect key is `<runId>:propose:<repo>:<path>:<sha256 of content>:<stepOf(options)>`, so a corrected content for the same path in one run is a new effect, and so is a later model step returning to an earlier content (A, B, A writes A again), never a recorded earlier one. PR discovery queries `head=<owner>:<branch>` per branch (the root branch, then `<root>-g-<n>` for the number of every PR found, at most 250 requests), never pages the repository's PRs; following every number keeps a PR off the predicted chain from hiding the tool's open PR from the multiple-open guard. Ownership and effect markers count only as the tool-owned final footer (`<branch marker>\n<effect marker>` as the last two lines of a PR body or commit message), never quoted earlier in the model-written `reason` or an edited body. Neither after the PR write nor while reconciling an applied open PR is the base re-checked (the diff is pinned to the observed base SHA), so a busy default branch never reports an applied proposal as a failure. Pinned tree modes, complete observed-head diffs and historical markers constrain writes/replay; detected head movement fails closed. Branches require exclusive trusted writers and serialized same-path proposals, and checks cannot make mutable PR branches immutable.

Custom run repositories must persist and hydrate `Run.taint`, including `taint.at` as a `Date`, across insert/update/read/recovery. `@chamvi/store-db` holds it in the nullable `chamvi_runs.taint` JSONB of its baseline migration (`UuidBaseline1794096000000`). Terminal runs and newly created clean runs remain untainted. A custom backend that adds taint to existing data backfills its unfinished runs conservatively (source `migration:legacy-run`), because their checkpoints may already contain external content. First-write monotonicity is engine-owned, not a new repository compare-and-set API. That backfill requires downtime: stop all old ingress, workers and approval pollers across every replica and scheduled job, wait for process exit, migrate/backfill, then start only new binaries. Never mix old/new runtimes on the store: old pollers can publish a new gate's private `waiting.body` instead of `notification`, and old workers can create/checkpoint untainted runs after the one-time backfill. Claims/notification locks do not prevent this; draining executions alone is insufficient. Custom stores require the same sequence.
