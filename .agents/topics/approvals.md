# Approvals and Hooks

Read before changing `approve()`, the tool-call frame, suspension, approval delivery, answers, choice options or pending-call replay.

Durable `approve()` replaced the `approvals` map, the AI SDK `toolApproval` path and `approvalTimeoutMs`:

- **Tool-call frame** (`effect/frame.ts`, internal): `wrapToolsForRun(tools, ctx, store, { allow?, hooks?, trust?, onSuspend?, stepIndex? })` runs every call inside an `AsyncLocalStorage` frame `{ runId, toolCallId, toolName, stepIndex, approvals, ... }` (`stepIndex` read per call: the checkpoint index of the model step that made the call; the pending calls' checkpoint index while they replay) (`runToolCall`, `currentToolCall`). Order per call: frame, `allow` (`ToolNotAllowedError`), `beforeToolExecution` (its result is the input; a changed one is re-validated through the tool's `inputSchema`, a failure a `ValidationError` tool error), `guardWhenTainted` gate (when classified and already tainted; a tool's `trust.approvalDetail(input, ctx)`, a function only, adds `detail` to the gate's private body and its binding, and sets the frame's `outboundApproved`, which the public `outboundApproved(ctx)` (`approval/request.ts`) reads so a tool skips an approval of its own the gate covered), effect lookup and execute (the effect key from the final input), `taint` persistence before a result or execution error is exposed (when classified), `afterToolExecution` (on a fresh and on a recorded result; a streaming tool's final value; never for a tool error). A thrown `ToolDeniedError` (`tool_denied`) is a tool error, `FatalToolError` still fails the run. Tools without `execute` pass through untouched.
- **`approve(ctx, { title, body?, options?, multiple?, timeoutMs? })`** (`approval/request.ts`; `ChannelHandle.approve()` is the same with `channel` and `address`): outside a frame, or in a streaming tool's body, `InvalidRunStateError`; `timeoutMs` default `DEFAULT_APPROVAL_TIMEOUT_MS` 24 h, 1 to `APPROVAL_TIMEOUT_MAX_MS` (2^31 - 1), else `ValidationError`. The n-th call of a frame (0-based, taken before any await) has `approvalId = <stepIndex>:<toolCallId>:<n>` (the step index, so a provider that reuses a call id in a later step asks again instead of reading an earlier step's decision); a decision recorded under the effect key `approval:<runId>:<approvalId>` (`approvalDecisionKey`) is returned, else the request is stashed on the frame (the first suspension of the call wins) and an internal `SuspendSignal` thrown. It sends nothing. Internal trust approvals use `bound:<sha256>` of `[stepIndex, toolCallId, n, binding]`, where the binding hashes the operation and final arguments. This keeps their ids bounded even for long provider call ids; ordinary `approve()` ids remain ordinal.
- **Suspend**: the wrapper catches the signal, records the request in call order and answers the AI SDK with `SUSPENDED_RESULT` (never stored); a stop condition ends the loop after that step. The checkpoint keeps the assistant message's tool calls and drops the suspended calls' results (`withoutResults`), no `tool` step for them; then `pause()` moves `running -> waiting` with `WaitPoint { kind: 'approval', approvalId, toolName, toolCallId, title, body?, notification?, channel?, address?, expiresAt, notifiedAt? }` from the first suspended request in call order (one approval per pause; the others stay pending and suspend again after the resume; parallel identical effect calls share one application, so a call whose shared application suspended stays pending on the same approval and gets the recorded result on replay), releasing claim and slot (a keyed run keeps its key blocked). Re-pausing on the same approval keeps the wait point, so the approval the owner was asked stays answerable; the `approvalId` is the wait point's identity (`answer()` and the delivery compare it).
- **Delivery** (`deliverApproval`): once the wait point is stored and it names a channel, the engine sends, detached from the execution (tracked in `deliveries`, awaited by `idle()` and `drain()`, so a slow `out` holds neither the slot nor the executions entry and a resume meanwhile starts the next execution cleanly; an execution only removes its own executions entry, and the queue never starts a run whose previous execution still holds its slot), `ChannelMessage { kind: 'approval', key: '<runId>:<approvalId>', title, body, approvalId, expiresAt }` (never the token) through that channel's `out` to `waiting.address`, with `{ signal, trigger }`, under the store lock `notify:<runId>:<approvalId>` held for one attempt (aborted after `claimTtlMs`), and records `waiting.notifiedAt`. For a trust gate, `waiting.notification` replaces the private approval body on this source-channel delivery; the full body remains in the inbox/API. `tick()` re-sends on every poll while it is missing; a crash before the wait-point write sends nothing, after it re-sends under the same key; a channel the engine does not hold goes to `onError` per attempt. `approve()` without a channel sends nothing (inbox and API only).
- **Answer** (`answer()`): `approve(runId, { approvalId, approved, reason?, approver? })` (`ApprovalAnswer`) and the `tick()` timeout (`approval timed out`, denied) move `waiting -> queued` (guarded by `expectStatus`, so only one answer writes), record the decision with `save('approval:<runId>:<approvalId>', { approved, reason?, approver? })`, append a `wait` step (`name` the tool, input `{ toolCallId, title, body? }`, output `{ approvalId, approved, reason, approver? }`), then clear `waiting`. A failure undoes back to `waiting`, so the wait point stays answerable. `approve()` validates the approver before any store read and refuses a run that is not waiting, another `approvalId` or a wait point at or past `expiresAt` with `InvalidRunStateError`; a run that moved on meanwhile is `InvalidRunStateError` (the `stale` factory, also for the `tick()` timeout, which ignores it).
- **Options**: `options: ApprovalOption[]` (`{ id, label, detail? }`) and `multiple` are checked by `toApprovalOptions()` in `requestApproval` (`ValidationError` tool error: 1 to `APPROVAL_OPTIONS_MAX` 20 options, ids `APPROVAL_OPTION_ID_PATTERN` (128 characters, no whitespace) and unique, a label one non-blank line (no C0/C1 control, U+2028 or U+2029, since channels write labels raw) of at most `APPROVAL_OPTION_LABEL_MAX_LENGTH` 200, a detail at most `APPROVAL_OPTION_DETAIL_MAX_LENGTH` 20 000 and `APPROVAL_OPTIONS_DETAIL_MAX_LENGTH` 100 000 together, `multiple` a boolean, `true` needing options (`false` without options is plain); other keys dropped) and copied onto `ApprovalRequest` and the `WaitPoint` (jsonb, no migration; `multiple` only when true, a plain request gets neither key). `engine.approve()` checks `ApprovalAnswer.selected` with `assertSelectionShape()` (at most 20 distinct strings) before the store read and with `toSelection()` after the state checks (`ValidationError`, the run keeps waiting): a plain wait point takes none, a denial none (an empty one dropped), a single choice exactly one, a multiple choice at least one, all known ids; the decision effect and the `wait` step's `output` get `selected` in option order, the step's `input` the `options` (details included) and `multiple: true`; the `tick()` timeout never selects. `toApprovalDecision` reads `selected` back only as a string array, so a recorded plain decision stays plain; replay goes through `fitRecordedDecision()`: a recorded denial as is, an approval with `selected` re-ordered to the options the tool passes now, or `{ approved: false, reason: 'options changed' }` (approver kept) when it does not fit them under `toSelection()`'s rules (an id not offered, a single choice now, a selection for a now plain request, none for a request that gained options), so a tool never gets an id it did not offer. `deliverApproval` spreads `options`/`multiple` into the `ChannelMessage`; `consoleChannel()` prints `select one:` (or `select one or more:`) and `option <id>: <label>` lines before the `approval ... waits` line.
- **Artifacts**: `artifacts?: string[]` on the request and on each option name the run's artifacts to show (ids from `ctx.artifacts.put()`, keyed puts so a replay re-puts the same ids). Shape checks with the options (`toArtifactIds()`/`collectArtifactIds()`: unique non-empty strings, `APPROVAL_ARTIFACTS_PER_OPTION_MAX` 20 per option, `APPROVAL_ARTIFACTS_MAX` 100 in total), then in `requestApproval` after the recorded-decision lookup (a replay with a decision skips it, so a failed list never hides the decision) one `frame.artifacts.list()` (the wrapper's `ctx.artifacts`) must hold every id (`ValidationError` tool error, no pause). Copied onto `ApprovalRequest`, the `WaitPoint` and the `wait` step's `input` only when non-empty; `fitRecordedDecision()` ignores them. Never in a `ChannelMessage` (`deliverApproval` copies options without `artifacts`): private images stay in the inbox and API.
- **Pending calls** (`engine/execute/`): the next execution first finds the checkpoint's assistant tool calls without a result (`pendingToolCalls`) and runs them in order through the wrapped tool set with their recorded ids (`executePendingCall`), re-applying what the AI SDK would: `toolPolicy` (`ToolNotAllowedError`), the input schema parse (`ValidationError` result), the `contextSchema` check for third-party tools (fails the run), the hooks. After each finished call the checkpoint gets its result first (`withToolResults`, saved under the same `stepIndex`), then its `tool` step, so a drain, crash or lost lease after it never runs it again; no further call starts once the execution was aborted, and an abort waits for that write before settling. A call that suspends again pauses without a model call. Then the model loop starts. The model sees only the tool's result; the decision lives on the `wait` step. Code before `approve()` runs again on resume (documented replay rule, as for crash recovery). A checkpoint with pending calls gets one step beyond `maxSteps`.
- No resume tokens: an approval is answered only by run and approval id (`engine.approve()`, `@chamvi/http`'s authenticated `POST /runs/:id/approve` and MCP `approve_run`), so there is no `resumeSecret` and no message carries a credential.
