# Architecture

## Core Concepts

App, Agent, Channel, Run, Step, State, Tool, Workspace, Repository. Keep the concept surface at about ten. chamvi never wraps the AI SDK: models (`LanguageModel`), messages (`ModelMessage`) and tool sets (`ToolSet`) are passed through as-is.

`@chamvi/core` holds: agent definitions with channel subscriptions and tool hooks, the `IChannel` contract and the tool-driven outbound (`ToolContext.channels`, `consoleChannel()`), the `Engine`, step checkpoints, budgets, effect tools, durable approvals (`approve()`, answered by run and approval id), recovery and drain, agent state, streaming deltas, structured output, run artifacts (attachments and tool files), the `IStore` aggregate, `createMemoryStore()`. Everything time-based goes through an injectable `IClock` (`systemClock`; `ControllableClock` in tests). The public surface is `src/index.ts`. `@chamvi/test-kit` exports `describeRepositoryContract` and `ControllableClock`.

## Engine

Use `IEngine` for engine references in contracts, fields and function parameters. It extends `IContextProvider` and describes the engine's public operations, including readonly `store`, `clock` and `isDraining`. `Engine` implements it and remains the concrete constructor and subclass base.

`new Engine({ store, agents, ... })` validates at construction (`InvalidAgentDefinitionError`): agent and channel names unique (channel names follow the agent-name rule, `assertChannelName`), every subscription must name a registered channel (`assertRegistrable`: `Agent "<a>" subscribes to unknown channel "<c>".`), and every agent's model must resolve (see Models below). Defaults: `claimTtlMs` 60 s, `concurrencyMaxRuns` 4, `owner` `${hostname}-${pid}`, `clock` `systemClock`, `onError` logs to `console.error`. `start({ channels? })` recovers, starts every channel (see [Channels](topics/channels.md)) and begins polling; `dispatch`, `cancel`, `approve`, `tick`, `recover` and `drain` are the operations; `provide(key, value)` (`IContextProvider`) holds the values tools inject (see [topics/agents.md](topics/agents.md#context)). The engine is the one source of what an app is built from: `store` and `clock` are public readonly fields, `getAgent(name)` and `listAgents()` (registration order, a new array) read the registered agents and `getChannel(name)`/`listChannels()` the channels, so channels and `@chamvi/http` take only the engine. `on(type, listener)` is typed per event (`run.updated` carries `run`, `step.appended` carries `step`, `run.delta` carries `delta`) and sees local events only.

The live agent registry (`putAgent`, `removeAgent`, revision markers) and model resolution (`ModelRef`, `IModelResolver`) are in [topics/agents.md](topics/agents.md).

## Cross-cutting Rules

Each rule has its detail in a topic file; these are the ones a change outside that area breaks silently.

- **Agents** ([agents.md](topics/agents.md)): `defineModelAgent()` (`defineAgent()` its deprecated alias) and `defineSimpleAgent()` return `{ kind, name, definition }` with budget defaults (`maxSteps` 20, `timeoutMs` 15 min); names match `^[a-z0-9]+(-[a-z0-9]+)*$` (at most 64). One `ToolContext { run, state, artifacts, channels }` per execution, passed only to chamvi tools (`contextSchema === toolContextSchema`); nothing provided through `engine.provide()` is stored, cloned or serialized, and `inject(ctx, key)` works only on the context the engine passed. Tool code reaches a model through `resolveModel(ctx, ref?)`: the AI SDK never sees a string model and its global provider is never consulted. An AI SDK `needsApproval` tool is refused. `toolPolicy` shapes `activeTools`; `wrapToolsForRun` re-checks every call. A simple agent (`defineAgent({ run })`, no model) runs `run()` in one synthetic tool-call frame (ids `0:run:<n>`) and re-runs it from the start on every execution (the replay rule).
- **Live registry** ([agents.md](topics/agents.md)): `putAgent`/`removeAgent` run under the store lock `agents:<name>` and cancel unsettled runs of a changed revision once across replicas; a queued run whose agent revision this replica does not hold stays `queued`, never fails with `unknown agent`.
- **Channels** ([channels.md](topics/channels.md)): the presence of `start`, `in` and `out` is a channel's only capability. Outbound is tool-driven: the engine sends nothing of its own except the approval requests a tool asked for. `ChannelHandle.emit()` is an effect keyed by run, channel and canonical message, so `out` must be idempotent on `message.key`. Dispatches (#129) reach `agent.on()` roles of the caller's or another agent (`from`), depth per role up to 8; lineage (`parent`, `parentRunId`) is never forgeable through `engine.dispatch()`.
- **Trust** ([trust.md](topics/trust.md)): `Run.taint` is durable first-exposure provenance, persisted before an untrusted result or error reaches the model (a failed write fails the execution). `guardWhenTainted` runs after the before hook and before effect lookup; trust approval arguments stay in the private inbox/API, the source channel gets only a generic notification. Destination exemptions (source address, `defaultAddress`) fix the destination, not the content. Shell is not gated; this is no sandbox, DLP or injection defense.
- **Approvals** ([approvals.md](topics/approvals.md)): `approve()` works only inside a tool-call frame; ids are `<stepIndex>:<toolCallId>:<n>`, taken before any await. A suspended call re-runs its code before `approve()` on resume (the replay rule). No resume tokens: an approval is answered only by run and approval id, and no message carries a credential.
- **Packages without a `/module` import of `@chamvi/app`**: see conventions.md → *Feature package modules* and *Dependency graph*; the package graph stays acyclic in all four dependency fields.

## Run Lifecycle

Run statuses are exactly `queued | running | waiting | completed | failed | cancelled | interrupted`. Steps are `llm | tool | wait`.

```
dispatch -> queued -> running -> completed | failed | cancelled
running -> waiting (a tool awaits approve()) -> queued (an answer or the timeout) -> running
running -> waiting (a tool awaits waitForDispatch()) -> queued (children settled or the timeout) -> running
running -> interrupted (drain) -> queued (recover) -> running
running with an expired claim (crash) -> queued (recover) -> running
```

- **Intake**: `dispatch` first refuses an `idempotencyKey`, `concurrencyKey` or `address` above `TRIGGER_KEY_MAX_LENGTH` (255, the store's varchar width) or with a NUL (`assertTriggerKey()`, `trigger/key.ts`, `ValidationError`, before any store write); channels (`webhookChannel()`, `githubChannel()`) use the same helper. With an `idempotencyKey`, `dispatch` claims `(scope, key)` in the `IIdempotencyRepository` (TTL 7 days); the scope is `<agent>:<channel>`, and with an invoker `<agent>:<channel>:<kind>:<id>` with `kind` and `id` each `encodeURIComponent`-ed (`idempotencyScope()`, `trigger/helpers.ts`), so two invokers sending the same key get a run each and one principal cannot squat another's key; a duplicate returns the existing run id with `deduplicated: true`. A key whose run was never created (runs.insert failed after the claim) is healed by the next dispatch, which creates the run under the reserved id; `runs.insert` is insert-if-absent, so concurrent healers create it once.
- **Attachments**: `dispatch` validates each `ArtifactInput` (`mediaType` `type/subtype` without parameters, optional string `filename`, `data` a `Uint8Array`; `ValidationError`) before any store write, then, after the idempotency dedupe returned (a duplicate stores nothing), stores each as an artifact of the run (id `<runId>.<index>` from `attachmentIds()` in `artifact/module.ts`, the index zero-padded to one width per dispatch, at least 4 digits, so `find` (createdAt, then id) returns the input order; `size` = byte length, `createdAt` = run createdAt) and creates the run. Tool artifacts (`artifacts.put()`) keep `randomUUID()` ids; a keyed put (`put({ key })`, 1 to 255 characters, no NUL; refused on a dispatch attachment) uses `keyedArtifactId()` = `<runId>.k.<first 32 hex of sha256(key)>` and `IArtifactRepository.save`, so the same key replaces (never an attachment id, fits `varchar(128)`). `storeArtifact` relies on `insert`'s insert-if-absent: when the id is taken by the same run it returns the stored artifact (another run's: `InvalidRunStateError`), so concurrent healers of one reserved key write to the same ids, the second write is a no-op and `trigger.attachments` always names what the store holds (the first writer's bytes). A crash between storing and `runs.insert` leaves orphan artifacts (accepted; nothing purges artifacts yet), and a racing healer that sends more attachments than the winner leaves its extra indexes listed on the run.
- **Scheduling** (`engine/queue.ts`): a pass lists `queued` runs FIFO (createdAt, then id) and starts them up to `concurrencyMaxRuns`. **Execution guard**: a pass that found queued runs first builds a start predicate (`prepareStart`, one `find()` read, skipped while no folder agent is registered): a run may start when `cancelRequested` (it settles `cancelled`), or when its agent is registered here and has no revision or is loaded at the stored marker's hash; any other run is skipped before any claim and stays `queued` for a replica that has the agent's current revision (never failed with `unknown agent`). `execute()` re-checks after the claim (`isCurrent`, one `findOne`) and hands a run whose agent was removed or replaced meanwhile back to `queued` (owner-guarded); recovery requeues as before, so the guard also covers recovered runs; `tick()` keeps skipping approval deliveries of unknown agents. A keyed run starts only when no other run of the same agent and `concurrencyKey` is `running`, `waiting` or `interrupted`; check, claim and transition happen under a store lock `concurrency:<agent>:<key>` so it holds across replicas.
- **Claims**: `claim(id, owner, claimTtlMs)` is a lease, renewed every `claimTtlMs / 3`. The poll runs on the same interval and calls `tick()` (approval expiry) and `recover()`. Every write of a running run is conditional on status and owner; an engine that loses its lease aborts the execution, writes nothing more and reports a `LeaseLostError` to `onError`.
- **Execution** (`engine/execute.ts`): one `ToolLoopAgent.stream()` call per execution (consumed to the end; settling reads the result's `steps`, `finishReason`, `text`, `output` promises), starting from the latest checkpoint. Checkpoints hold the stored messages (artifact markers); the model gets a hydrated copy whose marked file parts carry the bytes from `read` (a missing one fails the run with `ArtifactNotFoundError`), also the file items of a tool result's `content` output a tool built with `artifactFilePart(artifact)` (public, `artifact/module.ts`: `{ type: 'file', mediaType, filename?, data: { type: 'data', data: <marker> } }`), hydrated again per model call through the `ToolLoopAgent`'s `prepareStep` (a result made in this execution reaches the next model call with its bytes, while the response messages the checkpoint saves keep the marker), and the engine saves `[...storedInitial, ...responseMessages]`, so the pending-call path after an approval works on stored messages. Each `text-delta`/`reasoning-delta` part is emitted as `run.delta` (`RunDelta { runId, step, kind: 'text' | 'reasoning', text }`, `step` = the checkpoint `stepIndex` the step is saved under); deltas are never stored, local to the executing replica and never emitted once the execution was abandoned. No opt-out: every AI SDK provider streams. A model call that fails mid-stream (an `error` part) still ends its step: the AI SDK finishes it with finish reason `error`, so the engine appends the `llm` step (the partial text) and saves its checkpoint before the run fails with that error. A step whose provider stream closed without its finish part (the AI SDK then synthesizes finish reason `other` and never executes the step's tool calls) fails the run with `IncompleteResponseError` (`incomplete_response`); the engine tells it apart through `onLanguageModelCallEnd`, which fires only for a received finish, so a provider that reports `other` itself still completes.
- **Structured output**: with `output`, a `completed` run's `output` is the parsed value (else the text); a final answer that fails to parse or validate (`NoOutputGeneratedError` or a schema failure) fails the run with `ValidationError` (`validation_error`, message from the cause, the cause cut to `MAX_ERROR_CAUSE_LENGTH` 500 characters plus an ellipsis, `execute/constants.ts`). Before parsing, a loop end with no answer fails with `IncompleteResponseError` (`incomplete_response`, `incompleteOutput()` in `execute/helpers.ts`): finish reason `length` (cut answer) or `tool-calls` outside a budget stop (a call nothing executed, e.g. a tool without `execute`, named in the message). A plain agent keeps completing with the text in both cases (decided: its text is still usable and the llm step records the finish reason). The "step limit reached by an earlier execution" branch parses the checkpoint's last assistant text through `output.parseCompleteOutput` with the same rules (a `length` checkpoint is incomplete). The `ToolLoopAgent` gets `withoutPartialOutput(output)` (`execute/helpers.ts`): a prototype copy whose `parsePartialOutput` returns `{ partial: text }` without parsing, so the AI SDK neither re-parses the accumulated answer per delta nor holds deltas back (returning `undefined` would publish the whole text at `text-end` only); `parseCompleteOutput` and `responseFormat` stay the agent's. After every step the engine appends the steps and saves a checkpoint (messages plus the step's `finishReason`). A cancel or drain abort lets the step-end writes in flight finish (all tool rows and the checkpoint of a completed step), so a recovery does not redo a step whose tools already ran; an abandon guard then stops a still-running generate from writing after the run settled. Each execution owns an `AbortController` combined into the signal the agent and the tools get (`run.signal`); it aborts on every exit, so a throw while consuming the stream (e.g. a throwing `onError` behind a failing `run.delta` listener) cancels the model stream instead of leaving it open.
- **Budgets** (`engine/budget.ts`): `maxSteps` and `maxTokens` are stop conditions, `timeoutMs` an abort signal per execution (built on the `IClock`). Stopped by a budget while the last step asked for tool calls: `failed` with `BudgetExceeded`; otherwise `completed` (a plain agent), or for an agent with `output` the structured-output rules apply (a `length` finish fails with `incomplete_response`). Timeout: `failed` with `Timeout`.
- **Tool errors** go back to the model as tool-error results; only `FatalToolError` (and infrastructure or store failures) fail the run.
- **Cancel**: aborts a local execution (`cancelled`), or marks a `queued`/`waiting` run cancelled. A run `running` on another replica (or `interrupted`) gets `cancelRequested: true`; the owner sees it in `recover()` on its next poll and aborts with stop `cancel`, and an execution that starts on such a run settles it `cancelled` without a model call. A cancel that races a pause (the abort cannot interrupt the `waiting` write) cancels the run the pause left waiting, without delivering the approval.
- **Drain**: `drain({ timeoutMs })` stops every channel first, then stops polling and starting runs, waits for in-flight runs and approval deliveries within the same deadline (default 30 s), then aborts leftovers and marks executing runs `interrupted` with the claim released. Aborted approval deliveries stay unnotified and retryable; an abort-ignoring transport cannot hold drain until its separate claim TTL. `stop()` stops the channels, then only polling.
- **Recovery**: `recover()` (on `start()` and every poll) claims each `running` or `interrupted` run whose claim expired or was released and requeues it; the next execution continues from the latest checkpoint. A step whose checkpoint never landed runs again.

## Repository Contract

`IStore` (`src/repository/types.ts`) is a plain aggregate of separate capability implementations: `runs`, `steps`, `checkpoints`, `idempotency`, `locks`, `effects`, `state`, `artifacts`, `agentRevisions` and optional `conversations`. `Engine.store` exposes that aggregate; each consumer uses only its needed role. There is no facade forwarding repository methods: access capabilities directly, for example `engine.store.runs.findOne(id)`. Factory options are `MemoryStoreOptions` and `DatabaseStoreOptions`; the database factory returns `DatabaseStore`.

| Interface | Holds |
|-----------|-------|
| `IRunRepository` | Runs (`insert` derives `parentRunId` from `trigger.parent`, refuses an absent parent); `update` with `expectStatus`/`expectOwner`/`expectWaitId` guards; `find` filters `ids`/`parentRunId(s)`/`hasParent`/`waitKind`, ordered by createdAt then id (asc, or desc with `order: 'desc'`), unbounded without `limit`; `claim`/`renewClaim` leases |
| `IStepRepository` | Append-only steps per run |
| `ICheckpointRepository` | Latest checkpoint per run (highest `stepIndex`; equal index replaces) |
| `IIdempotencyRepository` | `claim(scope, key, runId, ttl)`: first caller wins |
| `ILockRepository` | `acquire`/`release` of keyed leases |
| `IEffectRepository` | Recorded effect results by effect key |
| `IStateRepository` | Per-agent KV (`set(..., undefined)` removes the key; `find(agent, { limit?, offset? })` in key code-point order, unbounded without `limit`) and document collections (`where` = top-level equality) |
| `IAgentRevisionRepository` | One revision marker per folder agent, `AgentRevision { agent, hash, changedAt }` (no code): `findOne`, `save` (upsert), `delete` (missing is a no-op), `find` (agent code-point order); copied in and out |
| `IArtifactRepository` | `insert(artifact, data)` (atomic insert-if-absent, `false` keeps the stored one), `save(artifact, data)` (atomic upsert by id: same run replaces metadata and bytes, keeps `createdAt`; another run's id `InvalidRunStateError`), `findOne` (metadata), `read` (bytes, a plain `Uint8Array`), `find(runId)` (createdAt, then id); bytes copied in and out |

Rules every implementation must keep: a TTL created at T with `ttlMs` is expired at exactly `T + ttlMs`; values are copied in and out (no aliasing); atomic operations are atomic across callers; `steps.insert`, `checkpoints.save` and `conversations.beginTurn` for a run the store does not hold throw `RunNotFoundError` and write nothing (memory: `hasRun`; Postgres: `withRunReference()`, see [store.md](topics/store.md)). The separate classes assembled by `createMemoryStore()` implement these contracts in-process (structured clones, no await between check and write). `describeRepositoryContract((clock) => store)` from `@chamvi/test-kit` is the shared Vitest suite every store must pass; the factory must use the given `ControllableClock` for expiry. Redis is never required.

Repository queries use `findOne` (record or undefined) and `find` (existing array/page shape); matching `OrFail` methods throw on an absent record or an empty selected page, even when its total is nonzero. Stored falsy state values remain present. Single run/artifact failures keep their specific errors; other absence uses `RepositoryNotFoundError`. Multi-collection queries keep descriptive names (`findDocuments`, `findItems`, `findNotes`, `findOneNote`) with matching `OrFail` variants. Persistence adapters do not gain generic ORM query options or an inheritance hierarchy.

The Postgres store and its migrations: [topics/store.md](topics/store.md).

## Idempotency and Side Effects

1. Trigger dedupe at intake via `IIdempotencyRepository`.
2. Completed steps are never repeated: execution resumes from the latest checkpoint.
3. Side-effecting tools use `defineEffectTool()`. Per call the wrapper (`wrapToolsForRun`) returns the recorded result for the effect key, else asks `alreadyApplied(effectKey, input, ctx)`, else executes and records the result; both hooks get the `ToolContext` (`ctx.run`, `ctx.state`, `ctx.artifacts`), and a custom `effectKey(input, ctx, options)` also gets the AI SDK call options (`toolCallId`, `messages`, e.g. to key by model step). The default key is `${ctx.run.runId}:${toolName}:${sha256(canonical JSON of input)}`. A throwing execute records nothing; a crash between the effect and the record repeats it unless `alreadyApplied` finds it (`effectMarker(key)` is the hidden marker to embed). Parallel identical calls in one step share one application.

## Errors

All errors extend `ChamviError` (ebec `BaseError`) with a `code`: `InvalidAgentDefinitionError` (also every model and provider problem: an agent with no model and no default, a provider that is not configured, a missing key or package, a malformed setting; a tool error from `resolveModel` in `execute`), `BudgetExceededError` (`BudgetExceeded`), `FatalToolError`, `IncompleteResponseError` (`incomplete_response`), `ContextNotProvidedError` (`context_not_provided`, a tool error in `execute` and effect hooks, a failed run from the tools factory), `RunNotFoundError`, `ArtifactNotFoundError` (`artifact_not_found`), `InvalidRunStateError`, `LeaseLostError`, `TimeoutError` (`Timeout`), `ToolNotAllowedError` (`tool_not_allowed`, only ever a tool error), `ToolDeniedError` (`tool_denied`, a gate's refusal, only ever a tool error), `ChannelNotFoundError` (`channel_not_found`, `ctx.channels.findOneOrFail()` for an unknown channel or one without `out`, and an approval delivery through a channel the engine does not hold, to `onError`), `AgentNotFoundError` (`agent_not_found`, `dispatch` for an agent the engine does not hold, http 404), the run-only codes `agent_replaced` and `agent_removed` (`ErrorCode.AGENT_REPLACED`/`AGENT_REMOVED`, stored on runs a registry change cancelled, no class), `SandboxError` (`sandbox_error`, a workspace or provider failure, only ever a tool error), `ValidationError`; the codes are `ErrorCode` (`errors/constants.ts`); outside core more codes exist: `github_request` (`@chamvi/github`'s tool errors, never fatal, and its channel's send failures), `openclaw_request` (`@chamvi/channel-openclaw`), `web_request` (`@chamvi/tool-web`'s request failures, never fatal), `chat_request`, `chat_intake_failed`, `chat_stop_timeout` (`@chamvi/chat`) and `whatsapp_auth`, `whatsapp_connection`, `whatsapp_logged_out` (`@chamvi/chat-whatsapp`, reported to `onError`). A failed run stores `{ code, message }` in `run.error`.

## Deploy Kit (outside this repo)

The deploy kit has four parts: `@chamvi/app` + `@chamvi/cli` (above), the base image `ghcr.io/chamvi/node:26` (`images/node`: `node:26-trixie-slim`, tini entrypoint, uid 1000, workdir `/app`), and two repos of their own. Both follow this repo's contract, so changes here are checked against them ([Downstream Repos](../AGENTS.md#downstream-repos)).

- **Chart `agent-app`** ([chamvi/helm](https://github.com/chamvi/helm), `oci://ghcr.io/chamvi/helm/agent-app`, 0.1.x; map in [references/helm.md](references/helm.md)): Deployment (Recreate, probes under `basePath`, preStop sleep 5 s, grace 120 s, guard `preStop + CHAMVI_FORCE_EXIT_MS < grace`), Service, optional Ingress with a derived `CHAMVI_PUBLIC_URL` (origin only), optional run-job CronJobs (`Forbid`, `backoffLimit: 0`; they set `CHAMVI_SCHEDULER=false` everywhere), sandbox Role/RoleBinding and an egress NetworkPolicy (DNS plus TCP 443 to public addresses) or, opt-in, a CiliumNetworkPolicy, optional ServiceMonitor, a helm test hook. Value `command` renders into `args`, so tini stays PID 1. Released by release-please plus `tada5hi/hevi`.
- **Template** ([chamvi/agent-template](https://github.com/chamvi/agent-template), a GitHub template repository; map in [references/agent-template.md](references/agent-template.md)): one example agent on `@chamvi/app`, a two-stage Dockerfile on `ghcr.io/chamvi/node:26` (by digest), CI with a read-only docker smoke, Flux examples (`OCIRepository`, `HelmRelease`, image automation) for the chart, image tags `main-<sha7>-<commit unix ts>` and `<semver>`.
